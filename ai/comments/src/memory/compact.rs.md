# compact.rs

Spec §4. Library for `ai memory build`.

- Prompts: `prompts/compact.txt` is the spec's COMPACT verbatim with "OptChat" → "ai" (line breaks shift; whitespace only). `prompts/scale.txt` is a 50-word (`WORDS`) lorem ipsum size reference, introduced as meaningless filler. Tasks and retries give the model a word target only, never `NODE`: told "at most 512 bytes, about 60 words", Sonnet aimed at the ceiling and missed it (38 of ~95 first tries over 512; all 4 failures 513-524 bytes after 5 retries stating the bytes over). The prompts drop "non-ASCII characters cost 2-4 bytes" for the same reason. It replaced shitty-optchat's realistic SCALE line, whose content (export.py, --verbose, ship tonight) Haiku 5.5 copied into summaries.
- `message`: the step alone, no context and no ids. OptChat gave the compactor the whole view (up to 128 KB) so chat messages could be resolved; notes stand alone (OptMem's `nap` prompt also carries only the block), and the context made every call ~50k tokens.
- `summarize`: `write_line` under `COMPACT`. `write_line` and `ruler` are shared with `ai chat`'s roll-up (`src/chat/summarise.rs`), which has its own system prompt and tasks. `write_line` returns the call's `Who` (backend agent and model, the conversation's session) with the line; `put_node` records both. Trimmed, flattened reply; empty fails; over `NODE` → a retry in the same conversation stating the line's words and asking for a complete rewrite of at most `WORDS` words, or fewer for a line of long words or non-ASCII that overruns `NODE` in fewer (as many as fill the 365 bytes `WORDS` words take at 7.3 a word) (showing the line cut at the limit made models truncate mid-sentence), up to `TRIES`; the shortest try wins (may stay a few bytes over: `NODE` is a target).
- `Compactor`: single-owner pump. The owning thread holds the `Store` and `Mem`; each job runs `summarize` on its own thread with an owned `Job` and sends the result back on a channel. Commit = `put_node` (one commit, with cascaded free parents), then the view refits. A failure is reported once per node (`take_reports`) and the node stays busy for its next backoff delay, then is pumped again; see Retries below. The job's context is snapshotted when the pump decides (rule 3 holds at that moment).
- Lock: `compact.lock` in the memory dir, `Store::try_lock` (advisory `File::try_lock`, released by the OS when the process dies). `new` returns `None` when held. A store upgrade takes the same lock (store.rs.md).
- `run`: until nothing is due on the latest snapshot (re-absorbs notes from other processes before deciding it is done). `settle`: until every view line is built (stage 2's pre-turn wait). `log`: append messages and pump (stage 2).
- `refresh` absorbs external commits and pumps. `step` drains all completed jobs; `next_retry` bounds its wait. Dropping a compactor calls `Backend::stop`; Claude closes its registry and ends every running call, including concurrent opens. Detached worker results are discarded after shutdown.
- Logging: `pump` hands each job thread the current dispatcher and span, and times the call (`Done` carries the duration). `finish` logs INFO `built` (node as id+n, bytes, secs) and WARN `failed` on a node's first failure, with the `wait` before its retry (repeats at DEBUG, matching `take_reports`, so a dead backend does not flood the unrotated log). `summarize` logs WARN `over limit` per over-NODE reply, with that request's tokens and cost. Without a subscriber these are no-ops.
- Spend: `write_line` adds each request's `Conversation::used` to the caller's `Spend` through `ask`, even when the call fails, marking requests after the first as retries; `Done` carries it, so `built`, `failed` and the run's `end` (`Compactor::spent`, summed by `cli::rounds`) show requests, retries, tokens and cost, all and retries only (`log::spend!`).
- Retries: `backon`'s `ExponentialBackoff` used as a plain iterator of delays feeding `waits` (the compactor keeps its threads and queue; backon's async `Retryable` is there if it moves to Tokio). `Options::backoff`: from `retry` (`RETRY`, 10 s) doubling to `RETRY_MAX` (5 min), with backon's jitter (adds 0-100% of each delay, so 8 waits base 10+20+40+80+160+300+300+300 s total 20-40 min), `retries` (`RETRIES`, 8) times. When a node's iterator is exhausted, `finish` returns `GaveUp` (node, tries = retries + 1, last error): `step`/`run` fail, the caller drops the compactor (lock released, running calls stopped by `Backend::stop`), unbuilt nodes stay pending. Before, a dead backend (usage limit, logged out, bad `AI_MEMORY_MODEL`) left the unwatched note-spawned nap retrying every 10 s forever.
- Bound per node, not per run: one backoff per failing node, kept in `failed` (which already tracked "failed since last success" for reports) and dropped on success. A run-wide streak would advance once per failed call, so `jobs` (8) nodes failing together in one wave would burn the whole bound in seconds, and one node's delays would depend on unrelated nodes. Per node, a dead backend still ends the summariser within one node's schedule (all nodes fail together), a transient outage recovers each node independently, and a node that alone keeps failing (e.g. always an empty reply) ends the summariser too instead of blocking its parents forever.
