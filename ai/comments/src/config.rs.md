# config.rs

`ai.toml`: every setting `ai` reads, one table per tool (`[chat]`, `[agent]`, `[memory]`, `[summariser]`) and one per agent (`[agents.<name>]`), keys kebab-case as Cargo's. Each table is its tool's own type (`agent::Config`, `agent::Table`, `memory::Config`, `summariser::Config`), so a tool owns its keys, defaults and checks. A project's file also holds `[project]` (`project::Table`, project.rs.md).

- Three files: the user's in `home()` (`~/.ai/ai.toml`, from `$HOME`); the project's, the nearest `ai.toml` at or above the cwd, found as Cargo finds `Cargo.toml`; and the private settings (`private_file`: `ai.toml` in the private store, `.ai/local/ai.toml`, in the project's home, `project::home`: the main checkout when the cwd is in a linked git worktree), one user's overrides, kept out of version control and so absent from a new worktree, with history in the private store. `LOCAL`, `ai.local.toml`, is only the link `ai init` makes to them beside `ai.toml`, so a human finds them where the convention puts them; the loader reads the store's file, not the link. An `ai.local.toml` that is a file of its own fails every load (`check_link`), since reading only the store's file would drop its settings silently. The search skips the user's file (`nearest`, compared by path, then canonically), so a cwd under `~/.ai` is not in a project. Only the nearest project file and its project's private settings count; one anywhere else is not read. Each file's value of a key wins over the one before (`Layer`, folded in that order); a key none sets keeps the tool's default.
- `[agents.<name>]` (`Agent`) is the one table keyed by name: the maps merge by name, then each agent key by key, so the private settings can move one agent's worktree and keep its instructions. `instructions` is the exception: each file's adds to the list, user's first, then the project's, then the private one, so a role's general instructions in `~/.ai` travel with it and a project adds its own on top. Each resolves as its file is read, against that file's folder (`Agent::from`): instructions belong with the definition, so an agent in `~/.ai/ai.toml` keeps them in `~/.ai` and moves from project to project. The private settings resolve against the home instead, where their link sits: a human edits them through `ai.local.toml` beside `ai.toml`, so their paths read from there, and `agents/` in the store's own folder is the thread store. `worktree` resolves once, after the fold, against the project's home, whichever file set it (`Agent::under`): a worktree belongs to the project, and resolving from the home rather than the checkout `ai` runs in makes `../dev` the same directory from the main checkout and every linked worktree. Outside a project there is no root, and a relative `worktree` stays as written. `Agent` has no harness or model: an agent is tied to neither (ai/research/20261024T084514--agents.md).
- `File` is one file as written, `[project]` included; `Settings` is what the files set together. `[project]` in the user's file or in the private settings is an error: the project's id and name are its identity, the same for everyone. `Project::find` reads only `ai.toml`, so such a table is reported by the commands that read settings.
- A missing file sets nothing. An unreadable one, a TOML error, an unknown table or key, or a bad value fails the command with the file's path before the TOML error, which shows the line and the key (`main` prints only the outermost message, so the path is part of it, not a context).
- Only `ai init` writes `ai.toml`, and only `[project] id` (project.rs).
- `Settings::find` is the CLI's; `Settings::load` takes the user's file as an argument, for tests.
- Who loads it: `ai memory` and `ai view` at the command's start (`memory::Runtime::config`), `ai notes` at the command's start for `[summariser]` (`notes::Runtime::summariser`), `ai agent` when a command needs its settings (`Store::settings`, from the directory the store was found from), and `Project::find` for `[project]`.
