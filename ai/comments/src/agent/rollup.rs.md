# agent/rollup.rs

Design: `ai/research/20261014T002322--chat-design.md`, Roll-up. Pure: what lines a thread has and what each is made from; summarise.rs builds them. Sizes from `20261014T200729--step-compaction-cost.md`; prompt points from `20261014T002032--chat-rollup-prior-art.md` and OptChat's "Compactions" (`/hatimthayyil/code/optchat/optchat.md`).

Rendering
- `render`: each item's `render::item_line` and a newline, the line the view prints (render.rs.md): `t.i|kind: text`, the id from the item's place (model.rs.md), the same on every branch through it, so each item renders once. The prompt asks each finding to cite the item holding its detail as `[t.i]`, so a line points where to zoom. Memory's compactor hides ids because the model copied them; here copying them is the point.
- `CUT`: tool inputs and outputs at `CLIP` = 4 KB, messages and replies at 24 KB (half the input, so no single item fills a chunk). Items stay whole in the store.

Turns in three parts
- A turn is its message, its work and its final reply (`Turn::reply`, `Turn::work`, model.rs.md). The final reply is the item that ends the turn when that is the assistant's text; Claude Code marks it `end_turn`, the reply that tells the user what came of the work. Text before it reads as the agent narrating to itself. A turn a message cuts short, or one the user interrupts, has none: its work is every step after the message.
- The work has its own lines (`Source::Chunk`, level 0): one work line `t.1+n` when it fits `INPUT`, else one per chunk. The turn line (`Source::Turn`) is written from the message, the work lines in order and the final reply, so a long run is read once, by the work line's call, and the turn line's call reads a few hundred words. A turn with no work has no work line; its turn line reads the message and reply.
- The view can then show a recent turn as its message and final reply word for word with the work line between them, and an older one as its turn line (view-structure work, not yet in view.rs).
- A message never falls in a turn's work: every user or work item opens a turn (`Kind::opens`), including a message the user sends mid-run (claude.rs.md, test `a_mid_run_message_opens_a_turn`), which closes the turn before it with no final reply.

Chunking (`chunk`)
- Over a turn's work (`Turn::work`), always: one chunk when it fits `INPUT` = 48 KB. Greedy over its steps: whole steps while they fit; a step over the budget starts a chunk and is cut before each tool call the same way; a piece still over it (a tool call with many parallel results) is a chunk alone. The message is not in a chunk: it is each chunk call's `<context>`, clipped to 4 KB.
- The cut before an over-budget step keeps chunks stable as items are appended: a chunk is final once another follows it (test `chunks_but_the_last_stay_as_items_are_appended`). `Part::chunks` is the whole cut; `Part::done` the chunks that have lines: all once the turn is closed, else all but the last, which waits until it is closed. The last chunk of a turn is keyed at most at `Turn::last` (`chunk_last`), so markers appended after an ended turn keep its key. An open turn has no final reply yet, so its work is every step so far; when it closes on a reply, the reply leaves the last chunk, and the done chunks before it are unchanged (chunks are fixed by their prefix).
- Keys: chunk `0@last`. A chunk's range is fixed by the items above `last` except in one case: a fork inside an over-budget step that is itself split into pieces could give two branches different chunks ending at the same item. Claude Code forks at user messages (claude.rs.md), so the key's first writer wins and the case is left.

Lines (`Rollup`)
- `Rollup::new(tree)`: renders every item once, then for every tip (`Tree::tips`) walks its branch (`branch`): `model::turns` on the path, chunks per turn, `Branch::lines` (turn lines of the closed turns) and `nodes` over them. Lines are merged by key across branches (first wins), so a shared prefix gives one record. Subagent items are not rolled up.
- `Source`: `Chunk` (work items, message as context; `whole` when it is the turn's whole work), `Turn` (message, work lines, final reply), `Node` (two lines). `children` are the lines it needs: a turn line waits for its work lines.
- `nodes`: aligned pairs from the first closed turn of the path, level + 1, keyed by the right half's last item. A node over turn lines is level 2; position 0 is the first turn from the root, whichever session it came from.
- `words`: a line's target, its `size` over `RATIO` (10), clamped to `WORDS`..`MAX_WORDS` (50..200). `size` counts the AI's own words and `CALL` (20) per tool call in the items a line covers, summed up the tree for turn lines and nodes (a turn line covers its work and its reply); messages and tool output count nothing, so a large Read never lengthens a line. `work_limit` is a work line's accepted bytes from its items alone, so the view can bound a recent turn before its lines exist. On the ai-chat thread this puts a median turn (about 350 words, 5 calls) at 50 and the largest (2,265 words, 58 calls) at 200. A node's target is about the sum of its halves', so a node joins free until the cap binds; calls merge only turns raised to 50 by the floor, and lines at the cap. Constants until the config system.
- `free`: a line whose input fits its `limit` (512 characters per 50 words asked) is that input flattened, items without their ids (`bare`): no call. Ids at the head of a free line read as a line id inside a line (`216-240|216|user: …`). Sizes are summed before any string is built, as the compactor asks this for every pending line after each call. A turn whose work line is short and reply brief joins free: `user: … <work line> ai: …`.
- `task`: the ruler (memory's `SCALE` repeated to the target), the order with its word target (`words`, never bytes) (`Compress the work of this turn, the steps between its message and its final reply` / `this part of the work of a long turn` / `this turn, given as its message, the lines of its work in order and its final reply` / `Merge these two adjacent lines`), `<context>` (the message) for work lines, `<input>`. Work lines in a turn's input are labelled with their id, `t.i+n|`.

For the view: `rollup::branch(tree, tip)` cuts one branch alone, rendering only its items (`Rollup::branch` reuses the roll-up's renderings); view.rs takes its turns and chunks from it.
