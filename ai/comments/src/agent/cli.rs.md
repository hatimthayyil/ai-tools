# agent/cli.rs

Design: `ai/research/20261014T002322--chat-design.md`, Commands and Contract. Caller: `plugins/claude/hooks/register.ts` (register.ts.md).

Porcelain and plumbing
- Porcelain (`new`, `start`, `resume`, `list`, `view`, `attach`, `detach`, `zoom`, `grep`, `build`) is for users and agents: a failure is a sentence on stderr that says what to do, exit 1.
- Plumbing (`sync-session`, `compact-session`) is for harness glue: two-word names, hidden from help (`hide = true`). Not attached (no session, no repository, no attached binding): exit `NOT_ATTACHED` (3) and print nothing, so the plugin tells "not attached" from a failure without parsing text.

Agents
- `new <name>` is the only command that creates an agent: an empty `threads/<name>` directory (`Store::create`, under the thread's writer lock; an existing one is an error). Every other command names an agent through `Store::existing`, which refuses an unknown name with `Create it: ai agent new <name>`, so a typo fails instead of making a stray thread.

Sessions and threads
- Commands that read a session take `--harness` (default `claude`), `--session`, `--transcript`. Flags win: processes the plugin starts do not have `CLAUDE_CODE_SESSION_ID`. Without `--session`, the harness's environment names it (`claude::session_id`).
- `pick` is the one thread selection for `view`, `zoom`, `grep`, `build` and `ai view`: the name given (positional on the views, `-a` elsewhere, whose positional is an id or pattern), else the thread the session is attached to, else `choose`: the repository's only thread, else a picker when stdin and stderr are terminals, else an error listing the threads, newest first, with the command's usage. A terminal is the test because Claude Code's Bash tool gives neither: an agent or hook never meets a prompt it cannot answer. The picker (dialoguer `Select`, on stderr so stdout stays the output) lists `list`'s rows (`row`), newest first, the newest selected; Esc fails with `No agent chosen.`. `pick` returns the session's binding only when the session is attached to the picked thread, so `view` shows the session's branch there and the thread's newest branch elsewhere.
- `thread_view`, for `ai view` (view.rs.md): unnamed, an agent session reads only the thread it is attached to, and a repository with no threads (or none at all) gives no thread. `ai view` is how every agent starts: the repository's only thread, or an error, in a session that never attached would put a conversation it is not part of in its context, or stop its wake.
- Every command resolves names in the repository containing the current directory (`Store::find`, gix discover): two repositories each have their own `develop`.
- The transcript is looked up (`claude::transcript`) only by `attach`. Plumbing passes the given path, else the binding's: `attach` and `start` record it.

Launching
- `start <name> [-- args]`: first `ready` on the branch the new session will graft onto, so its seed has every line and a failure stops before anything is bound or launched; `resume` starting a new session does the same, while `claude --resume` keeps the session's own context and needs no view. Then a version-4 UUID (getrandom), bound to `name` with its future transcript `<config>/projects/<project_dir(dir)>/<uuid>.jsonl` (the file does not exist yet, so nothing is ingested; the graft is the thread's newest item), then `exec claude --session-id <uuid> [--append-system-prompt <instructions>] args…` in `dir`. The plugin seeds the new session with `compact-session` when it starts (register.ts.md, Seed).
- `dir` (`worktree`): the agent's `[agents.<name>] worktree`, else the current directory. Checked before `ready`, so a bad definition spends no summariser call. Missing: an error printing `git worktree add <path>` (`ai` makes no worktrees). Canonicalized, because Claude Code names the session's project directory from its real cwd, and a lexical `repo/../wt` would also make `Project::find` walk up into `repo`. It must be `Store::holds`: the session's hooks run there and find the store by the `ai.toml` id, so a worktree without the committed `ai.toml` would sync nowhere. `ai.local.toml` is not in a git worktree; hooks there read the worktree's settings.
- `instructions`: the files' text, user's, project's, then local, joined by a blank line, read at each `start` and `resume` (an edit applies at the next launch), passed as one `--append-system-prompt <text>`: Claude Code keeps its own system prompt and adds the agent's. The `-file` variant is listed in `claude --help` only under `--bare`, so the text is passed inline. A missing file fails before anything is bound. A launcher's own `--append-system-prompt` after `--` comes later on the line.
- `--harness`: `claude` only. It is there so the command line stays when other harnesses come; a session's harness is chosen at each start, not in `[agents]`.
- `resume <name> [-- args]`: the thread's newest Claude Code binding, by tip then attach time. `claude --resume` finds a session only from the directory it started in, so `resume` reads that directory from the transcript (`claude::session_dir`, the first entry's `cwd`) and runs claude there when it lies in this project (`Store::holds`: same project id, so any clone or worktree), from any subdirectory. Re-attached (catching up), then `exec claude --resume <id> [--append-system-prompt <instructions>] args…`: a system prompt is per launch, so a resumed session gets the instructions again. It runs where the session ran, not in `[agents] worktree`: Claude Code finds a session only from its own directory. Otherwise (transcript gone, no directory recorded, directory outside the project) one line on stderr says why, and it starts a new session in the current directory, with the same args. The args are the launcher's (model, permission mode, plugin dirs), so a resumed session runs as it was started. No guard against running inside a session: Claude Code refuses a nested launch itself.

Reading
- `list`: per thread its name, turns on the newest branch, UTC minute of the newest item and branch count when more than one; under it every session: harness, id, attached or detached, the time of its newest item (else of its attaching), newest first; the calling session is marked.
- `ready` writes the lines a view needs before anything uses it: read the branch it is given in the latest snapshot, build the lines its fold needs (`summarise::build`, within `WAIT`, waiting first for a running summariser, stopping at the first failure), read again. Any line still missing fails the command, naming each failed line with its error (`failures`, as `summarise` prints them), else how many lines are missing after `WAIT`, then `Write them, then try again: ai agent build -a <name>`. A view with a gap is never handed on: the request was for the view, so the error is the answer. The model is the configured one. Used by `compact-session` (the session's branch, `read_branch`) and `start` (the branch a new session grafts onto, `Snapshot::graft`).
- `view` never calls the model, whatever `chat.background` says: a command for looking writes nothing a user has not asked for. It renders the snapshot as it is (`view_in`); a turn without its line shows its message (view.rs.md, `render`). It syncs first when the calling session is attached to the thread it shows (the plumbing's sync, without starting a summariser); outside a session it reads without a sync.
- `view`: the picked thread's view, printed by `page::print` (page.rs.md): whole on a terminal (`run`'s `terminal`, set by `exec` from stdout), else in parts of `page::PART`. Every part comes from one state of the thread (store.rs `Mark`): the footer names it and the thread (`<name> --part <n> --at <state>`), because the background summariser writes lines between parts and a fresh fold would shift the page boundaries. A thread with no item yet prints that it holds nothing.
- `thread_view` (for `ai view`): `pick`'s thread's view with the thread's name and `Mark`, the session synced first; unnamed, an agent session reads only its attached thread. Given a `Mark` from an earlier part, that state unsynced, read with the calling session's binding as it stood then.
- `zoom <id> [--tool-output]`: `Branch::zoom` on the picked thread's branch (the session's when it is attached there, else the newest: `read_branch`), printed by `page::print`: whole on a terminal, else in parts pinned like the view's (`Parts`: hidden `--part`/`--at`, the state read unsynced), since a turn still open grows between parts. The footer names the thread and repeats `--tool-output`, so it works outside the session too.
- `grep [-a <name>]… <regex> [-F -i -s] [--tool-output]`: `Branch::grep` on each picked thread's branch, as zoom picks it, with memory's pattern flags (`memory::Pattern`). `-a` repeats (`Targets`), each name once, every one checked by `pick`, so an unknown agent fails the whole search; none means `pick`'s one thread. Matches go thread by thread in the order named, oldest first within each; with several threads each line leads with its agent's name and a space (`dev 12.3|…`), so a hit still zooms as `ai agent zoom -a dev 12.3`. Whole on a terminal; else `page::search`'s parts, newest first, each printed oldest first, its footer naming `ai agent grep -a <name>… '<pattern>' … --part <k> --at <state>,…` with the flags repeated (`memory::quote`, `memory::word`): `--at` holds one state per thread, comma-separated in the `-a` order, since each thread has its own.
- `attach`/`detach`: one-line confirmations. Attaching elsewhere is rejected until the session is explicitly detached.

Summarising
- `build`: `summarise::summarise` with `--model`, else the configured model (`Store::backend`), stopping at the first failure (`OnFail::Stop`). Prints `Wrote N lines, M by the model.` or `Nothing to write.`, or that another summariser holds the lock (it writes the same lines). Spawned by `sync-session` as `build -a <name> --background` (`OnFail::Continue`; the flag is hidden and takes no id, `--rebuild` or `--dry-run`): stdout null, stderr the log.
- `--rebuild`: `summarise::rebuild`, waiting up to `WAIT` for a running summariser; prints `Dropped N lines; wrote M, K by the model.`
- `<id>`: one line, its key from the picked branch (`Branch::line_key`: a closed turn, an aligned node over closed turns, or a chunk that no longer grows; anything else is a sentence naming the three). Alone: `summarise::build` of that line and the unbuilt lines under it, or `<id> is written already. Rewrite it with --rebuild.` With `--rebuild`: `summarise::rewrite`, then `Dropped N lines; wrote M, K by the model.` and, when lines above it went, that the next summarise writes them again.
- `--dry-run` (with or without `--rebuild`): `summarise::dry_run`; prints each line as the view would (`8+4|text`, `12.3+7|text`: `Id::line` from the places of its first and last items), the line it replaces indented under it as `was:`, then the totals. Stores nothing; still calls the model.
- Failed lines follow the totals (`Failed <key>: <why>`); exit 1 if any failed.

Plumbing
- `sync-session` (and `attach`): no output; when items were added, `Store::spawn_summariser` starts the background summariser, unless `ai.toml` sets `chat.background` false (summarise.rs.md; the only switch).
- `compact-session`: sync, then `ready` on the session's branch (the fold's unbuilt lines built within `WAIT`, 60 s, waiting first for a running summariser: summarise.rs.md, `build`), the view on stdout, whole (the plugin sends it as one message). Also the seed of a launched session: its tip is its graft, so the view ends where the session starts, its last turn headed as the previous session's. A session whose branch has no item (the launcher's, on a new thread) prints nothing. A line it cannot write fails it with no view on stdout, as any other error (no `claude` on `PATH`, a store error): exit 1, the reason on stderr.
