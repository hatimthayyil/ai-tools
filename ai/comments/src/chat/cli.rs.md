# chat/cli.rs

- CLI preflight scans every thread's format before dispatch. Newer formats fail before confirmation or writes. Normal terminal commands ask once before importing the repository's v1 threads, then run the requested command; confirmation and import status use stderr.
- `Cli::run` is noninteractive. It and background plumbing refuse v1 without waiting or converting. Library store APIs have no prompt behavior. Decline, blank input and EOF leave the old refs unchanged.
- Terminal confirmation requires the process group to own stdin's foreground terminal group (`tcgetpgrp`/`getpgrp`). A background job can inherit TTY descriptors; TTY detection alone would let its input read suspend it with `SIGTTIN`. A failed foreground-group query refuses confirmation.

Design: `ai/research/20261014T002322---chat-design.md`, Commands and Contract. Caller: `plugins/claude/hooks/register.ts` (register.ts.md).

Porcelain and plumbing
- Porcelain (`start`, `resume`, `list`, `view`, `attach`, `detach`, `zoom`, `grep`, `summarise`) is for users and agents: a failure is a sentence on stderr that says what to do, exit 1.
- Plumbing (`sync-session`, `compact-session`) is for harness glue: two-word names, hidden from help (`hide = true`). Not attached (no session, no repository, no attached binding): exit `NOT_ATTACHED` (3) and print nothing, so the plugin tells "not attached" from a failure without parsing text.

Sessions and threads
- Commands that read a session take `--harness` (default `claude`), `--session`, `--transcript`. Flags win: processes the plugin starts do not have `CLAUDE_CODE_SESSION_ID`. Without `--session`, the harness's environment names it (`claude::session_id`).
- `pick` is the one thread selection for `view`, `zoom`, `grep` and `summarise`: `-t <name>`, else the thread the session is attached to. It returns the session's binding only when the session is attached to the picked thread, so `view` shows the session's branch there and the thread's newest branch elsewhere.
- Every command resolves names in the repository containing the current directory (`Chat::find`, gix discover): two repositories each have their own `develop`.
- The transcript is looked up (`claude::transcript`) only by `attach`. Plumbing passes the given path, else the binding's: `attach` and `start` record it.

Launching
- `start <name> [-- args]`: a version-4 UUID (getrandom), bound to `name` with its future transcript `<config>/projects/<project_dir(cwd)>/<uuid>.jsonl` (the file does not exist yet, so nothing is ingested; the graft is the thread's newest item), then `exec claude --session-id <uuid> args…`. The plugin seeds the new session with `compact-session` when it starts (register.ts.md, Seed).
- `resume <name> [-- args]`: the thread's newest Claude Code binding, by tip then attach time. `claude --resume` finds a session only from the directory it started in, so `resume` reads that directory from the transcript (`claude::session_dir`, the first entry's `cwd`) and runs claude there when it lies in this repository (`Chat::holds`: same common git dir), from any subdirectory. Re-attached (catching up), then `exec claude --resume <id> args…`. Otherwise (transcript gone, no directory recorded, directory outside the repository) one line on stderr says why, and it starts a new session in the current directory, with the same args. The args are the launcher's (model, permission mode, plugin dirs), so a resumed session runs as it was started. No guard against running inside a session: Claude Code refuses a nested launch itself.

Reading
- `list`: per thread its name, turns on the newest branch, UTC minute of the newest item and branch count when more than one; under it every session: harness, id, attached or detached, the time of its newest item (else of its attaching), newest first; the calling session is marked.
- `fresh_view` is the one way a view is made fresh, for `view` and `compact-session`: read the branch `read_branch` picks (a session's through `Branch::session`, so a seed heads its last turn as the previous session's; else the thread's newest), build the lines its fold needs (`summarise::build`, within `WAIT`, waiting first for a running summariser), read again, render; with the commit read. `view` syncs first when the calling session is attached to the thread it shows (the plumbing's sync, without starting a summariser: the lines it needs it writes itself); outside a session it writes the lines without a sync. The model is the configured one.
- `view`: the picked thread's view, paged by `PART` (20,000 bytes, under the 30,000-character cap on a Claude Code command's output) with memory's `page`. Every part comes from one commit of the thread: the footer names it and the thread (`-t <name> --part <n> --at <commit>`), because the background summariser writes lines between parts and a fresh fold would shift the page boundaries. A thread with no item yet prints that it holds nothing.
- `zoom <id> [part] [--tool-output]`: `Branch::zoom` on the picked thread's branch (the session's when it is attached there, else the newest: `read_branch`), paged by part number, not pinned: what it shows is mostly items, which never change. The footer names the thread and repeats `--tool-output`, so it works outside the session too.
- `grep <regex> [-F -i -s] [--tool-output] [--before <id>]`: `Branch::grep` on the picked thread's branch, as zoom picks it, with memory's pattern flags (`memory::Pattern`). Pages newest first: the newest matches that fit `PART`, printed oldest first, then `Newest k of n. Older: ai chat grep -t <name> '<pattern>' … --before <id>` with the flags repeated (`memory::quote`, `memory::word`); else `n matches.`.
- `attach`/`detach`: one-line confirmations. `attach` reports a new thread; attaching elsewhere is rejected until the session is explicitly detached.

Summarising
- `summarise`: `summarise::summarise` with `--model`, else the configured model (`Chat::backend`). Prints `Wrote N lines, M by the model.` or `Nothing to write.`, or that another summariser holds the lock (it writes the same lines). Spawned by `sync-session` as `summarise -t <name>`: stdout null, stderr the log.
- `--rebuild`: `summarise::rebuild`, waiting up to `WAIT` for a running summariser; prints `Dropped N lines; wrote M, K by the model.`
- `<id>`: one line, its key from the picked branch (`Branch::line_key`: a closed turn, an aligned node over closed turns, or a chunk that no longer grows; anything else is a sentence naming the three). Alone: `summarise::build` of that line and the unbuilt lines under it, or `<id> is written already. Rewrite it with --rebuild.` With `--rebuild`: `summarise::rewrite`, then `Dropped N lines; wrote M, K by the model.` and, when lines above it went, that the next summarise writes them again.
- `--dry-run` (with or without `--rebuild`): `summarise::dry_run`; prints each line as the view would (`8+4|text`, `12.3+7|text`: `Id::line` from the places of its first and last items), the line it replaces indented under it as `was:`, then the totals. Stores nothing; still calls the model.
- Failed lines follow the totals (`Failed <key>: <why>`); exit 1 if any failed.

Plumbing
- `sync-session` (and `attach`): no output; when items were added, `Chat::spawn_summariser` starts the background summariser, unless the git config `ai.chat.summarise` is false (summarise.rs.md; the only switch).
- `compact-session`: sync, then `fresh_view` of the session's branch (the fold's unbuilt lines built within `WAIT`, 60 s, waiting first for a running summariser: summarise.rs.md, `build`), the view on stdout, whole (the plugin sends it as one message). Also the seed of a launched session: its tip is its graft, so the view ends where the session starts, its last turn headed as the previous session's. A session whose branch has no item (the launcher's, on a new thread) prints nothing: the plugin then seeds nothing, or compacts natively. Lines that fail stay placeholders (the thread's log has why). An error (no `claude` on `PATH`, a store error) fails the command, so the plugin compacts natively and shows the reason.
