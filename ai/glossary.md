# Glossary

- `memory`: the store `ai memory` manages; one per user per machine, shared by every repo and session, append-only. A bare git repo at `~/.ai/memory` (override `AI_MEMORY_DIR`); all data lives as objects under `refs/ai/memory`, one commit per mutation.
- `message`: one entry of the log, with a `kind`; its blob is `log/<hi>/<lo>`: `key value` header lines (`ts kind origin repo root head branch agent model session`, empty ones left out), a blank line, then the text. Ids are positions `0, 1, …`, permanent.
- `kind`: `user` (the user's words), `talk` (the agent's replies), `tool` (its tool calls), `echo` (tool results), `note` (`ai memory note`, `import`).
- `node`: one summary line of the tree, ≤ ~512 characters (`NODE`). `(l, i)` covers messages `[i·2^l, (i+1)·2^l)`; level 0 summarizes one message, level `l` merges its two children. Stored one per line in `trees/<n>/<l>/<hi>/<lo>` segments of 256, under a column row (`ts origin agent model session stale text`); `stale` is `1` while the text awaits a rebuild. `state` names the current tree, the one being built and the last number given.
- `id+n`: how a node is named: first message `id`, `n = 2^l` messages. One message is a bare `id`; `zoom` and `show` take either.
- `free node`: a source that fits `NODE` is its own node, no model call: a short message (`kind: text`), or two lines joined. Built in the same commit that completes its sources.
- `view`: the nodes tiling `[0, T)`, oldest first, under `VIEW` = 128,000 bytes; grows by appending and merging the most due pair, never splits; folded again from message 0 at load. `ai memory view` prints it.
- `placeholder`: `(not summarized yet: zoom it)`, the view line of a message whose level-0 node is not built.
- `compactor`: builds nodes with a model, in rule-3 order (messages one at a time, merges alongside), `JOBS` = 8 at once, size retries, fixed 10 s retry. One per memory (`compact.lock`). Runs as `ai memory build`.
- `rule 3`: a node is built only when every view line before its end is already a summary, so the compactor never sees a placeholder.
- `build` (memory): `ai memory build`: run the compactor on the tree being built, else the current tree, until nothing is buildable, then exit. `note` starts one in the background when a node is due. A run that gives up leaves the rest for the next `build`. `--dry-run` prints the plan alone. Its output is a `progress` display.
- `tree` (memory): `ai memory tree`, the trees of the memory by number: `current` is what `view`, `zoom` and `grep` read; `rebuild [a..b | id+n]` starts or extends the tree being built, a copy of the current one, marking stale the summaries above the named notes (none named: every note); `reroll <id+n>` marks one summary and those above it; `use N` makes tree N current, stale or not, without building it or copying it; a tree being built is left as it is; `drop N` drops a tree, or cancels the one being built; `diff A B` lists summaries that differ. Stale summaries keep their text until `build` rewrites them. Notes are never rebuilt.
- `progress`: what a summariser run shows (`progress::Progress`, shared by `ai memory build` and `ai agent build`): the plan (per level its lines, written, to write; an upper bound on model calls; cost and time at the average of the log's last 200 `built` events), then on a terminal one bar per level and a total on stderr with event lines (`built`, `joined`, `retry`, `failed`, `gave up`) above them, or off one each event as a plain line counted `[n/total]`, then the end (built, by the model, joined, dropped; calls, retries, cost, tokens; the log). The background summariser shows nothing.
- `backend`: the summariser's model access (`Backend`/`Conversation`), set by `[summariser] backend`: `claude`, Claude Code's `claude -p` (default Sonnet, medium effort); `api`, a provider's API through genai (`memory::Api`), `model` being `<provider>/<model>`, the key from the provider's environment variable. `[summariser] effort` sets how hard the model thinks (`claude --effort`, or genai's reasoning effort; unset, medium for claude and the provider's default for api), `[summariser] jobs` how many calls a build runs at once (`Backend::jobs`, default 8). Both keep each call in the store's `calls/`, with its thinking tokens.
- `ai memory view`: print the view under date headers: whole on a terminal, else in parts.
- `part`: one page of a view's output when it is not on a terminal: at most `PART` (20,000) bytes, headed by its command and `part k of n`, ending with `Next: ai page <view>:<part>` while parts remain.
- `saved view`: every part of one paged output, saved by its first read as `<n>.json` in `$XDG_CACHE_HOME/ai/views/` and printed part by part by `ai page <n>:<part>`; numbered with the lowest free number, gone 10 minutes after it was last read.
- `zoom`: open `id+n` two levels down; a bare `id` gives the original message in bounded pages (`part`, from 1).
- `origin`: a store's random id (6 Crockford base-32 characters), made at `init` and kept in the store's `origin` file; stamped on every message and node the store writes.
- `show`: every field of one message or node.
- `grep`: rg-style regex search over every message's text (smart-case, `-F`, filters `--since`, `--kind`, `--origin`, `--agent`, `--session`, `--repo`; `-t` adds nodes); off a terminal, in parts newest first.
- `snapshot`: the memory as of one commit; every command reads one.
- `knob`: a memory size set under `[memory]` in `ai.toml`, shown by `ai memory config`: `view.lines`, `entry-chars`.
- `ai.toml`: `ai`'s settings, one table per tool (`[chat]`, `[agent]`, `[memory]`, `[summariser]`, and in the user's alone `[backup]`): the user's in `~/.ai`; the project's, the nearest one at or above the cwd (never the user's); and the project's private one, `ai.toml` in its folder of `~/ai`, linked from `ai.local.toml`; each later one's keys win. A project's also holds `[project]`: its `id` and `name`.
- `witness`: `[summariser.witness]`, a second model that checks every summary the summariser writes, for memory, agent threads and notes (`memory::Witnessed`, prompt `src/memory/prompts/witness.txt`). It reads the request, which holds the sources, and the summary, and reports unsupported claims, contradictions, changed meaning, and a dropped "not", "never" or user rule, never what was left out for length. The summariser rewrites the summary, held to its limit again, or contests a finding after a `Contested:` line; the witness checks again with the whole exchange, until it replies `OK`, with no limit on rounds (`memory::settle`). The log has each round: `witness found faults`, `summariser answered`, `witnessed`.
- `provenance`: origin of a data item: who/what produced it, when, from which session, model and commit.
- `attribution`: authorship of work (code, files) as AI-generated, AI-assisted or human.
- `format`: the store's format number, the `format` blob at the tree root (absent: 1). This ai reads and writes only its own (`FORMAT`); it refuses a newer store and upgrades an older one.
- `upgrade`: the pure, automatic rewrite of an older-format store to `FORMAT`, one commit `upgrade format N -> M` on the old head under the compactor's lock; the old head is the rollback.
- `project`: the directory of the nearest `ai.toml` at or above the cwd, never the user's; its id, a TypeID `project_<UUIDv7>`, is minted once by `ai init`. Its agents and private settings live in its folder of `~/ai`, and a note records its id.
- `~/ai`: the user's git repository, which they keep like their dotfiles: each project's folder `projects/<project>/` (its `id`, its private settings `ai.toml`, its agents' threads in `agents/`). `ai` commits a project's folder on events, touching no other path. What a new machine needs.
- `project folder`: `~/ai/projects/<name>/`, found by the project id in its `id` file, so every checkout and clone of the project finds the same one; a name another id holds is refused.
- `~/.ai`: what belongs to this machine and never goes in git: the user's settings, memory, the threads' locks and compactor logs (`agents/<project id>/`), the backup's repository (`backup/`), key (`backup.key`), staged copies (`backup-staging/`), lock and last run (`backup.json`).
- `old store`: `.ai/local/` in a project's home, where an older ai kept its agents (format 4) and private settings. Refused until moved; on a terminal `ai agent`, `ai resume` and `ai init` offer the move (`agent::convert`), which archives it whole in `~/.ai/archive/`.
- `notes`: the store `ai notes` manages: a global knowledge base agents consult deliberately, never loaded at session start. A non-bare repo of Markdown files at `~/.ai/notes` (override `AI_NOTES_DIR`), one commit per change.
- `topic`: a directory of the notes, named by its slug path with dots (`linguistics.syntax`); repo knowledge goes under `projects.<repo>`.
- `leaf`: one note of the notes: one claim, titled (`# <title>`, ≤ 80 characters, the claim in a few words), body ≤ 1024 characters, file `<id>--<slug of title>.md`; the id is its UTC Denote timestamp, permanent. Frontmatter: `source`, `confidence` (`verified | reported | speculative | assessment`), `checked`, `decay`, `links`, `supersedes`, `invalid_at`.
- `scope`, `gist`: the two parts of a topic's `_summary.md`: one line on what lies below, and its key claims. Written by the compactor model from the topic's children; out of date when the hash of that input changes.
- `breadcrumb`: a topic path as `ai notes grep` prints it: `physics › qm › decoherence`.
- `item`: one normalised harness entry in `ai agent` (`agent::Item`): a user message, work, assistant text, tool call, tool output or marker, with its source id (harness, session, entry), parent and time. Thinking is dropped.
- `marker`: an item that is a harness event, not content: a compaction point, the harness's own summary, an interrupt.
- `branch`: the items from a root of the item tree to one tip. Rewinds, edits and two sessions on one thread add branches; nothing is removed.
- `step`: an assistant text, if any, and the tool calls and results after it, up to the next assistant text.
- `turn`: a user message or work item and the steps that answer it, up to the next one on the branch; closed once one follows. Codex uses the word the same way (thread, turn, item). Stored line records keep the kind name `exchange`.
- `human prompt`: a user entry that opens a turn: one the user typed or sent (mid-run included) or a subagent's task. Tool results, hook context, `isMeta` entries, local commands and their output, task notifications are not.
- `work`: an item that is a message from another agent, with its sender: a subagent's hand-back, a fork's report (from its description), a peer's report, a coordinator's instruction. It opens a turn (OptChat's name).
- `agent`: a name in a project with one thread, created only by `ai agent new`; `ai agent rename` gives it another name, its thread and attached sessions with it. Every thread is an agent's.
- `address`: an agent's `<project>.<agent>`, the name of its project's folder in `~/ai`, a dot, then its name; it splits at the last dot, since an agent's name holds none (`Store::address`). The name of its Claude Code sessions, by which other sessions send it messages; at most 200 characters (`claude::session_name`).
- `reports-to`: an `[agents.<name>]` key, the agents it reports to (its superiors), each with a table of its own. Several make the hierarchy a graph; `Settings::hierarchy` refuses a self-report, an unknown name and a cycle, failing only the commands that read the hierarchy. The agents below an agent, through any number of levels (`Hierarchy::below`), are the threads it may read besides its own.
- `thread`: an agent's history: a directory `threads/<name>` of the project's agent store, `agents/` in its folder of `~/ai`, so every checkout shares it. Holds items, session tracks, attachment changes, subagents, lines and source records as append-only JSON Lines files; its locks and log are this machine's, in `~/.ai`; format 6.
- `source record`: a line of a thread's `sources.jsonl` (`record::Pointer`): what the thread read of one file of a session, by harness, session, the machine (`host`, `backup::host`), the file's real path there (`path`), the length and SHA-256 of the bytes from its start (`len`, `sha256`), and when they were read (`at`). A record whose `from` is 0 begins a `version` (`agent::Version`); the file's later ones say it grew, each going on from the length the one before told of. In place of a copy: the file holds the bytes while it begins with them, then the machine's backup does (`read back`).
- `version state`: where a version's bytes are (`backup::threads::State`), as `ai backup threads` tells: `held`, a repository holds them; `pending`, the file holds them and this machine's newest snapshot not yet; `bare`, the file holds them and no local repository is made; `away`, read on another machine and in no repository here; `lost`, in neither the file nor a repository, which fails the check. `ai agent list` tells only, by size, how many of a session's files are gone or shorter than what was read.
- `read back`: finding again the bytes a source record tells of (`backup::read`): in the file, if it still begins with them; else in the local repository, then the remote one, in a snapshot of the record's machine whose file at the path begins with them (`restic find`, then `restic dump`): the last one made before the record's `at`, the first after it, a few later ones and the newest, never every snapshot. A database is looked for at its staged copy's path too. `ai agent resume` reads a session's files that are gone back into place (`agent::restore`).
- `segmented file`: how agent store format 4 kept a growing file: a directory of its own name holding `000000.<ext>`, `000001.<ext>`, …, each segment cut at a line's end. Joined in order, the segments are the file, byte for byte; a move to `~/ai` writes each as that one file (`agent::convert`).
- `loose object`: a git object kept whole as a file of its own under `.git/objects/`, as gix writes every object. `git gc` packs them, each version of a file stored against the one before; a commit to `~/ai` starts it once the loose objects written since the last one pass `[agent] gc-after-mib` (`repo::gc`).
- `sequence number`: an item's position in its thread, from 0, permanent. Parents and line keys are sequence numbers. A subagent's items are numbered apart, beside the main tree.
- `binding`: a harness session's record in a thread (`sessions/<harness>/<session>`): transcript (recorded from its harness home), graft, tip, attach and detach times, from the thread's `attachments.jsonl`. Attached until detached; a session is attached to at most one thread of a project.
- `graft`: the item a session's roots hang on: the thread's newest item when the session was first attached; none on a new thread.
- `tip` (of a session): the item of its transcript's newest entry, the end of its branch.
- `line` (chat): a summary in a thread, keyed by its level and the last item it covers (`level@last`), of kind chunk (a work line), turn or node; written once.
- `sync` (chat): ingest an attached session's new entries into its thread, writing nothing if nothing is new; an unattached session is reported as such.
- `view` (chat): what `ai agent compact-session` and `ai agent view` print for a session: an instruction, then one list of every turn of its branch once, oldest first: the fold, the recent turns (`[agent.view] recent`, default 3), the newest turns (`latest`, default 1), in `total` entries (default 64). Computed fresh each time; nothing about it is stored.
- `level` (chat view): how much of a turn the view shows, least first: oldest (in a merged line), older (its turn line), recent, newest. Never decreases toward the present.
- `recent turns`: the `[agent.view] recent` turns before the newest: message and final reply word for word, work lines between.
- `newest turns`: a branch's last `[agent.view] latest` turns, the last closed or open: the view lists their every item as `ai agent zoom` does, under each turn's number, and builds no line for them.
- `fold` (chat): the turns of a session's branch before the recent ones, in lines, oldest coarsest: from one line per turn, the most due aligned pair merges first, due = (T − last)/2^l, until at most `total − latest − recent` are left, never merging the newest `[agent.view] single` turns. An unbuilt line shows what is built under it, else a placeholder.
- `id` (chat): how a line or item prints, on a branch: `12` turn 12, `8+4` turns 8 to 11 (a node when aligned), `12.3` item 3 of turn 12 (item 0 opens it), `12.3+7` items 3 to 9 of turn 12 (a work line, or a chunk of the work). Turns count from 0 along the branch; past a fork, the same id names a different turn on each branch. What `ai agent zoom` takes. Store keys stay `level@last`.
- `place` (chat): an item's turn and number in it, from its branch (`model::Place`); fixed by the path from the root, so the same on every branch through the item.
- `open turn`: a branch's last turn, not yet closed: no message follows it and the harness has not ended it.
- `placeholder` (chat): `8+4|(not summarised yet)`, a line the roll-up has not built.
- `launcher`: `ai agent resume <name> [-- args]` when the thread has no session to continue: a new session id bound to the thread with its future transcript, then `exec claude --session-id <id> --name=<address>`.
- `seed` (chat): the view a launched session of an existing thread starts with, its only context: the plugin's `SessionStart` (`startup`) context, from `ai agent compact-session`. Kept in the transcript, so a resume replays it; a compaction replaces it.
- `roll-up`: a thread's lines and what each is made from (`agent::Rollup`), over every branch: work lines (level 0), turn lines of closed turns from their message, work lines and final reply (1), binary nodes over aligned pairs of closed turns along the branch (1+k). Built by the chat compactor.
- `final reply`: the item that ends a turn when it is the assistant's text (Claude Code's `end_turn`), the reply that tells the user what came of the work. A turn cut short by a message or an interrupt has none.
- `work` (of a turn): its steps between its message and its final reply; all its steps when it has no final reply. Summarised in its own work line, `t.1+n`. Not the `work` item kind.
- `chunk`: consecutive steps of a turn's work, at most `INPUT` (48 KB), cut greedily at step boundaries (an over-budget step before its tool calls); final once another chunk follows it. Work that fits is one chunk, its work line. Its call reads the turn's message as context.
- `free line` (chat): a line whose input fits its limit (512 characters per 50 words asked) is that input without item ids, flattened, with no model call.
- `grep` (chat): `ai agent grep <regex>`: matches on a thread's branch in items' words and tool calls, tool output with `--tool-output`, and built lines; off a terminal, in parts newest first.
- `build` (chat): `ai agent build -a <name>`: the thread's summariser, one per thread (its lock), building every ready line until none is; `sync-session` starts it in the background unless `ai.toml` sets `chat.background` false. `--rebuild` drops every line and writes them again; `<id>` writes one line, and with `--rebuild` rewrites it and drops the lines above it for the next run; `--dry-run` prints the plan alone, calling no model and storing nothing; `--preview` has the model write each line and prints it beside the line it replaces, storing nothing; `--model` picks the model for the run. Its output is a `progress` display, levels being its tiers: work (L0), turns (L1), then nodes of 2, 4, … turns.
- `porcelain`: a command for users and agents (git's term): listed in help, errors worded as what to do.
- `plumbing`: a command for harness glue, at least two words, hidden from help: `ai agent sync-session`, `ai agent compact-session`, `ai agent end-session`, `ai memory prompt-hook`.
- `harness files`: a harness's own folders and files of transcripts and session data (`backup::harness::HARNESSES`), under its default folder in `$HOME`: what `ai backup` backs up, with the folders `[backup] folders` names.
- `backup`: `ai backup`: every harness's transcripts in restic repositories, restic run as a program (`backup::restic`), never forgetting or pruning. A `run` backs up each harness's folders (`backup::harness::HARNESSES`, under its default folder) and those `[backup] folders` names, each where it really sits, as one snapshot of this machine, under its host name (`backup::host`), in the local repository, `~/.ai/backup`; none when restic's dry run finds no file new or changed. One run at a time (`~/.ai/backup.lock`), a second waiting; a run that met a problem fails after doing all it could. `watch`, the service `ai-tools-backup`, runs every `[backup] every`; a session's end starts a run once the repository is made, unless `on-session-end = false`. `check` is `restic check`; `threads` tells each `version state`.
- `[backup]`: the backup's settings (`backup::Config`), read from the user's own `~/.ai/ai.toml` alone, since its keys name where backups go and commands that print passwords; a project's file that holds the table is refused whole. Keys: `repository`, `password-command`, `every`, `on-session-end`, `folders`, and `[backup.remote]`. A command that prints a password or the remote's variables is run by `sh -c` and stopped after 60 seconds (`backup::command`).
- `backup key`: `~/.ai/backup.key`, the local repository's password while no `[backup] password-command` names another: 32 random bytes in hex, mode 600, made with the repository. A run never makes a second key for a repository that exists.
- `staged copy`: a harness database copied with SQLite's backup API to its own path under `~/.ai/backup-staging/` (`backup::db`), what a run backs up in place of the file its harness is writing; left untouched while the database doesn't change.
- `remote` (backup): `[backup.remote]`, a second restic repository, named as restic names it, that gets a copy of every snapshot the local one holds (`restic copy`) at the end of a run that made one or whose last copy failed; made at the first copy with the local repository's chunker parameters. A copied snapshot has an id of its own, the local snapshot's id as its `original`, and the same `tree`. Its `password-command` is required; `env-command` prints the variables restic reaches it with.
- `last run` (backup): `~/.ai/backup.json` (`backup::State`): when the last run ended, when the last without a problem did, the last run's problem, the newest snapshot a run made, and the last copy to the remote that went through. `ai backup status` prints it and fails while the last run failed.
