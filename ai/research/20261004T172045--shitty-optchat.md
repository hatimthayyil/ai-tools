# shitty-optchat: lessons for `ai chat`

Research for `ai chat`. No code changed. Date: 2026-10-04.

Source: https://github.com/gebeer/shitty-optchat at `955394f` (Bun + TypeScript, Claude Code 2.1.289, all measurements 2026-10-04). Paths below are relative to that repo; `§N` = its `SPEC.md`, "gist §N" = the OptChat spec (`/hatimthayyil/code/optchat/optchat.md`). Cache mechanics and priming are in `20261004T171431--optchat-cache-claude-code.md` and are not repeated here. **[inf]** marks my inference, not something the repo states.

## Summary

- A complete, working OptChat on `claude -p`: ~1,100 lines of TS, 17 tests, built in 6 gated steps with probes before each design choice (§12, §16.1). README status: early, single user, "memory merges are not yet tested on real data".
- The engine is one fresh `claude -p` per turn, killed at its first `result`; zoom/date come from a stdio MCP server the harness ships as a subcommand; the compactor is one `claude -p` (sonnet, no tools) per node, 8 in parallel.
- Everything Claude Code-specific worth knowing is measured: isolation flags, permissions, mid-run messages, tool-output truncation, thinking, kill semantics. These transfer to Rust unchanged.
- The pi/Codex proposal (`docs/pi-codex-proposal.md`) was **rejected** (commit `955394f` message): Codex OAuth refuses explicit cache breakpoints and its implicit cache reads only byte-identical prefixes, so cross-turn view caching fails there.
- The big mismatch with `ai memory`: OptChat assumes one writer, permanent dense ids, and variable-size messages up to 30k+ chars. Our store is multi-writer CAS, renumbers on sync, and holds 512 B records with ≤305 B text. Recommendations in §7 below.

Data dir `~/.optchat`: `chat/{main,tree}/YYYY-MM-DD.jsonl`, `lock` socket, `instructions.md` (the user's AGENTS.md equivalent), `usage.jsonl`; its own git repo (§1).

### A turn (`turn.ts` `createSession`, §5.2)

1. `input(text)`: if a call runs, write it to the child's stdin as a stream-json user message and record it in `sent`; else queue it and start the loop.
2. Loop while queue non-empty: `settle(signal)` (wait until every view part is built; prints `waiting for N summaries…`), `render` the view **before** logging the new messages, `await prime(view)` (raced against cancel), then log each queued text as `user`.
3. Spawn the master, send one user message: `cutBlocks(view)` (≤4 unmarked text blocks) + `join(texts, "\n\n")`.
4. Map events to log entries in stream order (§5.3): `assistant` text → `talk`; `tool_use` → `tool` as `name + JSON(input)`; `user` `tool_result` → `echo` (`cap()`ped, non-text parts as `[type]`); replay events after the first → `user` for the matching `sent` entry; thinking → never logged. Each `log()` fsyncs and calls `pump()`.
5. At the **first `result`**: kill the child, push untaken `sent` back to the queue front (only if a `result` arrived; after a cancel or crash they are logged as unanswered `user`, to avoid a requeue loop).
6. On loop end: `onIdle` → git commit of the data dir; restart the 1 s idle-priming timer.

### Compactor (`compactor.ts`, `summarize.ts`, §3, §7)

- `pump()` runs after every log and every commit: `buildFree` first (free nodes written to `chat/tree` like any node, no JOBS slot), then one O(T) scan starting every node that is built-able, not busy, and whose end ≤ `first()` (gist §4.1 rule 3), up to JOBS.
- A job's context snapshot is taken synchronously when the pump decides, so it sees exactly the state rule 3 checked; `context()` throws on an unbuilt line ("a rule-3 bug must be loud").
- Commit = append to `chat/tree` (fsync), `setNode`, `fit()`, wake waiters.

### View fold (`view.ts`)

- Size = sum of node text bytes (no `id+n|` prefix). Ties in `due` go leftmost. `fit` never splits; when no pair has a built parent it waits.
- `refold` at load uses `T = i+1` per step against the **final** tree, so it equals the live fold only when the compactor kept up (§3 as built). **[inf]** After any restart with a lagging compactor, the view differs from what was last primed: one cache rewrite, harmless.
- `render`: `<chat>\n` + `id+n|text` lines (newlines → spaces) + `\n</chat>`. `cutBlocks` cuts after the last `\n` before each mark, skipping marks past the end.

### zoom/date (`mcp.ts`, §9)

- `optchat mcp` subcommand, launched by Claude Code via `--mcp-config` as inline JSON `{"mcpServers":{"optchat":{"command":<bun>,"args":[cli.ts,"mcp"],"env":{"OPTCHAT_DIR":dir}}}}`, built once per process.
- Read-only, no lock; reloads both JSONL streams on every call (`ponytail:` comment: cache by mtime if slow).
- `zoom(id,n)`: validate integers, power of 2, `id % n == 0`, `id+n ≤ T`; `n=1` returns `id+0|kind: text` whole with newlines; otherwise the two children; unbuilt → `No line id+n.`. `zoom(id,1)` works for any existing message (the placeholder tells the model to zoom it). `date(id)` → local `YYYY-MM-DD HH:MM` or `No message N.`
- Verbatim gist tool descriptions; protocol: `initialize`, `ping`, `tools/list`, `tools/call`, `-32601` otherwise.
- The turn checks `system/init.mcp_servers` for `optchat: connected` and warns otherwise (§13).

### Persistence and locking

- Every message/node: one `write` + `fsync` per JSONL line; new day file → fsync the directory (`store.ts` `write`).
- Load: skip/report invalid lines; the lock holder appends a missing final `\n`; readers (`view`, `browse`, `mcp`) never write and stay quiet about an unterminated last line (can't tell torn from in-progress).
- Lock: listen on `<dir>/lock` (unix socket, `unref`'d). Live owner → exit 1; refused connect → stale, unlink and take over. Accepted race: two simultaneous takeovers can both win (`store.ts:94`). Socket path limit ~107 chars.
- Git: after each turn loop and at exit, `git init` if needed, `.gitignore` with `lock`, `add -A`, commit only if staged, fixed identity, `commit.gpgsign=false`, serialized; errors printed once, never fail a turn (`persist.ts`).

### Exact `claude -p` invocations

Shared (`claude.ts` `baseArgs`):

```
claude -p --model M --effort E
  --input-format stream-json --output-format stream-json --verbose --include-partial-messages
  --no-session-persistence --setting-sources "" --strict-mcp-config
  --system-prompt-file F --tools T
env: inherited process.env + CLAUDE_CODE_PROMPT_CACHE_TTL=5m
```

| call | model / effort | tools | extra flags | extra env | message |
|---|---|---|---|---|---|
| master | `opus` / `high` | `Bash,Read,Edit,Write,Glob,Grep,WebFetch,WebSearch` (+2 MCP) | `--mcp-config <json> --permission-mode bypassPermissions --replay-user-messages` | — | view blocks unmarked + new text |
| priming | identical argv (`masterArgs()` shared) | same | same | `DISABLE_PROMPT_CACHING=1` | view blocks each marked + `"ok"`; killed at `message_start` |
| compactor | `sonnet` / `medium` | `""` | `--safe-mode` | `DISABLE_PROMPT_CACHING=1` | `<chat>` pieces each marked + unmarked step block |

Why each flag:

- `stream-json` in/out: send content blocks with `cache_control`, inject mid-run messages, read events. `--verbose` is required by stream-json output; `--include-partial-messages` gives text deltas and `message_start` (priming needs it).
- `--no-session-persistence`: nothing under `~/.claude/projects` (P8).
- `--setting-sources "" --strict-mcp-config`: no hooks, plugins, skills, CLAUDE.md, auto-memory, user MCP servers in the request (P2: 19 distinctive strings, 0 hits over 28 bodies; user hooks don't run).
- `--system-prompt-file`: replaces the default prompt and suppresses the volatile gitStatus block (round 1 Q5). Undocumented in `--help` but works (§13).
- No `--safe-mode` on master/priming: it silently drops `--mcp-config` servers (P1). The compactor has no MCP, so it keeps it.
- No `--bare`: refuses OAuth.
- `--permission-mode bypassPermissions`: `-p` cannot ask; default mode denies redirects, writes outside allowed paths and **every MCP tool** (P4). `dontAsk` + `--allowedTools` of the 10 tools also works. The flag is not in the request (cache-neutral).
- `--replay-user-messages`: the only signal that a mid-run message was consumed.
- `CLAUDE_CODE_PROMPT_CACHE_TTL=5m`: subscriptions default to 1 h marks; a 5 m mark after a 1 h one is a 400.
- System prompt file = `master.txt + "\n\n" + view_doc.txt + "\n\n" + instructions.md`, written once to a temp dir per process.

## 2. Deviations from the OptChat spec

| # | Deviation | Reason / evidence |
|---|---|---|
| D1 | Engine is `claude -p` on subscription, one process per turn | API pricing for third-party harnesses too high (§11) |
| D2 | Master view has no cache marks; a priming call writes them | CC uses all 4 marks from step 2; a view mark → `400 Found 5` (round 1 Q2, W1) |
| D3 | Kill at first `result`; requeue unreplayed mid-run messages | Otherwise CC runs a follow-up turn in the same conversation ~20 ms later, breaking gist rule 11 (round 2 probe 1b, R2) |
| D4 | CAP applies to the log only | CC owns model-facing tool output (and truncates it itself, §13) |
| D5 | MASTER prompt without the subagent paragraph | No spawn/tell in v1 |
| D6 | Compactor: `DISABLE_PROMPT_CACHING=1` + the spec's own 4 marks | Retries are tiny, so losing CC's rolling marks costs nothing; spec layout caches across calls (round 2 probe 2) |
| D7 | CC's identity line + userEmail block precede our content | Forced with OAuth; constant, cache-harmless |
| D8 | zoom/date via stdio MCP, not HTTP | Simpler; no subagents share it |
| D9 | `bypassPermissions` default | `-p` can't answer prompts (P4); approved by the user |
| D10 | `master.txt` adds: each turn is a fresh process, background tasks die with the reply | Kill at `result` kills `run_in_background` tasks (§13 step 6) |
| — | Thinking shown only as `thought for ~N tokens` | CC never streams thinking text (`thinking_delta` empty; T1) |
| — | Mid-run messages reach the model as a `role:"system"` wrapper, not a user message | CC behaviour (round 2 probe 1a, wrapper text quoted there) |
| — | Messages arriving while the turn waits in settle/prime join the same call | As built (§5.2) |
| — | Free nodes are persisted in `chat/tree` | Readers/MCP need no free-node logic (§3 as built) |
| — | View size counts node text only; refold uses the final tree | Gist leaves it open (§3 as built) |
| — | `import-optmem`: notes get 12:00 local time | Source has dates only; synthetic time is recognizable (§10) |
| — | Gist §9 (spawn/tell/computer) out of scope | v1 scope (§11) |

## 4. Compactor via `claude -p`

- Flags: base + `--model sonnet --effort medium --system-prompt-file prompts/compact.txt --tools "" --safe-mode`, env `DISABLE_PROMPT_CACHING=1`, `CLAUDE_CODE_PROMPT_CACHE_TTL=5m` (`summarize.ts`). Effort medium because low overshoots far more (gist §4.2).
- Message (layout A): `<chat>\n` + bare context lines (no ids) + `</chat>`, cut at 50k/80k/100k, **every piece marked** (≤4 marks, last at `</chat>`); then an unmarked step block: `For scale, this line is exactly 512 bytes:\n<SCALE>\n\nCompress this message into one line, in at most 512 bytes:\n<kind: text>` or `Merge these two lines …:\n<a>\n<b>`. `prompts/scale.txt` is exactly 512 bytes, hand-written, untested.
- Size retry loop: same process, follow-up user message `That line is N bytes; the limit is 512. It must end where it is cut here:\n<first 512 bytes, UTF-8 safe>| ← LIMIT`; stop when ≤512 or after 5 tries, return the shortest. Retries read the whole context and write nothing: ~6.3k eq each (round 2 probe 2).
- Failure: refusal, empty reply, `is_error`, non-zero exit, or no `result` in 5 min → node fails → fixed 10 s retry forever; first failure per node reported.
- Concurrency: JOBS=8 independent processes; failed nodes keep their slot during the 10 s wait.
- Caching: each next level-0 call reads through the 100k mark (~34–38k tokens) and writes only the tail piece + new line. S2 (real code, 105k-char chat): cold 50.3k eq, then **7.3–7.7k eq per call**, write 1.4–1.7k. Layout B (one block per tail line, `</chat>` moved to the step) would cut to ~6.5k eq (−38 %) but only while consecutive calls add ≤ ~20 lines (P7); unbuilt.
- Quality: 4/4 summaries 340–453 B, no retries/refusals, 3.1–4.7 s each (S3). Merges of real notes: 425–461 B.
- Cost per message: not measured end to end. **[inf]** Gist §10 says ~2 compactor calls per message amortized; at ~7.5k eq each that is ~15k eq per logged message minus free nodes, so a tool-heavy turn (10 tool/echo messages) costs ~150k eq in compaction against ~24k eq for the primed turn itself. Free nodes (`kind: text` ≤ 512 B; short tool calls often qualify) reduce it. Parallel calls sharing a prefix probably each pay the write before the first entry exists (unmeasured).
- One-off: importing 128 OptMem notes needs 82 sonnet calls before the view settles (S4, §13).

## 5. Other harnesses (`docs/pi-codex-proposal.md`)

- A proposal for Pi 1.0.2 (`@earendil-works/pi-coding-agent`), **rejected** by the author (commit message). It defines **no harness-adapter interface**; it argues for Pi's native agent loop via its SDK, a fresh in-memory session per turn, and hooks: `context_with_system` (replace transcript), `before_provider_request` (replace final payload, add cache marks), `tool_result` (cap before replay), steering via `session.steer()`, `clearQueue()` to recover unconsumed input, `registerTool` for zoom/date (no MCP), `ModelRuntime.streamSimple()` for the compactor (§1–3 of the proposal).
- Pi gotchas: steering lands only after a whole tool **batch** (not between siblings); codemode nests tool calls invisibly (log the outer call + its output only); Pi's `CacheWarmer` defaults on and must be disabled; extension hook errors fail open; session files persist reasoning (§1, §2, §8.2).
- Codex OAuth probes (§8.1, §8.3, §8.4): `prompt_cache_breakpoint` and `prompt_cache_options` → HTTP 400 "not supported on this model" (gpt-6.1-sol); `reasoning.context:"all_turns"` accepted. Implicit caching: exact repeats read 96–99.6 %, but any tail change at ~100k or ~50k reads **0**, for one block, 4 blocks or 4 messages, on gpt-6.1-sol and gpt-5.6-terra. Append-only replay inside a turn does reuse the prior prefix. Verdict: cross-turn view caching impossible on that route; in-turn fine.
- "Pi drives `claude -p` subprocesses": rejected as extra layers for no benefit (§6).
- Spec ambiguity resolved there by the user: CAP applies to zoom results too (§8). shitty-optchat itself caps only via the echo log.

## 6. Gaps, bugs, untested parts

- Memory merges not tested on real data (README). The full 82-call import tree was never built (S4).
- Whether a request killed at `message_start` is billed: inconclusive, assumed billed (F6). Kill sometimes loses the race (2/6, harmless, F3).
- Layout B unbuilt. Pump O(T) scan and MCP reload per call: fine to ~1e5 messages (`ponytail:`).
- Stale-socket double takeover race accepted (`store.ts:94`).
- Real `claude` behaviour when the harness is SIGKILLed (stdin closes): unmeasured (§16.8).
- Early merges forcing a full view rewrite: frequency unmeasured (§16.8).
- `<persisted-output>` files are CC's and get cleaned up; the log keeps only the notice (§16.8).
- Ctrl-Z during a real request: long suspension may break the API stream, unmeasured.
- Background tasks die with the turn; long-running servers impossible by design.
- Thinking text unavailable; only its size.
- Untested on purpose: flags, prompt files, MCP protocol, CLI end to end, `browse`, `cap()`, REPL screen, signals, `persist.ts` (§10; checked by hand in a pty).
- Doc drift: §16.2 says "the 19 tests" while §10 and §16.1 say 17.
- **[inf]** No env scrubbing: launched from inside a Claude Code session, the children inherit `CLAUDE_CODE_*` / plugin dirs; P2 showed no request leak for plugin dirs, other vars untested.
- **[inf]** The MCP config JSON carries `OPTCHAT_DIR`; only tool names/descriptions reach the request, so the "byte-identical config" rule (§9) is stricter than the cache needs, but harmless.

## 7. Implications for `ai chat` (Rust, on `ai memory`)

### Adopt as-is

- The invocation table in §1 above: flags, env, `masterArgs` shared by master and priming, `--safe-mode` only on the compactor, `bypassPermissions` default (or `dontAsk` + allowlist), system prompt file written once, `system/init` MCP check.
- Turn mechanics: render before logging; stream-json in; log in stream order; kill at first `result`; requeue untaken only after a `result`, else log them unanswered; mid-run input to stdin with replay matching.
- Event→log mapping and `cap()` head+tail; never log thinking.
- Compactor layout A, same-process size retries, shortest of 5, fixed 10 s retry, 5 min timeout, JOBS=8, rule 3 with the context snapshot taken at decision time, loud failure on an unbuilt context line.
- Child hygiene: registry, SIGTERM then SIGKILL after 5 s, kill in every exit path. In Rust add `PR_SET_PDEATHSIG` (Linux) in `pre_exec` so children die even when `ai chat` is SIGKILLed **[inf]**: closes the one unmeasured gap.
- zoom/date as an `ai chat mcp` subcommand over stdio. Hand-written JSON-RPC (4 methods, ~60 lines): the crate has no async runtime, and `rmcp` would pull in tokio for that.
- Usage log per call (`turn`/`compact`/`prime`) with model and the four usage numbers; `stats`.
- Probe discipline: re-run P1–P3 after each Claude Code upgrade.

### Change for the git-ref store

| OptChat assumption | `ai memory` reality | Recommendation |
|---|---|---|
| One writer, socket lock for process life | CAS per mutation; other sessions run `ai memory note`/`wake`/`sync` concurrently | Keep CAS, no lock. `ai chat` treats a CAS failure as "re-read the new commit": records that sort after its tail are appended to the in-memory log and `fit()` runs; anything else is a renumbering (below). Only the chat process runs the pump while it is live; to stop two pumps (e.g. two `ai chat`s) racing on summaries, take an advisory lease file `~/.ai/memory/chat.lock` (flock, not in the ref) for the **pump and REPL only**. Concurrent `note`s stay allowed. |
| Permanent dense ids `0..T-1` | Positions renumber when sync inserts earlier records | Renumbering may only take effect between turns. During a turn, `zoom`/`date` read a **pinned snapshot**: the chat writes the turn's commit oid to a file the MCP server reads (not in the MCP config, which must stay byte-stable). After a renumbering: refold, reuse summaries by fingerprint, accept one full cache rewrite. |
| `fsync` per JSONL line before returning | gix loose objects + ref update | Set `core.fsync=objects,reference` (and `core.fsyncMethod`) in the memory repo at init. **[inf]** Verify gix honours it; if not, fsync the written object files and the ref file ourselves. One commit per logged message keeps the gist's "a crash loses nothing" contract. |
| Variable-size messages (echo ≤ 30k chars, user pastes unbounded) | 512 B fixed records, text ≤ 305 B | Keep fixed 512 B records as the index, with a new `kind` field. Text that fits stays inline (every free level-0 node then reads straight from the record). Longer text goes into its own blob, referenced from the record by oid plus a short inline head for `grep`/display. Git dedups identical blobs. Fixed-width slicing and `fp` keys stay unchanged. |
| NODE = 512 B summaries | TREE record text ≤ 367 B | Widen tree records to 1024 B, with text ≤ 512 B **bytes** (UTF-8, as the gist measures). The gist's own evidence: 128 B lines were useless, 280 B was OptMem's, and 512 B is the target. |
| Level-0 node per message | Summaries exist only for blocks ≥ 2; `RAW_MAX` 16 raw shortcut | Pure binary (already decided): add `tree/1`, drop `RAW_MAX` from building (keep it only as a zoom display rule if wanted). |
| Compactor = background `claude -p` inside the harness | `nap` = the agent writes summaries by hand, nothing runs in the background | Inside `ai chat`, the compactor replaces `nap`. Outside a chat, notes from other sessions leave nodes pending; `ai chat` builds them at startup (and `nap` remains for sessions without a chat). |
| Persist = git commit per turn + backup | Commit per mutation, `sync` to the remote | Drop `persist.ts`; backup = `ai memory sync`. Run sync between turns (best-effort, like `wake`), never mid-turn. |
| `date` ISO UTC, local day files | `ts` UTC to the second, `(ts, origin)` key | Use the existing key. Provenance per message: agent `ai-chat`, model from `system/init`, session = the chat process id or turn id. |
| `instructions.md` in the data dir | `--setting-sources ""` drops the user's CLAUDE.md | Put the user's instructions explicitly into the system prompt file; source decided by the user (open question 2). |
| Each message is a git commit | ~25 KB loose objects per commit (git-ref note, Risks) | A tool-heavy turn is dozens of commits; `git gc --auto` after each turn, not just on sync. |

### Harness adapter

No interface exists upstream. **[inf]** The shape that falls out of `claude.ts`, `turn.ts` and `prime.ts`:

```
trait Harness {
  fn turn(&self, system: &Path, view: &[String], text: &str) -> Turn;   // events: Text, Talk, Tool, Echo, Taken(user), Thinking(n), Done(usage), Failed
  fn prime(&self, view: &[String]) -> Option<Usage>;                   // None if the harness can't cache across turns
  fn summarize(&self, ctx: &[String], step: &str) -> Summarizer;         // send(retry) / reply()
}
Turn: send(text), cancel()
```

Build it only with the second harness (layering rule); start with Claude Code types only. Codex gets `prime = None`: its OAuth route can't cache a changed view (§5).

### Recommendations, in build order

1. `kind` field, blob-backed long text, 1024 B tree records, `tree/1`, pure binary. `ai memory` keeps working.
2. Rust view fold + pump with an in-process fake summarizer; tests: fit invariants, rule 3, refold.
3. Compactor via `claude -p` (layout A). Measure cost per message on a real log before going further, because compaction likely dominates cost (§4 above).
4. `ai chat mcp` + turn without priming. Then priming. Then REPL.
5. Sync between turns, pinned snapshot for zoom/date, renumber → refold.

### Open questions for the user

1. **Subscription budget.** Is ~15k eq per logged message for compaction (inferred, sonnet) acceptable, or should the compactor run on haiku, or only on `user`/`talk` with tool/echo pairs folded together? The second option deviates from the gist.
2. **Instructions.** Which file feeds the system prompt: `~/.claude/CLAUDE.md`, a new `~/.ai/instructions.md`, or the cwd's `AGENTS.md`? The last one changes per cwd and breaks the cache.
3. **Permissions.** `bypassPermissions` (shitty-optchat default) or `dontAsk` + an explicit tool allowlist?
4. **CAP on zoom.** Should `zoom(id,1)` cap a huge message (the Pi user said yes), or return it whole (gist §7.1, shitty-optchat)?
5. **Notes from other sessions.** Do they enter the chat log interleaved by time (one store, as leaned), so the master sees them in its view? Who summarizes them when no chat runs?
6. **Where `ai chat` runs.** One always-on machine (gist §10) with others only syncing, or a chat on every machine? Two live chats on two machines means interleaved renumbering at every sync.
