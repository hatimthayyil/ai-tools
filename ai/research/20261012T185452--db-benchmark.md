# Embedded SurrealDB vs SQLite: measured

Benchmark of embedded SurrealDB against SQLite on a synthetic code-knowledge workload. Follows `20261003T104835--memory-db.md`, which measured build, size and open but no queries. Bench source: `/hatimthayyil/tmp/db-bench` (targets and data deleted; raw output in `results/`).

## Summary

- **Queries: SurrealDB is slower on every query except vector kNN.** Warm medians run 1.4× to 100× behind SQLite. Typical: 8–25× on graph and lookup queries, 4–40× on BM25. Single-record lookups have a floor of about 0.1 ms per query in SurrealDB and about 0.01 ms in SQLite.
- **Vectors: SurrealDB is ahead.** HNSW top-10 takes 2.7 ms at recall 0.995, against 31 ms for sqlite-vec's exact scan (11× faster). SurrealDB's own brute force takes 940 ms (30× slower than sqlite-vec). SQLite has no ANN index in this setup.
- **Opening the store** takes 0.68 s and 249 MB RSS, against 1.7 ms and 4.7 MB for SQLite (390×). Almost all of it is one cause: at open SurrealDB calls `sysinfo::System::new_all()`, which reads `/proc` for every process and thread on the host (666 processes and ~4150 threads here). In a fresh PID namespace the same open takes 38 ms and 42 MB RSS, still 11× SQLite under the same wrapper. No setting turns this off.
- **Bulk load** is 5.6× slower (29.6 s vs 5.3 s). The store is 8× larger on disk (628 MB vs 79 MB). Peak RSS during load is 2.6 GB vs 86 MB.
- **Concurrency is unchanged from the earlier note.** A second process fails on `LOCK`. SQLite WAL with `busy_timeout` let both writers finish.
- **Build:** 7 m 27 s wall and 65 CPU-min vs 33 s. The binary is 108.5 MB vs 2.6 MB. That is 397 vs 17 crates.
- "SurrealDB is slow" is true for this workload, with one exception (ANN). The per-invocation cost (open) is the worst number, and it depends on how many processes the host is running.

## Setup

| | |
|---|---|
| Machine | Intel Xeon E-2176M @ 2.70 GHz, 12 threads (`nproc` = 12), 62 GiB RAM, NixOS, Linux 6.18.55, dm-crypt volume |
| Toolchain | rustc/cargo 1.99.0, release profile, `strip = true` |
| SurrealDB | `surrealdb` 3.3.3 (latest on crates.io), `default-features = false`, features `kv-surrealkv`, `kv-mem`; surrealkv 0.21.4; tokio 1.53.2 multi-thread |
| SQLite | `rusqlite` 0.40.2 `bundled` (libsqlite3-sys 0.38.2, SQLite 3.53.2), FTS5; `sqlite-vec` 0.1.9 (0.1.10-alpha.4 fails to build: missing `sqlite-vec-diskann.c`) |
| DuckDB | **skipped**. The bundled C++ build is long. It is single-writer-process like SurrealDB. It adds nothing to the question. |

Durability, both durable by default:

- SQLite: `journal_mode=WAL`, `synchronous=FULL` (fsync per commit).
- SurrealKV: `sync=every` (fsync per commit, grouped commit). This is SurrealDB's default.
- The "relaxed" rows use SQLite `synchronous=NORMAL` and SurrealKV `sync=never`.

Dataset, generated deterministically (splitmix64, fixed seed, `common/src/lib.rs`):

- 585 dirs, 3 levels deep; 5,000 files; 50,000 symbols (10 per file).
- 250,000 edges: 50k `contains` (file→symbol), 175k `calls`, 25k `imports` (file→file). Of the calls, 70% go to a lower id in the same leaf dir, 29.5% to a lower "core" symbol (skewed to low ids), and 0.5% anywhere in the same dir, which creates local cycles.
- One ~1 KB summary per file and per dir, each with a 16-hex content hash.
- 20,000 unit vectors, 768-dim f32, in 200 clusters; queries are perturbed data points.
- 1,000 review comments across 50 threads.

Same rows in both engines; result counts match across engines for every query.

Schemas (idiomatic per engine):

- **SQLite.** Tables `dir(parent)`, `file`, `symbol(file)`, `summary(path UNIQUE)`, `comment(thread, ts)`. Edges live in `edge(kind, src, dst)`: `WITHOUT ROWID`, PK `(kind, src, dst)`, index `(kind, dst, src)`. `summary_fts` is an external-content FTS5 table. `emb` is a `vec0(float[768], cosine)` table.
- **SurrealDB.** Records `dir:N`, `file:N`, `symbol:N`, `summary:N`, `emb:N`, `comment:N` with record links. Edge tables via `INSERT RELATION`: `contains`, `calls`, `imports`, and `has` (dir→dir). `FULLTEXT ANALYZER simple BM25` on `summary.text`, UNIQUE on `summary.path`, `HNSW DIMENSION 768 DIST COSINE TYPE F32` (default M/EFC), and an index on `comment(thread, ts)`.

Loading:

- Both engines commit every 1,000 rows. SQLite uses prepared inserts; SurrealDB uses `INSERT INTO t $rows` with native `Value`s, so there is no JSON.
- Secondary, FTS and vector indexes are built after the bulk load in both.
- Comments are inserted one statement per transaction.

## Results

### Cost of having it

| | SQLite | SurrealDB 3.3.3 | Ratio |
|---|---|---|---|
| Clean release build (wall / CPU) | 33 s / 45 s | **7 m 27 s / 65 min** | 13× / 87× |
| Crates (normal + build deps) | 17 | 397 | |
| Binary, stripped (`.text`) | 2.6 MB (2.1 MB) | **108.5 MB (82.6 MB)** | 42× |
| Baseline binary (dataset generator only) | 0.37 MB | 0.37 MB | |
| Open + one point query, separate process, median of 10 | **1.7 ms** | **679 ms** | 390× |
| same, in a fresh PID namespace (`unshare -rpf --mount-proc`; `unshare true` alone = 2.7 ms) | 3.5 ms | 38.0 ms | 11×; ~40× after subtracting `unshare` |
| RSS of that process | 4.7 MB | 249 MB (42 MB in PID namespace) | 53× |
| On-disk size after load (`du`) | 79 MB | **628 MB** (703 MB with `sync=never`) | 8× |
| Peak RSS during load (incl. ~76 MB generated dataset) | 86 MB | **2.56 GB** | 30× |
| Peak RSS during query run (incl. ~76 MB dataset) | 85 MB | 1.39 GB | 16× |

How the SurrealDB open time breaks down, on this host:

| Stage | Host `/proc` (666 procs) | Fresh PID namespace |
|---|---|---|
| `sysinfo::System::new_all()` alone (probe) | 664 ms | 3.1 ms |
| `Surreal::new::<SurrealKv>` | 509 ms | 24 ms |
| `use_ns`/`use_db` | 7 ms | 12 ms |
| first query | 0.8 ms | 0.8 ms |

- The call is `surrealdb-core` `kvs/ds/builder.rs` → `sys::refresh_if_cold()` → `ENVIRONMENT` → `System::new_all()`. It is unconditional.
- strace of one open: 29,587 `openat` and 83,888 `read`, nearly all under `/proc/*/task/*`.
- The cost grows with the host's process and thread count. A desktop with a browser and many agent sessions pays the most.

- Durable single-row commits cost the same in both engines, because fsync dominates.
- The in-memory engine (`kv-mem`, surrealmx) loads the graph 3.5× *slower* than SurrealKV on disk, so it is no shortcut for building a throwaway index.

### Queries, warm, median latency

Each query runs 2 warm-ups, then repeats until 2 s or 50 samples (min 5). The process opens the store once and runs everything warm. SurrealDB queries are SurrealQL strings through the SDK (parsed each call). SQLite uses cached prepared statements.

|---|---|---|---|---|---|

| Callers, unbounded, cycle-safe | 5,052 ids | 7.5 ms | 63 ms | 8.5× | 35 ms |
| Callers, unbounded, core symbol | 35,683 ids | 72 ms | 476 ms | 6.6× | 270 ms |

Notes:

- **BM25 results agree.** Both engines return the same top hit for every query. SurrealDB `@1@ 'a b'` means AND, like FTS5 `'a b'`.
- **Stale-summary variants.** In SurrealDB, binding the 5k-entry map alone costs about 7 ms per query. Other SurrealQL forms tried:
  - `$cur.filter(...)` with a subquery per row: 2.7 s.
  - `LET` then `filter` over `$m`: 780 ms.
  - `hash NOT IN $cur.hash`: 5.2 s.

  The practical SurrealDB path is to fetch all `(path, hash)` rows (~15–20 ms) and diff in Rust.
- **Shortest path in SQLite.** The recursive-CTE form explodes without per-node visited sets, so SQLite uses an application BFS. That is how a Rust app would do it. SurrealDB's `+shortest` is the one graph query where it comes close, at 1.4×.
- **Graph queries on kv-mem** run about 2× faster than on SurrealKV, so part of the gap is the storage layer. Even in memory, SurrealDB is 3–10× behind SQLite on disk, which is warm in the page cache at 79 MB.

### Two writer processes at once

Each process does 300 single-row commits; the second starts 0.3 s after the first.

| | Outcome |
|---|---|
| SQLite WAL, `busy_timeout = 10 s` | **Both succeed.** The writers interleave (935 ms and 1,665 ms). Readers are never blocked. |
| SurrealDB SurrealKV | **The second fails at open:** `Database at data/surreal/LOCK is already locked by another process`. Reading from a second process fails the same way. |

## Tuning tried (SurrealDB)

- **`sync=never`.** It makes single commits 24× faster (133 ms per 1k) and the graph load 22% faster. Open time does not change.
- **Engine knobs are out of reach from the SDK.** Block cache, memtable and vlog are read from a `ConfigMap`. The embedded SDK passes an empty map plus the connection-string query keys, prefixed `datastore_`. So only `sync`, `versioned` and `retention` can be set through the SDK. `SURREAL_*` env vars do not reach SurrealKV. The defaults on this 62 GiB host are a block cache of ~30 GiB (half of RAM minus 1 GiB) and a 1 GiB memtable. That fits the 1.4–2.6 GB RSS seen under load. Changing them needs `Surreal::unstable_from_datastore` with a hand-built `Datastore` (semver-exempt); not tried.
- **The open-time fix is outside SurrealDB's settings.** Running in a PID namespace with few processes cut open from 679 ms to 38 ms. That is not a deployable fix for a CLI. The real fix is upstream: skip `System::new_all()` (use `System::new()` and refresh only the own pid), as `surrealdb-common`'s memory probe already does.
- **kv-mem** is not faster to fill: 54 s vs 30 s.

## What was not measured

- DuckDB (skipped, see Setup).
- SurrealDB with RocksDB (`kv-rocksdb`). The earlier note expects a worse build, and the lock is the same.
- SurrealDB block cache and memtable tuning through `unstable_from_datastore`.
- An ANN index for SQLite (sqlite-vec 0.1.9 has none; the DiskANN code is in the broken alpha). So the kNN row compares HNSW against an exact scan.
- Cold-cache (dropped page cache) query latency; all query numbers are warm.
- Scaling beyond this size, and SurrealDB's newer experimental executor.

## Rerun

```
cd /hatimthayyil/tmp/db-bench
./build-times.sh        # clean builds per engine into target-clean-*, wall/CPU/size
./run.sh                # builds into ./target, loads both, queries, opens, concurrency, kv-mem
rm -rf target target-clean-* data
```

- Requires cargo, hyperfine, GNU time (`/run/current-system/sw/bin/time`), and `unshare` with unprivileged user and PID namespaces.
- `run.sh` writes data to `./data`. The SurrealDB store is ~0.7 GB; a full run takes ~4 min after the build.
- Binaries take `load|query|open|writer DIR`. `bench-surreal` also takes `stages DIR` and `sql DIR 'stmt'...`, and `load mem` runs the kv-mem load and queries.
- `BENCH_RELAXED=1` switches to the relaxed durability settings.
- Tunables are the constants at the top of `common/src/lib.rs`.
