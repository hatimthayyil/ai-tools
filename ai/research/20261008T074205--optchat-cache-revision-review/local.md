# Local OptChat cache audit

Author: @codex (GPT-6)
Date: 2026-10-08
Scope: read-only audit of current v0.5.0 memory/chat source, earlier v0.4 source, and the old/new OptChat recipe. Existing uncommitted compactor prompt/retry changes were observed without modification. Changelog: 2026-10-08 @codex (GPT-6): audited reachability, request layout and revisions; ran a deterministic production-view reproduction with no model calls.

## Does our code retain the cache-breaking design?

### Takeaway

Yes: the frozen chat still uses the old erroneous merge priority, merges continually near the high-water budget, rebuilds its view on restart and uses the old large fixed cache blocks. These are confirmed source defects relative to the revised chat design. Current standalone memory uses a different overview and task-only compactor, so the chat findings cannot be applied wholesale to `ai memory wake` or `nap`.

### Cited Findings

- Revised sibling source is clean at OptChat `3c190e06f34aba0c69f49042c526093269604935`; old source was `f51fe5c910427fd6f384d22823140b1693c76207`. The latest explains the original bug explicitly: age measured from a pair's first message picks older merges that the push algorithm would keep. It prescribes `(T-last)/2^l`, with last the pair's last message. — [Revised explanation](/hatimthayyil/code/optchat/optchat.md:157).
- Our exact old formula remains `(t - a.id()) / 2^(a.l+2)`. `Coord::id` is the first message of the older sibling. `t` is the count of messages. — [Merge score](/hatimthayyil/code/ai-tools/ai/src/rs/memory/src/view.rs:134); [Coordinate](/hatimthayyil/code/ai-tools/ai/src/rs/memory/src/tree.rs:21).
- `Mem::fit` merges whenever size exceeds 128,000 and stops as soon as it fits that same budget. Each appended message and completed summary invokes it. There is no 64,000 low-water target or batch-in-progress state. This retains the original recipe; revised §3.2 appends between batches and folds from >128,000 to ≤64,000. — [fit and add_message](/hatimthayyil/code/ai-tools/ai/src/rs/memory/src/view.rs:112); [Completed jobs](/hatimthayyil/code/ai-tools/ai/src/rs/memory/src/compact.rs:271); [Revised timing](/hatimthayyil/code/optchat/optchat.md:184).
- `Mem::load` loads persisted tree nodes then calls `refold`; `refold` clears the view and replays all messages from zero against the now-available tree. The view coordinates are process state, not a persisted live snapshot. The revised recipe explicitly requires saving/loading `view.json`. — [Load](/hatimthayyil/code/ai-tools/ai/src/rs/memory/src/view.rs:34); [Refold](/hatimthayyil/code/ai-tools/ai/src/rs/memory/src/view.rs:150); [Revised persistence](/hatimthayyil/code/optchat/optchat.md:195).
- Production source reproduction used 20 ten-byte nodes and a 30-byte view budget. With all leaves appended before parents were supplied, the live view was `0+8,8+8,16+4`. Refolding the identical built tree produced `0+16,16+2,18+2`. Thus a restart *can* change view prefixes even with identical log/tree content; it need not happen for every run. The existing refold test only exercises a promptly built seeded tree and cannot establish equality under delayed parents. — [Executable reproduction](/hatimthayyil/code/ai-tools/ai/research/20261008T074205--optchat-cache-revision-review/local-reproduction.rs); [Existing test](/hatimthayyil/code/ai-tools/ai/src/rs/memory/tests/memory.rs:243).
- Independent score calculation at `T=10`, view `0+4,4+4,8+1,9+1`: old scores are 0.625 for `0+4,4+4` and 0.5 for `8+1,9+1`; corrected scores are 0.75 and 1.0. Old ordering rewrites from the first line; corrected ordering preserves the first eight messages and merges the recent pair. The production reproduction also shows repeated rewrites of existing lines once a constant three-line budget is full. — [Executable reproduction](/hatimthayyil/code/ai-tools/ai/research/20261008T074205--optchat-cache-revision-review/local-reproduction.rs); [Author's same counterexample](/hatimthayyil/code/optchat/optchat.md:177).
- Chat actually renders this `Mem` into its prompt and waits for built summaries before issuing fresh calls. Standalone `wake`, however, calls `cover(t, WAKE_LINES)` and recursively opens missing nodes; it never uses the chat view's `fit` result. — [Chat](/hatimthayyil/code/ai-tools/ai/src/rs/chat/src/session.rs:217); [Wake](/hatimthayyil/code/ai-tools/ai/src/rs/memory/src/cli.rs:304); [cover](/hatimthayyil/code/ai-tools/ai/src/rs/memory/src/cover.rs:28).
- `ai memory nap` and `pending` still construct/refit a `Mem`, so the bad formula is not dead code. But current `due` uses only node availability/readiness/busy status, not the folded view; `message` has no context, and `run` finishes by checking running jobs. Therefore the folded coordinates have no demonstrated influence on standalone compactor input or cache. — [pending](/hatimthayyil/code/ai-tools/ai/src/rs/memory/src/cli.rs:386); [Scheduler](/hatimthayyil/code/ai-tools/ai/src/rs/memory/src/view.rs:167); [Task-only input](/hatimthayyil/code/ai-tools/ai/src/rs/memory/src/compact.rs:80); [Run loop](/hatimthayyil/code/ai-tools/ai/src/rs/memory/src/compact.rs:325).
- The backlog explicitly freezes `ai chat` pending upstream implementation, after a costly session. — [Backlog](/hatimthayyil/code/ai-tools/ai/backlog.md:7).

### Inferences

- Reproduce without Cargo or APIs: `rustc --edition=2024 -Awarnings 'ai/research/20261008T074205--optchat-cache-revision-review/local-reproduction.rs' -o /tmp/optchat-local-audit`, then `/tmp/optchat-local-audit`. It includes the unchanged production `tree.rs` and `view.rs`; unused store calls are stubbed, and the `anyhow::Result` alias is replaced only to avoid external dependencies. No application files or shared memory are written. The initial attempt using an existing `anyhow` rlib failed due to a rustc-version mismatch; this standalone invocation compiled and ran successfully.
- Fixing only the `first`/`last` priority is insufficient for revised cache preservation. Chat also needs hysteresis and saved coordinates/batch state. A persisted view has to be pinned to its log/tree snapshot and validated when messages are reordered or synchronized; blindly replaying history with newly available parents loses the live folding history.
- A merge invalidates reusable prefixes from the changed block onward. Earlier stable marked prefixes, tools and system content can remain cacheable. Do not say every compaction trashes all cached tokens.
- Leave OptMem-style `wake` behavior alone when fixing chat: rebuilding its short overview is a deliberate standalone-memory design, not proof of the chat bug affecting every agent startup.

### Gaps

- No local usage ledger ties the reported quota spike to individual fold decisions. The confirmed defects explain cache churn, not an exact subscription savings percentage.

## Are cache marks, priming and compactor requests equivalent to the revised recipe?

### Takeaway

They are materially different. Our chat compensates for Claude Code's automatic mark limits with a priming request, but a changed short view rewrites its whole view block in the prime. Current memory removed expensive context replay deliberately; restoring revised full-envelope compactions would be a redesign with a separate context-size and quality tradeoff.

### Cited Findings

- Our split points remain 50,000, 80,000 and 100,000 characters, cut at earlier newlines, with a final remainder block. Revised Anthropic layout uses four-line blocks, marks the final complete view block and request end, and waits for an in-flight writer before duplicate writes. — [MARKS/cut_blocks](/hatimthayyil/code/ai-tools/ai/src/rs/memory/src/compact.rs:27); [Chat split](/hatimthayyil/code/ai-tools/ai/src/rs/chat/src/prime.rs:12); [Revised mark layout](/hatimthayyil/code/optchat/optchat.md:223).
- A prime marks *every* current view block then sends unmarked `ok`. The real turn uses identically split view blocks with no caller marks then appends unmarked user text. Prime and actual master use identical argv/model/system/tools; prime alone sets `DISABLE_PROMPT_CACHING=1`. This flag removes automatic marks, while our serializer still includes explicit `cache_control` for marked blocks. — [Prime send](/hatimthayyil/code/ai-tools/ai/src/rs/chat/src/prime.rs:79); [Turn send](/hatimthayyil/code/ai-tools/ai/src/rs/chat/src/session.rs:268); [Master command](/hatimthayyil/code/ai-tools/ai/src/rs/chat/src/master.rs:54); [Serializer](/hatimthayyil/code/ai-tools/ai/src/rs/memory/src/claude.rs:365).
- Below 50,000 characters the entire rendered `<chat>…</chat>` is one block. Appending lines changes that block before its closing tag; the previous prime's mark is at the old whole block's end, not at the still-unchanged individual line boundaries. Fixed large blocks similarly limit the next prime to surviving large checkpoints. Exact current-view priming can still help the following turn; the defect concerns repeated changed-view primes and their rewrite costs. — [Block slicing](/hatimthayyil/code/ai-tools/ai/src/rs/memory/src/compact.rs:46); [Rendered tags](/hatimthayyil/code/ai-tools/ai/src/rs/memory/src/view.rs:212); [Historical cache probe findings](/hatimthayyil/code/ai-tools/ai/research/20261004T171431--optchat-cache-claude-code.md).
- Primer freshness requires exact string equality and age under 270 seconds. Every changed view therefore requires another prime before a queued turn; changed built views also prime speculatively after one idle second. The request is killed at `message_start`. The source treats any such event as `Primed::Yes`, even if both reported cache token counts are zero. — [Freshness](/hatimthayyil/code/ai-tools/ai/src/rs/chat/src/prime.rs:46); [Idle/demand priming](/hatimthayyil/code/ai-tools/ai/src/rs/chat/src/session.rs:228); [Prime success](/hatimthayyil/code/ai-tools/ai/src/rs/chat/src/prime.rs:98); [Stop event](/hatimthayyil/code/ai-tools/ai/src/rs/chat/src/session.rs:56).
- Every child forces automatic marks to five minutes; explicit caller marks omit TTL and thus do not request an hour. Revised text distinguishes five-minute API entries from subscription-owned one-hour caching and says not to send keepalive pings. Our idle priming is change-triggered cache preparation, not a periodic keepalive. — [TTL env](/hatimthayyil/code/ai-tools/ai/src/rs/memory/src/claude.rs:60); [Explicit mark](/hatimthayyil/code/ai-tools/ai/src/rs/memory/src/claude.rs:370); [Revised TTL](/hatimthayyil/code/optchat/optchat.md:233).
- In v0.4 (`5892350`), each compactor request carried the full preceding view, flattened without IDs, split at the old fixed marks and explicitly cached. There was no in-flight-prefix write coordination. v0.5 commit `b7f468b` removes `Job::context`, `Mem::context/first`, and compactor view marks altogether. Current task-only `message` is unchanged by pending prompt/retry edits. — [Current context-free request](/hatimthayyil/code/ai-tools/ai/src/rs/memory/src/compact.rs:80); [Scheduler without view gate](/hatimthayyil/code/ai-tools/ai/src/rs/memory/src/view.rs:167); [Prior v0.4 evidence](/hatimthayyil/code/ai-tools/ai/research/20261007T064116--ai-chat-subscription-usage-review.md).
- Current compactor is Sonnet/medium, no tools, separate COMPACT system, and disables automatic marks. Chat master defaults Opus/high with builtins and MCP tools. Revised compactions use the same static system/tools envelope as turns and a *separate smaller* context view with 16–32 KB sawtooth. Our v0.5 tasks cannot share the master's tools/system cache envelope; this is an intentional inexpensive task-only design rather than a lingering expensive view-cache bug. Even upstream's suggested cheaper compactor model can prevent cross-model cache reuse, so same-envelope wording alone does not prove sharing between different models. — [Compactor settings](/hatimthayyil/code/ai-tools/ai/src/rs/memory/src/claude.rs:310); [Tool-less command](/hatimthayyil/code/ai-tools/ai/src/rs/memory/src/claude.rs:320); [Chat backend](/hatimthayyil/code/ai-tools/ai/src/rs/chat/src/cli.rs:49); [Revised compactor envelope/view](/hatimthayyil/code/optchat/optchat.md:245); [Model-switch caveat](/hatimthayyil/code/optchat/optchat.md:236); [Deliberate rationale](/hatimthayyil/code/ai-tools/ai/comments/ai/src/rs/memory/src/compact.rs.md:6).
- Summary size repairs remain up to five requests in one conversation and shortest output wins; failed jobs restart after ten seconds indefinitely. Revised recipe retries failed jobs on the next message, not a ten-second repeating background timer. These can amplify requests independently of cache-shape defects. — [Size repairs](/hatimthayyil/code/ai-tools/ai/src/rs/memory/src/compact.rs:94); [Failure timer](/hatimthayyil/code/ai-tools/ai/src/rs/memory/src/compact.rs:276); [Revised retry](/hatimthayyil/code/optchat/optchat.md:296).
- Latest stated 98.6% turn and 96.2% compaction prefix hits came from replaying 3,000 messages against a *model* of Anthropic caching. They are simulated replay statistics, not measurements of our code, account or subscription. — [Author's measurement qualification](/hatimthayyil/code/optchat/optchat.md:239).

### Inferences

- Before any chat redesign, freeze the request envelope, correct score, batch merges, persist view and evaluate stable four-line blocks under the actual Claude Code mark budget. Directly adding marks to real turns risks the documented four-breakpoint limit from older probes; the revised gist's API-style scheme cannot be copied mechanically into this wrapper.
- Keep current standalone compactor small unless a quality study justifies context. If adding context, use a bounded/persisted compaction view, prefix-flight coordination and a request ledger; do not restore v0.4's whole-view replay on every job.
- Record both priming and actual turn usage to evaluate total savings. A high real-turn hit rate can conceal expensive prime writes; display cache-hit metrics for all requests and distinguish API-equivalent cost from subscription quota.

### Gaps

- No live provider calls were made. Whether this installed Claude Code version preserves explicit marks and how many automatic marks it inserts today are not re-probed; historical probes are evidence of why the existing adapter is shaped this way, not a guarantee for current versions.
- Exact byte savings, actual cache reuse percentage, total quota consumed and summary-quality consequences of removed context remain unproven by this source audit.
