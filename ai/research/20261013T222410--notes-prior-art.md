# Prior art for `ai notes` (design A)

Checks the claims design A rests on: atomic leaf notes, one curated slug tree, single-parent rollup summaries, free weak links, supersedes links, curator on write, budgeted view/zoom.

## 1. Luhmann's Zettelkasten (Schmidt 2018, Sociologica)

- **Fixed position, not topical order.** "the filing technique does not build on the idea of an order of contents ... but of a fixed order of positioning." Each card gets a number, so a fixed place that never changes (1/1, 1/1a, 1/1a1, ...; up to 13 characters, e.g. `21/3a1p5c4fB1a`).
- **Branching is local, not a taxonomy.** A new card only needs "some relation to the previous entry"; "there is no top and no bottom"; "the number on its own does not really inform about the relations between different notes". Top-level sections are loosely coupled, "not ... a strictly hierarchical order".
- **He rejected one-subject classification.** Assigning a topic to "one and only one single (top-level) subject" is ambiguous. He used "multiple storage" instead: the same topic is reachable from several contexts through references.
- **References (Verweise)** come to about 20k in collection I and 30k in collection II, roughly one per card or one per two cards. There are three kinds:
  - outline references, which work like a table of contents;
  - collective references: a card at the start of a section listing up to 25 related cards, mostly far away. These are the **hubs**.
  - single references, inside a card's argument.
- Luhmann added references to old cards as new ones arrived ("permanent data bank update").
- **Orphans die.** Cards with no links became "black holes ... remain isolated later on and hence fade away".
- **Keyword index (Schlagwortregister)** had about 1,250 entries in collection I and 3,200 in collection II. It listed "only one to four places" per term: entry points into the web, not a complete index. There was no table of contents. He rebuilt the index 4 times when it got messy.

Implication: Folgezettel is one-position-per-slip, but the position records a *line of thought*, not a *topic classification*. Design A's curated topic slugs (`linguistics.syntax.minimalism`) are the systematic classification Luhmann avoided. That is fine for summarisation, because summaries need a partition. Hubs and the keyword index map to:
- **hub nodes**: a node type whose body is mostly weak links (Luhmann's collective-reference cards);
- **orphan lint**: no notes with zero weak links in or out;
- **a small entry-point index**: term to 1–4 ids.

## 2. RAPTOR (Sarthi et al., ICLR 2024)

- **Build.** Chunks of about 100 tokens, embedded with SBERT, then UMAP and a GMM. The number of clusters is chosen by BIC, global then local. A cluster that goes over the summariser's limit is reclustered. gpt-3.5 summarises each cluster, and the process repeats upward.
- **Multi-parent: yes.** It uses "soft clustering, where nodes can belong to multiple clusters", because segments span topics. The code assigns a node to every cluster with GMM probability > 0.1 (`threshold=0.1`, `raptor/cluster_utils.py`).
- **Retrieval.**
  - Tree traversal: top-k per layer, from the root down.
  - Collapsed tree: all nodes of every layer ranked flat by cosine, filled to a token budget (2,000 tokens, about 20 nodes).
  - Collapsed "consistently performs better". Traversal keeps a fixed ratio across layers. Collapsed picks whatever granularity the question needs.

## 3. MemTree (Rezazadeh et al., ICLR 2025), the closest analogue to design A

- **Online single-parent tree.** An insert descends from the root to the most similar child. The similarity threshold rises with depth (θ0 = 0.4, λ = 0.5). If no child passes, the insert becomes a new leaf. If it reaches a leaf, that leaf becomes a parent.
- An LLM rewrites every ancestor on the path ("aggregate"), at about 3.3 calls per insert. The authors accept being "less flexible than a generic graph" to bias toward hierarchy.
- **Retrieval is collapsed (flat over all nodes).** Traversal "biases the search towards paths already established", and small-k traversal lost accuracy.
- **Results** were about on par with offline RAPTOR: QuALITY 59.8 vs 59.0, MultiHop-RAG 80.5 vs 81.0. Cumulative build time was 1.4x RAPTOR. Rewriting along the insertion path favours recent content.

## 4. GraphRAG (Edge et al., 2024)

- **Build.** Hierarchical Leiden communities form a strict partition at each level, so each node has a single parent per level.
  - Leaf communities are summarised from element summaries ranked by prominence, filled to the token limit.
  - A higher level that would overflow swaps in sub-community summaries: a rollup from children's summaries.
- **Global search** is map-reduce over community summaries: partial answers are scored 0–100, zero scores dropped, the rest merged. **Local search** starts from entities.
- **Results.**
  - Every summary level beat vector RAG on comprehensiveness and diversity.
  - Intermediate and low levels did best.
  - Root summaries (C0) used 2–3% of the tokens of source-text map-reduce and still won 72%/62% against vector RAG.
- **Updates are the weak point.**
  - Adding documents makes communities and their reports stale.
  - Community reports are a large share of build cost.
  - Reported `graphrag update` behaviour: only appends new communities, and deleting a document needs a full reindex. This is secondary-source, unverified.
  - Zep chose label propagation over Leiden because it extends incrementally, but drift still forces "periodic community refreshes".

## 5. A-MEM (Xu et al., NeurIPS 2025)

- **Note** = {content, timestamp, LLM keywords, tags, context description, embedding, links}.
- **Links.** Top-k embedding neighbours (k = 10), then the LLM decides which to link.
- **Evolution.** For each neighbour, the LLM may rewrite its context, keywords and tags, and "the evolved memory m_j* then replaces the original". There is no versioning. The prompt also lists undocumented "merge" and "prune" actions.
- **Ablation** (F1, gpt-4o-mini; no error bars, no significance tests):
  - Multi-hop F1 was 9.7 with neither link generation (LG) nor memory evolution (ME), 21.4 without ME, and 27.0 with both.
  - Links carry most of the gain, and evolution adds some.
- Evolution only rewrites *metadata*. Content is never merged.

## 6. Mem0 (Chhikara et al., 2025)

- **Paper.** For each extracted fact, the top s = 10 similar memories go to an LLM tool call: ADD, UPDATE ("replace with richer information"), DELETE (physical removal of the contradicted memory) or NOOP.
- **Mem0g** (graph variant) instead *marks* conflicting edges invalid rather than deleting them, "to enable temporal reasoning".
- **The current Mem0 docs describe add as ADD-only:** "New memories are added without overwriting or deleting existing memories." Production Mem0 has moved away from in-place UPDATE/DELETE. No reason is stated in the docs.
- No error rates for operation choices are published.

## 7. Zep / Graphiti (Rasmussen et al., 2025)

- **Bi-temporal edges.** Valid time is `t_valid`/`t_invalid`, when the fact held in the world. Transaction time is `t'_created`/`t'_expired`, when the system learned or retired it.
- A contradicting new edge sets the old edge's `t_invalid` to the new edge's `t_valid`. The old edge is kept.
- Entity and edge dedup on write: embedding plus full-text candidates, then an LLM decides duplicate or not. Edge dedup is limited to the same entity pair.

## 8. Newer LLM-maintained stores

- **Karpathy "LLM Wiki" (gist, Apr 2026).** Three layers:
  - immutable `raw/` sources;
  - LLM-owned wiki pages;
  - a schema file, with `index.md` (catalog, one line per page, read first) and an append-only `log.md`.
  - Ingest touches 10–15 pages. Lint looks for contradictions, "stale claims that newer sources have superseded", orphans and missing cross-references.
  - The index alone works to about 100 sources / hundreds of pages, then "you want proper search".
- **Letta MemFS.** Agent memory is a git repo of Markdown files with YAML frontmatter. A required `description` is always visible in the tree. `system/` files are always in context, and others are read on demand. Consolidation ("dreaming") runs in background subagents after N steps or at compaction, off the hot path. Large reorganisations back up first.
- **HippoRAG 2 (2025)** found structure-augmented RAG "drops considerably below standard RAG" on basic factual recall. It uses a KG plus Personalized PageRank, with no summaries.
- **MemoryAgentBench FactConsolidation (2025)** tests conflict resolution: the newer fact must win.
  - Single-hop: Mem0 18%, Zep 7%, MemGPT 28%, BM25 48%, HippoRAG-v2 54%, GPT-4o long context 60%.
  - Multi-hop: ≤ 7% for every system. "Selective Forgetting still poses a significant challenge to all memory mechanisms."
- **"Don't Ask the LLM to Track Freshness" (2026).** Resolving freshness with deterministic code (max over version serials) instead of LLM judgement gave 78% single-hop and 30% multi-hop (gpt-4o-mini). The bottleneck is assembly after retrieval, not storage.
- **"Ground Truth First" (2026).** Rankings flip with how long a memory has been in use. A budgeted curated-map memory led at 3 weeks but fell from 96% to 72% recall of evicted content by 9 weeks. A provenance-typed graph rose to 90%. Weakly written facts failed 24% of the time vs 2%.

## Answers

**(a) Single-parent rollup plus free cross-links: supported for summarising, with one caveat for retrieval.**
- GraphRAG (partition per level), MemTree (strict tree, competitive with RAPTOR) and Luhmann (one position per card, about 1 cross-reference per card) all pair one position with many links.
- RAPTOR's soft clustering is the only multi-parent case. It has no ablation showing it helps, and its threshold is a GMM artefact.
- The stronger finding is about **retrieval**: RAPTOR and MemTree both found top-down traversal worse than flat search over all levels. Design A should make `grep`/search span leaves *and* summaries at once and return breadcrumbs, so an agent can land at any depth. `view` → `zoom` traversal should not be the only path in.
- Luhmann's evidence argues against treating the topic tree as meaning. Keep slugs cheap to move (`mv`), and treat hubs and weak links as the place where cross-topic structure lives.
- Add orphan detection: Luhmann's "black holes" and Karpathy's orphan lint.

**(b) Staleness and validity: use bi-temporal invalidation, not deletion and not a bare link.**
- Every system that handles change well keeps the old fact and marks it: Graphiti `t_invalid`, Mem0g "mark invalid", and current Mem0, which went ADD-only.
- Design A's `supersedes` link is the right primitive if it also sets `invalid_at` (when the fact stopped holding) on the old note, kept apart from `checked` (when we last verified it). That makes it a valid-time/transaction-time pair like Graphiti's.
- Freshness should be decided by code from those fields, never by the curator's judgement ("Don't Ask the LLM to Track Freshness").
- Views should hide invalidated notes by default and roll up only valid children.
- Decay rate × days since `checked` gives a mechanical "recheck due" flag, the lint step in Karpathy's wiki.

**(c) Failure modes of curator-on-write.**
- A-MEM overwrites neighbours with no history.
- Mem0's paper DELETE physically removes facts, and the product now avoids UPDATE/DELETE entirely.
- All LLM-curated stores score poorly on conflict resolution (Mem0 18%, Zep 7% single-hop; ≤ 7% multi-hop). Plain BM25 beats them.
- Eviction under a budget lost 24 points of recall over 9 weeks.
- No paper reports error rates for the merge/delete decision itself; that loss is unmeasured.
- Design A's curator should therefore never destroy anything:
  - `merge`/`duplicate` keep both files, marking one superseded or linking it;
  - `contradicts` adds a link and leaves both valid until a human or evidence resolves it;
  - every decision is a git commit, so it can be reverted.
- Run expensive reorganisation (splits, summary rebuilds) off the write path, as Letta does with dreaming and GraphRAG with periodic refresh.
