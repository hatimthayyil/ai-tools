# Agent team

Author: Claude Code (Claude Opus 5.5)

Design for a team of agents under the user: a tree of agents, experts and their knowledge, who reads whom, messages between agents held for the user's approval, and the TUI where the user approves them. It builds on `20261024T084514--agents.md` ("the agents note") and `20261029T193051--agent-messaging-survey.md` ("the survey"). Nothing here is built. **Agreed** marks the user's decisions, **Recommended** proposals awaiting the user's confirmation; the open questions close the note.

## 1. The tree

**Agreed**

- `main` is the user's single point of contact: one agent, at user level.
- Four levels:
  1. `main`, at user level.
  2. Companions, at user level: experts in a field (knowledge), such as `quran` or `linguist`, or in a skill, such as software engineering. `infrastructure` is both.
  3. A lead in each repo, `lead@<repo>`.
  4. Specialists in each repo, such as `developer` and `reviewer`.
- A user-level agent works across repos; a repo-level agent works in one.
- The user's intent and priorities pass down the tree, level by level.
- Every agent is well-rounded, with specialities of its own.

Example:

```
main
├─ quran              field; repos under it
│  ├─ lead@quran
│  └─ lead@quranics
│     ├─ developer@quranics
│     └─ reviewer@quranics
├─ infrastructure     field and skill
│  └─ lead@config
├─ linguist           field; consulted, no repos under it
├─ engineer           skill; consulted, no repos under it
└─ lead@ai-tools      no companion covers it yet
```

**Recommended**

- Rank is a relation, not a kind of agent: `under = "<superior>"` in `[agents.<name>]`. "No agent is special" (agents note) holds: `main` is an ordinary agent at the root.
- One superior per agent, so reading rights (§3) and escalation (§5) each have one answer.
- Levels can be skipped: `lead@ai-tools` sits under `main` while no companion covers ai-tools. A companion has repos under it when its field spans them; the others have none and are consulted.
- `scope = "user"` in `~/.ai/ai.toml` makes an agent user-level: one agent, one thread. Without it an agent is repo-level, one per repo, as today: one defined in `~/.ai/ai.toml` exists in every repo (agents note, "Scope").
- A specialist's `under = "lead"` is the same in every repo, so it sits in `~/.ai/ai.toml`. A lead's superior differs per repo, so it sits in that repo's private settings (`.ai/local/ai.toml`): collaborators who share `ai.toml` have trees of their own.

## 2. Experts and knowledge

**Agreed**

- Knowledge is shared: no silos. Any agent may ask an expert, and may read the knowledge directly, at least parts of it.
- An expert answers from the knowledge store, `ai notes`, or asks the user.

**Recommended**

- A field is a subtree of `ai notes`, the topic tree at `~/.ai/notes` (`$AI_NOTES_DIR`, src/notes/cli.rs:30-38), such as `linguistics`. Its expert is its keeper. Every agent reads everything; each field has one keeper.
- Any agent adds notes to any field (`ai notes add`); the keeper curates them (`ai notes mv`, `ai notes link`). One curator keeps a field's topics coherent; open additions keep knowledge from waiting on one agent.
- The keeper answers what needs judgement rather than a lookup, and asks the user when the notes don't settle it.
- All knowledge is readable at first. A part is closed only for a stated reason, such as personal notes.

## 3. Reading

**Agreed**

- A higher agent reads the views of the agents below it (`ai agent view`, `zoom`, `grep`). A lower agent never reads a higher one. Siblings never read each other.
- The user reads every thread.
- `ai memory` is shared by every agent; the rule covers threads.

**Recommended**

- A superior reads its whole subtree: `main` reads `developer@quranics`.
- The rule is a guard, not a wall: every agent runs as the same OS user and can read the files. The CLI refuses a read when the calling session's agent, bound through `CLAUDE_CODE_SESSION_ID` (src/agent/claude.rs:18-20), is not above the target. The harness plugin refuses direct reads of other threads' files, as the `/ai recall` guard refuses writes (branch `feat/ai-recall`). It stops mistakes, not an agent set on reading.

## 4. Messages and the gate

**Agreed**

- Any agent may write to any agent: its siblings, the agents above and below it, and agents outside its branch, such as a developer asking `linguist`.
- The gate: every message between agents waits for the user's approval at first, including `main`'s and replies. The user can edit a message before approving it. The user's own messages pass no gate.
- An edited message is delivered as edited, and the edited copy also goes back to the sender's thread, so the sender's record holds what was delivered.

**Recommended**

- The user can reject a message; the reason goes back to the sender, which would otherwise wait for an answer that won't come.
- The recipient sees that a message carries the user's approval, and whether the user edited it.
- Only the user approves. The CLI refuses approve, edit and reject from any session bound to an agent, and the plugin guard blocks them: an agent that can approve empties the gate of meaning.
- A delivered message enters the recipient's thread as a turn opened by its sender, as a fork's report does today (src/agent/claude.rs:376-383). It arrives in an envelope naming the sender and the user's approval, with closing tags escaped (survey, "What the evidence says").
- Delivery in Claude Code (survey §2): the `ai` plugin submits an approved message as a turn of its own when the session is idle (`$.prompt.submit`), and blocks at the Stop hook when the message arrives during a turn. A stopped agent gets its messages at its next `resume` (survey §3).
- Standing approvals, a later layer, let routes the user names pass without waiting, such as `main` to `lead@ai-tools`. Until then every hop waits for the user: a message from `main` reaches `developer@quranics` after three approvals.

## 5. Disputes

**Agreed**

- When two agents disagree, a higher agent arbitrates, consulting the user.

**Recommended**

- The nearest common superior arbitrates: `developer@quranics` against `reviewer@quranics` goes to `lead@quranics`, `lead@quran` against `lead@quranics` to `quran`, two companions to `main`.
- Either side, or the user, escalates with a message to that superior. The ruling is a message like any other, so it passes the gate, where the user is consulted.

## 6. Changes to repos

**Agreed**

- A higher agent may change any repo under its responsibility.

**Recommended**

- It works on its own GitButler branch in that repo, as agents already share a checkout. Its commit messages carry the reasons: the repo's lead cannot read up, but reads the history.
- Its instructions say when to hand work down instead.

## 7. The user's powers and the desk

**Agreed**

- The user talks to any agent directly, at any time. `main` is a point of contact, not a required route.
- The user has powers no agent has, to intervene and edit. Approving and editing messages is the first.
- A TUI lists the messages awaiting the user's approval, and the user edits them there.

**Recommended**

- The powers: write to any agent; read any thread; approve, edit or reject any message. The CLI offers each one; the desk is where the user uses them.
- `ai desk` is the TUI, the name the backlog already uses. It is a terminal app run in a herdr pane and hosts no agent sessions; herdr runs those. Its first screen is the messages awaiting the user; then the agents, their status and views, and writing to any of them.

## 8. Names and addresses

**Agreed**

- A repo's lead is `lead@<repo>`.

**Recommended**

- A name lives at one level. Inside a repo a bare name means that repo's agent, since `ai agent` finds the store of the project at or above the working directory (src/agent/store.rs:138-140). A name used at both levels would change meaning with the directory: `main` typed in a repo would reach `main@<repo>`, never the user-level `main`. With one level per name a bare name has one meaning: user-level names resolve anywhere, repo-level names in their repo, and `ai` refuses a repo-level agent named like a user-level one.
- The software-engineering expert is `engineer`, distinct from the repos' `developer`s, whose instructions it can share.
- Another repo's agent is `<agent>@<project>`; a user-level agent is its bare name.
- A stored message names agents by project id, host and agent name, printed as a handle, so a rename doesn't strand its mail (survey, "Addressing").

## 9. Threads, memory and notes

**Agreed**

- Each agent's thread is its own detailed record. `ai memory` is the memory every agent shares.

**Recommended**

- Three stores, each answering one question:
  - a thread (`ai agent`): what did this agent do and say?
  - `ai memory`: what has the team decided and learned? Shared, dated, written on purpose.
  - `ai notes`: what is known about a topic? Shared, filed by topic, kept by experts.
- Once experts keep `ai notes`, knowledge belongs there, and `ai memory` holds decisions, rules and lessons.
- `ai memory` keeps its name until that line is settled. `ai memory note` and `ai notes` already share a word, so both names are settled together. Not `history`, which describes what threads hold.

## 10. Storage

**Agreed**

- A repo-level agent's thread lives in the repo's private store, `.ai/local/agents/threads/<name>/` (src/project.rs:149, src/agent/store.rs:32, :128-130).

**Recommended**

- A thread lives in its agent's scope: a user-level agent's in `~/.ai` (src/config.rs:45-47), beside memory and notes, as `~/.ai/agents/threads/<name>/`.
- Mail, the survey's choice B adapted to the gate: the recipient's thread holds an `inbox/` with one append-only file per writer, `inbox/<writer>.jsonl`. A sender appends its messages there. The user appends the gate's decisions (approved; edited, with the new text; rejected, with the reason) and the user's own messages. No file has two writers, so a synced store cannot conflict (survey, SAMP). State is a projection of the events: held until the user decides, delivered once the message is an item of the recipient's thread.
- The edited copy goes back to the sender as a message from the user, in the sender's inbox.
- A registry of the user's projects in `~/.ai` lets the desk find every inbox and agents write across repos. No such registry exists.

## 11. Layers

**Recommended**, each usable on its own:

1. Mail with the gate, CLI only, in one repo: send, hold, approve, edit, reject, deliver at the next turn boundary, reply.
2. `ai desk`, shipped with mail: no agent uses mail before the desk exists.
3. The tree inside one repo: `lead` over its specialists, the reading guard, escalation.
4. User-level agents: `main` and the companions, their threads in `~/.ai`, the project registry, mail across repos.
5. Standing approvals.
