# Agent team

Author: Claude Code (Claude Opus 5.5)

Design for a team of agents under the user: the tree of agents, who reads whom, messages between agents held for the user's approval, their delivery, and the desk where the user approves them. It builds on `20261024T084514--agents.md` ("the agents note") and `20261029T193051--agent-messaging-survey.md` ("the survey"); identity and enforcement are designed in `20261030T200814--agent-identity-and-enforcement.md` ("the identity note"), and where everything is stored in `20261021T224734--storage.md` ("the storage note"). Of this design only `reports-to` and its read grants are built; mail, its gate and the desk wait for the sandboxed launch (§11). **Agreed** marks the user's decisions, **Recommended** proposals awaiting the user's confirmation; the open questions close the note.

## Principle

**Agreed**

- Code enforces permissions: who reads which thread, and who approves mail. Workflows, such as arbitration, escalation and passing the user's intent down, are messages between agents; the CLI has no feature for them.
- Nothing guesses. A name resolves by one rule or is an error naming it (§8).
- A broken part fails only what needs it. A broken hierarchy fails the commands that read the hierarchy, never `ai memory` or an agent's own commands (built: src/config.rs, `Settings::hierarchy`).
- User-level details never enter a project repo, since a project may be published. Most of the agents' setup is the user's own, in `~/ai` (storage note).

## 1. The tree

**Agreed**

- `root` is the user's single point of contact: one agent, at user level.
- Four levels:
  1. `root`, at user level.
  2. Companions, at user level, with specialised roles, such as `quran`, `linguist` or `infrastructure`.
  3. Each project's main agent, `main`, addressed as `<project>.main`.
  4. Specialists in each project, such as `developer` and `reviewer`, some under others, such as `developer-hopf` under `developer`.
- A user-level agent works across repos; a project's agent works in one.
- An agent may have several superiors, so the hierarchy is a graph, not a tree.
- An agent's superiors are a list in its table: `reports-to = [...]`.
- The user's intent and priorities pass down the hierarchy, level by level.
- Every agent is well-rounded, with specialities of its own.

Example:

```
root
├─ quran              projects under it
│  ├─ quran.main
│  └─ quranics.main
│     ├─ quranics.developer
│     │  └─ quranics.developer-hopf
│     └─ quranics.reviewer
├─ infrastructure     projects under it
│  └─ config.main
├─ linguist           no projects under it
├─ engineer           no projects under it
└─ ai-tools.main      no companion covers it yet
```

**Agreed:** where the hierarchy is written follows the leak rule (Principle):
- The tracked `ai.toml` holds only the project's own hierarchy, in bare names: `[agents.developer] reports-to = ["main"]`.
- A link up out of the project, such as `main` reporting to the user-level `quran`, sits in the project's private settings in `~/ai`, or in the user's own `ai.toml`, never in the tracked file.

**Recommended**

- Rank is a relation, not a kind of agent: "No agent is special" (agents note) holds, and `root` is an ordinary agent at the top.
- `ai` refuses a cycle of superiors (built: `Settings::hierarchy`).
- Read rights follow from rank: `ai` compiles the hierarchy into each agent's read grants when it launches the agent (identity note, recommendations 1 and 5; built: `Hierarchy::below`).
- Levels can be skipped: `ai-tools.main` sits under `root` while no companion covers ai-tools. A companion has projects under it when its role spans them; the others have none.

## 2. Roles

**Agreed**

- Agents get specialised roles, not necessarily tied to a repo or project, and agents may sit above them. Mail and the desk must not block that; nothing in them depends on what a role is or what an agent knows.

## 3. Reading

**Agreed**

- A higher agent reads the views of the agents below it (`ai agent view`, `zoom`, `grep`). A lower agent never reads a higher one. Siblings never read each other.
- Reading a thread is extremely privileged. The rule is enforced, never left to agents' instructions.
- The user reads every thread.
- `ai memory` is shared by every agent; the rule covers threads.

**Recommended**

- A superior reads every agent below it, through any number of levels: `root` reads `quranics.developer`.
- How the rule is enforced is the identity note's recommendation.

## 4. Messages and the gate

**Agreed**

- Mail, its gate and delivery wait for the sandboxed launch (§11). Until then Claude Code's own messaging (`ListAgents`, `SendMessage`) carries messages between Claude sessions on one machine, which `ai` neither stores nor gates (`20261108T104659--claude-code-cross-session-messaging.md`). With the sandbox, `ai`, outside it, delivers approved mail into each session.
- Any agent may write to any agent: its siblings, the agents above and below it, and agents outside its branch, such as a developer asking `linguist`.
- The gate: every message between agents waits for the user's approval at first, including `root`'s and replies. The user can edit a message before approving it. The user's own messages pass no gate.
- One approval per message covers its sending and its delivery together.
- An edited message is delivered as edited, and the edited copy also goes back to the sender's thread, so the sender's record holds what was delivered.
- Delivery in Claude Code: the `ai` plugin submits an approved message as a turn of its own (`$.prompt.submit`). Submitted while the agent is in a turn, it queues and runs once that turn ends (`20261030T202150--claude-code-mail-delivery.md`). A stopped agent gets its messages at its next `resume` (survey §3).

**Recommended**

- The user can reject a message; the reason goes back to the sender, which would otherwise wait for an answer that won't come.
- The recipient sees that a message carries the user's approval, and whether the user edited it.
- How a message proves its sender is the identity note's recommendation.
- Only the user approves, edits or rejects: an agent that can approve empties the gate of meaning. How that is enforced is the identity note's recommendation.
- A delivered message enters the recipient's thread as a turn opened by its sender, as a fork's report does today (src/agent/claude.rs:376-383). It arrives in an envelope naming the sender and the user's approval, with closing tags escaped (survey, "What the evidence says").
- Standing approvals, a later layer, let routes the user names pass without waiting, such as `root` to `ai-tools.main`. Until then every message waits: intent passed from `root` down to `quranics.developer` level by level takes three messages and three approvals; `root` writing to it directly takes one.

## 5. Disputes

**Agreed**

- When two agents disagree, they write to a superior they share, which arbitrates, consulting the user. It is a use of messaging (Principle): the ruling is a message like any other and passes the gate. The CLI has no arbitration feature and no rule for which superior arbitrates.

## 6. Changes to repos

**Agreed**

- A higher agent may change any repo under its responsibility.

**Recommended**

- It works on its own GitButler branch in that repo, as agents already share a checkout. Its commit messages carry the reasons: the project's `main` cannot read up, but reads the history.
- Its instructions say when to hand work down instead.

## 7. The user's powers and the desk

**Agreed**

- The user talks to any agent directly, at any time. `root` is a point of contact, not a required route.
- The user has powers no agent has, to intervene and edit. Approving and editing messages is the first.
- The desk lists the messages awaiting the user's approval, and the user approves and edits them there.
- The desk is Emacs, through emx. Emacs packages (magit, transient, vertico, buffers) give the editing, review, replies, completion and flows a TUI of `ai`'s own would have to build.
- emx only shows what `ai` returns. `ai` commands give a structured output format (for example `--json`), so `ai` works without Emacs and other UIs can use the same commands.
- `ai` supports both ways of running Claude: Claude Code's terminal UI (herdr, an Emacs terminal buffer) and agent-shell over ACP.

**Recommended**

- The powers: write to any agent; read any thread; approve, edit or reject any message. The CLI offers each one; the desk is where the user uses them.
- The desk opens on the messages awaiting the user; then the agents, their status and views, and writing to any of them.

## 8. Names and addresses

**Agreed**

- Each project's main agent is `main`; the user-level main is `root`.
- Mail is `ai agent mail`, with `ai mail` as an alias. The gate's verbs are `approve`, `edit` and `reject`.
- An agent's address is `<project>.<agent>`, such as `quranics.main`. It is also the agent's Claude Code session name, which can't hold `@` (`20261108T104659--claude-code-cross-session-messaging.md`). Claude Code completes a typed `@` by prefix, so `@quranics.` lists a project's agents.
- An address splits at its last dot: agent names hold no dots, project names may (`quran.thayyil.net.main`).
- The address is flat: the hierarchy stays in `reports-to`. A specialist under another is named with `-`: `quranics.developer-hopf`, which `@quranics.developer` completes beside `quranics.developer`.
- A bare name resolves when exactly one agent matches it, in the project, then at user level. The full address only disambiguates; an ambiguous bare name is an error naming the addresses it matches.
- A name that resolves to no agent is an error naming it.
- A tracked `ai.toml` holds only bare names of its own project's agents, and refuses full addresses and user-level agents: they are user-level details.

**Recommended**

- One name may live at both levels: a user-level `linguist` and `quranics.linguist` are two agents. No name is reserved, and `ai` refuses nothing for a clash between levels; where a bare name matches both, the full address names one (open question 7).
- At the command line, the project is the one at or above the working directory, as `ai` finds it today (src/agent/store.rs); outside every project, a bare name looks only at user level.
- A stored message names agents by project id, host and agent name, printed as an address, so a rename doesn't strand its mail (survey, "Addressing").

Today's `reports-to` check (src/config.rs) resolves names against the tables of every file merged, and accepts a superior any file defines. Resolution by this rule replaces it; not built.

## 9. Threads and memory

**Agreed**

- Each agent's thread is its own detailed record. `ai memory` is the memory every agent shares.

## 10. Storage

**Agreed** (storage note):

- `~/ai`, a git repository the user keeps like `config`, holds every thread, user-level and every project's, each project's private settings, and memory, its notes and summary trees. `~/.ai` holds what belongs to this machine and never goes in git: the archive's disk copy, locks, logs, caches, this machine's settings. The store holds the archive's raw bytes, encrypted, off the machine.
- `<repo>/.ai/local` stays, ignored by the project's git, for the project's private working data (evals, datasets); only threads and private settings leave it. `<repo>/ai` holds the project's parts that can be public, and the tracked `ai.toml` stays in the repo.
- Agents never touch git: a sandbox gets its own thread's files read-write and its subordinates' read-only, never `~/ai/.git`. Only `ai` outside every sandbox commits.
- `~/ai/projects/` lists every project, so `ai` finds every inbox and agents write across projects with no separate registry.
- Mail: each agent appends its messages only to its own outbox. `ai`, run by the user from the desk outside every sandbox, writes each approved message, as approved or edited, into the recipient's inbox, which the recipient reads but cannot write; the user's own messages go straight to the inbox. No file has two writers, so a synced store cannot conflict (survey, SAMP), and an outbox's owner is the sender of its messages (identity note, recommendation 2). State is a projection of the events: held until the user decides, delivered once the message is an item of the recipient's thread.

**Recommended**

- The edited copy goes back to the sender as a message from the user, in the sender's inbox.
- A thread's outbox and inbox sit beside its thread in `~/ai`, at paths the sandbox binds one by one: the outbox read-write, the inbox read-only.

## 11. Layers

**Recommended**, each usable on its own:

1. Storage: threads and private settings in `~/ai`, machine-only files in `~/.ai`, one conversion of today's stores (storage note).
2. Sandboxed launch: `ai resume` starts each agent in its own sandbox, with access to its own thread only. It comes before mail, since sender identity and the gate rest on it (identity note, "What this changes in agreed design").
3. Mail with the gate, CLI only, in one project: send, hold, approve, edit, reject, deliver at the next turn boundary, reply.
4. The desk in Emacs, through emx, shipped with mail: no agent uses mail before the desk exists.
5. The tree inside one project: `main` over its specialists, read grants compiled from rank.
6. User-level agents: `root` and the companions, their threads in `~/ai`, mail across projects.
7. Standing approvals.

**Agreed:** layers 3 and 4 wait for layer 2. Until then agents write to each other through Claude Code's own messaging, and `ai resume` names each Claude session by its address (§8) so they can.

## Open questions

1. The host part of an address, for mail across machines, given `<project>.<agent>`; it may wait for a cross-host transport (survey question 1).
2. Waking an idle agent through herdr's `agent prompt` (survey question 5).
3. How a user-level agent starts: its harness and working directory, given that Claude Code finds a session only from the directory it ran in (agents note §4).
4. What an `[agents.<name>]` table in the user's own `ai.toml` defines. Today it defines an agent in every project, each with its own thread (agents note, "Scope"). Under §8's rule a bare name in the user's files is a user-level agent. Either such tables define user-level agents only, and a specialist present in every project is defined by each project, or a table marked as a template stays a definition every project takes up, its names resolving in each project that takes it.
5. The standing-approval rules (§4).
6. Which powers beyond messages the desk offers, such as stopping or redirecting an agent, or editing its thread or instructions (§7).
7. How a user-level agent's address is written: `~.<agent>`, if Claude Code session names accept `~` (unchecked).

The storage note's open questions cover memory's history, interrupted writes, renamed projects, conversion backups and snapshot timing; the identity note's cover the agents' login.
