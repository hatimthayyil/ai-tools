# Agent team

Author: Claude Code (Claude Opus 5.5)

Design for a team of agents under the user: the tree of agents, who reads whom, messages between agents held for the user's approval, their delivery, and the TUI where the user approves them. It builds on `20261024T084514--agents.md` ("the agents note") and `20261029T193051--agent-messaging-survey.md` ("the survey"); identity and enforcement are designed in `20261030T200814--agent-identity-and-enforcement.md` ("the identity note"). Nothing here is built. **Agreed** marks the user's decisions, **Recommended** proposals awaiting the user's confirmation; the open questions close the note.

## Principle

**Agreed**

- Code enforces permissions: who reads which thread, and who approves mail. Workflows, such as arbitration, escalation and passing the user's intent down, are messages between agents; the CLI has no feature for them.

## 1. The tree

**Agreed**

- `main` is the user's single point of contact: one agent, at user level.
- Four levels:
  1. `main`, at user level.
  2. Companions, at user level, with specialised roles, such as `quran`, `linguist` or `infrastructure`.
  3. A lead in each repo, `lead@<repo>`.
  4. Specialists in each repo, such as `developer` and `reviewer`.
- A user-level agent works across repos; a repo-level agent works in one.
- An agent may have several superiors, so the hierarchy is a graph, not a tree.
- The user's intent and priorities pass down the hierarchy, level by level.
- Every agent is well-rounded, with specialities of its own.

Example:

```
main
├─ quran              repos under it
│  ├─ lead@quran
│  └─ lead@quranics
│     ├─ developer@quranics
│     └─ reviewer@quranics
├─ infrastructure     repos under it
│  └─ lead@config
├─ linguist           no repos under it
├─ engineer           no repos under it
└─ lead@ai-tools      no companion covers it yet
```

**Recommended**

- Rank is a relation, not a kind of agent: a list of an agent's superiors in `[agents.<name>]`. "No agent is special" (agents note) holds: `main` is an ordinary agent at the root. The key's name is open: `reports-to = [...]` (identity note, recommendation 5) or `superiors = [...]`.
- `ai` refuses a cycle of superiors.
- Read rights follow from rank: `ai` compiles the hierarchy into each agent's read grants when it launches the agent (identity note, recommendations 1 and 5).
- Levels can be skipped: `lead@ai-tools` sits under `main` while no companion covers ai-tools. A companion has repos under it when its role spans them; the others have none.
- `scope = "user"` in `~/.ai/ai.toml` makes an agent user-level: one agent, one thread. Without it an agent is repo-level, one per repo, as today: one defined in `~/.ai/ai.toml` exists in every repo (agents note, "Scope").
- A specialist's superiors are the same in every repo, so they sit in `~/.ai/ai.toml`. A lead's differ per repo, so they sit in that repo's private settings (`.ai/local/ai.toml`): collaborators who share `ai.toml` have trees of their own.

## 2. Roles

**Agreed**

- Agents get specialised roles, not necessarily tied to a repo or project, and agents may sit above them. Mail and the desk must not block that; nothing in them depends on what a role is or what an agent knows.

## 3. Reading

**Agreed**

- A higher agent reads the views of the agents below it (`ai agent view`, `zoom`, `grep`). A lower agent never reads a higher one. Siblings never read each other.
- Reading a thread is extremely privileged. The rule is enforced, never left to agents' instructions.
- The user reads every thread.
- `ai memory` is shared by every agent; the rule covers threads.

**Recommended**

- A superior reads every agent below it, through any number of levels: `main` reads `developer@quranics`.
- How the rule is enforced is the identity note's recommendation.

## 4. Messages and the gate

**Agreed**

- Any agent may write to any agent: its siblings, the agents above and below it, and agents outside its branch, such as a developer asking `linguist`.
- The gate: every message between agents waits for the user's approval at first, including `main`'s and replies. The user can edit a message before approving it. The user's own messages pass no gate.
- One approval per message covers its sending and its delivery together.
- An edited message is delivered as edited, and the edited copy also goes back to the sender's thread, so the sender's record holds what was delivered.
- Delivery in Claude Code (survey §2): the `ai` plugin submits an approved message as a turn of its own when the session is idle (`$.prompt.submit`), and blocks at the Stop hook when the message arrives during a turn. A stopped agent gets its messages at its next `resume` (survey §3).

**Recommended**

- The user can reject a message; the reason goes back to the sender, which would otherwise wait for an answer that won't come.
- The recipient sees that a message carries the user's approval, and whether the user edited it.
- How a message proves its sender is the identity note's recommendation.
- Only the user approves, edits or rejects: an agent that can approve empties the gate of meaning. How that is enforced is the identity note's recommendation.
- A delivered message enters the recipient's thread as a turn opened by its sender, as a fork's report does today (src/agent/claude.rs:376-383). It arrives in an envelope naming the sender and the user's approval, with closing tags escaped (survey, "What the evidence says").
- Standing approvals, a later layer, let routes the user names pass without waiting, such as `main` to `lead@ai-tools`. Until then every message waits: intent passed from `main` down to `developer@quranics` level by level takes three messages and three approvals; `main` writing to it directly takes one.

## 5. Disputes

**Agreed**

- When two agents disagree, they write to a superior they share, which arbitrates, consulting the user. It is a use of messaging (Principle): the ruling is a message like any other and passes the gate. The CLI has no arbitration feature and no rule for which superior arbitrates.

## 6. Changes to repos

**Agreed**

- A higher agent may change any repo under its responsibility.

**Recommended**

- It works on its own GitButler branch in that repo, as agents already share a checkout. Its commit messages carry the reasons: the repo's lead cannot read up, but reads the history.
- Its instructions say when to hand work down instead.

## 7. The user's powers and the desk

**Agreed**

- The user talks to any agent directly, at any time. `main` is a point of contact, not a required route.
- The user has powers no agent has, to intervene and edit. Approving and editing messages is the first.
- A TUI lists the messages awaiting the user's approval, and the user edits them there.

**Recommended**

- The powers: write to any agent; read any thread; approve, edit or reject any message. The CLI offers each one; the desk is where the user uses them.
- `ai desk` is the TUI, the name the backlog already uses. It is a terminal app run in a herdr pane and hosts no agent sessions; herdr runs those. Its first screen is the messages awaiting the user; then the agents, their status and views, and writing to any of them.

## 8. Names and addresses

**Agreed**

- A repo's lead is `lead@<repo>`.
- Mail is `ai agent mail`, with `ai mail` as an alias. The gate's verbs are `approve`, `edit` and `reject`.

**Recommended**

- A name lives at one level. Inside a repo a bare name means that repo's agent, since `ai agent` finds the store of the project at or above the working directory (src/agent/store.rs:138-140). A name used at both levels would change meaning with the directory: `main` typed in a repo would reach `main@<repo>`, never the user-level `main`. With one level per name a bare name has one meaning: user-level names resolve anywhere, repo-level names in their repo, and `ai` refuses a repo-level agent named like a user-level one.
- Another repo's agent is `<agent>@<project>`; a user-level agent is its bare name.
- A stored message names agents by project id, host and agent name, printed as a handle, so a rename doesn't strand its mail (survey, "Addressing").

## 9. Threads and memory

**Agreed**

- Each agent's thread is its own detailed record. `ai memory` is the memory every agent shares.

## 10. Storage

**Agreed**

- A repo-level agent's thread lives in the repo's private store, `.ai/local/agents/threads/<name>/` (src/project.rs:149, src/agent/store.rs:32, :128-130).
- Mail, the survey's choice B adapted to the gate: the recipient's thread holds an `inbox/` with one append-only file per writer, `inbox/<writer>.jsonl`. A sender appends its messages there. The user appends the gate's decisions (approved; edited, with the new text; rejected, with the reason) and the user's own messages. No file has two writers, so a synced store cannot conflict (survey, SAMP). State is a projection of the events: held until the user decides, delivered once the message is an item of the recipient's thread.

**Recommended**

- The identity note proposes replacing B with per-sender outboxes that the desk delivers into each recipient's inbox; it is that note's open question 1.
- A thread lives in its agent's scope: a user-level agent's in `~/.ai` (src/config.rs:45-47), beside memory, as `~/.ai/agents/threads/<name>/`.
- The edited copy goes back to the sender as a message from the user, in the sender's inbox.
- A registry of the user's projects in `~/.ai` lets the desk find every inbox and agents write across repos. No such registry exists.

## 11. Layers

**Recommended**, each usable on its own:

1. Sandboxed launch: `ai resume` starts each agent in its own sandbox, with access to its own thread only. It comes first, since sender identity and the gate rest on it (identity note, "What this changes in agreed design").
2. Mail with the gate, CLI only, in one repo: send, hold, approve, edit, reject, deliver at the next turn boundary, reply.
3. `ai desk`, shipped with mail: no agent uses mail before the desk exists.
4. The tree inside one repo: `lead` over its specialists, read grants compiled from rank.
5. User-level agents: `main` and the companions, their threads in `~/.ai`, the project registry, mail across repos.
6. Standing approvals.

## Open questions

1. The address grammar and its host part: `agent@project@host`, the survey's `agent@project/host`, or another; the host part may wait for a cross-host transport (survey question 1).
2. The project registry: where it lives and how a project joins it (survey question 3).
3. Waking an idle agent through herdr's `agent prompt` (survey question 5).
4. How a user-level agent starts: its harness and working directory, given that Claude Code finds a session only from the directory it ran in (agents note §4).
5. The standing-approval rules (§4).
6. Which powers beyond messages the desk offers, such as stopping or redirecting an agent, or editing its thread or instructions (§7).
7. Repo `.ai` directories as submodules or subtrees of a user-level repository: parked.

Identity, enforcement, the mail store's replacement and the name of the superiors key are the identity note's open questions.
