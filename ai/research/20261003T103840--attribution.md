# Attribution: AI vs human vs both

Research for `ai`. No code changed. Date: 2026-10-03. Sources: local `git-ai` checkout (`/hatimthayyil/code/git-ai`, v1.7.6, `specs/git_ai_standard_v3.0.0.md`), the git-ai 1.7.5 install on this machine, and this repo's own `refs/notes/ai`.

## Summary

**git-ai is already installed and already attributing this repo.** Nix profile, trace2 daemon running (`git-ai bg run`, ~34 MB RSS), Claude Code `PreToolUse`/`PostToolUse` hooks in `~/.claude/settings.json`. Every commit in `main` has a note under `refs/notes/ai`. For example, `76b123c` attributes `ai/research/memory-git-ref.md` lines 1–381 to session `s_3eef8379439ce5`, which is Claude Code session `d3810a82-…`. That is the same id `ai memory` plans to store in its `session` field.

**Recommendation: keep git-ai as the capture layer, and treat the Git AI Standard v3 note as the canonical line-attribution record.** `ai` reads those notes natively and does not write them. `ai` adds what git-ai lacks: workspace policy (`my/` is human-only), the AI-generated vs AI-assisted classification from `my/glossary.md`, a review signal, and links between notes and memory.

Don't build a capture engine of our own. Most of git-ai's 175k lines of Rust deal with the hard part: following attribution through rebase, squash, stash, reset, amend and cherry-pick, driven asynchronously by trace2. Our requirements don't justify redoing that. The note format is small and open. If git-ai is ever abandoned, a native writer can replace it with no data migration.

| Question | Answer |
|---|---|
| Adopt, implement the standard, or build our own? | **Adopt git-ai for capture. Implement a v3 *reader* natively.** Build no capture of our own. |
| Enforce "AI must not edit `my/`"? | Attribution can only *verify* after the fact. *Enforce* with harness permissions (Claude Code `deny`), then verify with `ai attrib check` (hook/CI) over notes and working state. |
| AI-generated vs AI-assisted per line/file? | Measurable per line at HEAD: AI-attested line never touched by a human since vs AI line later edited. "Reviewed" has no signal today and needs one (open question). |
| Memory provenance link? | Shared key: the harness session id (`agent_id.id` = `$CLAUDE_CODE_SESSION_ID`). Note `s_` id = `sha256("claude:"+id)[0..14]`. Memory `head` = commit. A join, not a copy. |
| DB (platform-db)? | git notes stay the source of truth. A DB may *index* notes (commit → file → lines → session) for queries; it must stay a derived cache. |

## How git-ai works

### Data: Git AI Standard v3 (`authorship/3.0.0`)

- **Ref.** One note per commit under `refs/notes/ai` (MUST NOT use `refs/notes/commits`). Stashes get notes under `refs/notes/ai-stash`.
- **Note format.** Attestation section, a `---` line, then JSON metadata. Splitting it this way lets blame read only the top part.
  ```
  src/main.rs
    s_c9883b05a2487d::t_9f8e7d6c5b4a32 1-10,15-20
    h_31dce776f88375 42-50
  ---
  {"schema_version":"authorship/3.0.0","base_commit_sha":"…","prompts":{},
   "sessions":{"s_c988…":{"agent_id":{"tool":"claude","id":"<conv id>","model":"…"},"human_author":"…"}},
   "humans":{"h_31dc…":{"author":"Name <email>"}}}
  ```
- **Keys.**
  - `s_<14hex>` = `sha256("<tool>:<conversation_id>")[0..14]`. It is stable per agent session.
  - `::t_<14hex>` is a random trace id, one per checkpoint (one edit).
  - `h_<14hex>` = `sha256("Name <email>")`, a "known human".
  - Bare 16-hex keys are legacy, pre-1.4.
- **Lines.** 1-indexed ranges, valid only against the file at that commit. Lines with no key are **untracked** (unknown), which is not the same as human.
- **Metadata.** A session carries `agent_id{tool,id,model}`, `human_author` and `custom_attributes`. Line stats (`total_additions`, `accepted_lines`, `overriden_lines`) live only on legacy prompt records. Newer stats come from the local metrics DB.
- **Prompts and transcripts** are never in notes (`messages` was removed in 1.3.4). They live in local SQLite (`~/.git-ai/internal/transcripts-db`), redacted for secrets (`src/daemon/transcript_redaction.rs`, `src/authorship/secrets.rs`). `prompt_storage` is one of:
  - `default`: uploaded via CAS API only when logged in to Git AI cloud;
  - `notes`: redacted, put in the notes;
  - `local`: never leaves the machine.
- **Spec stance.** Any tool that writes conforming notes is compliant. The spec itself recommends integrating with git-ai rather than implementing it. Stable surface: the `s_`/`t_`/`h_` prefixes, `::`, and the overall note shape. Id length may change. v4 will rename `overriden_lines`.

### Capture

1. **Agent hooks.** `git-ai install-hooks` writes per-agent hook config. For Claude Code that is `PreToolUse` and `PostToolUse` with matcher `*` running `git-ai checkpoint claude --hook-input stdin`. Presets exist for about 15 agents (Codex, Cursor, Copilot, OpenCode, Gemini, …) and an IDE extension.
   - The pre-edit checkpoint snapshots the file, so whatever changed since then is *untracked*.
   - The post-edit checkpoint attributes the diff to the AI session.
   - Bash-created files are attributed by stat diffing plus recovery heuristics.
   - Working state goes to `.git/ai/working_logs/<base>/`.
2. **Humans.**
   - A `known_human` checkpoint fires only from IDE extensions that watch typing.
   - Otherwise a human edit shows up as an untracked gap.
   - **Caveat seen in this repo.** `attribution_recovery.rs::recover_remaining_as_known_human` labels all unknown lines `h_<committer>` when a commit has no AI attestation. Commits `947d39a` and `767911b` got `h_` labels this way, with no `KnownHuman` checkpoint in their working logs. So `h_` means "observed typing *or* inferred from the committer". It is not proof.
3. **Daemon, not wrapper.**
   - Install sets global `trace2.eventTarget=af_unix:stream:~/.git-ai/internal/daemon/trace2.sock`.
   - git streams trace2 events to the daemon. The daemon orders them per repo family and pins ref transitions exactly through reflog cursors; when it isn't exact, it fails closed.
   - After the fact it writes notes on commit and migrates them across rewrites.
   - No git hooks, and no added latency on git commands.
   - The binary *can* act as a `git` proxy (argv[0]), and the Nix `default` package ships that wrapper. This machine uses plain git plus trace2.
   - An "untraced commit fixup" covers commits made while the daemon was down, or by clients without trace2 (JGit, libgit2), using reflog evidence.
4. **Rewrites.**
   - Supported: rebase (including reorder, squash, split, drop, edit), cherry-pick, `merge --squash`, `reset --soft/--mixed`, stash/pop, amend, pull.
   - Not supported: `git mv` renames, filter-repo, replace.
   - Forge squash/rebase-merge needs git-ai's CI action.
5. **Sync.**
   - On push, the daemon fetches `+refs/notes/ai` into a tracking ref, merges with `git notes merge -s ours` (falling back to a manual merge), then pushes without force, with retries.
   - An HTTP notes backend is an alternative.
6. **Extension point.** `git_ai_hooks.post_notes_updated` runs shell commands with a JSON array of the new notes on stdin. It is async and detaches after 3 s.

### Gaps relevant to us, seen locally

- **Subagents are not distinguished.**
  - This subagent and its coordinator share session `d3810a82-…`, so notes put both under one `s_`.
  - The tool-use id and the parent-transcript detection stay in the local metrics DB, not in the note.
- **`model` is sometimes `"unknown"`** (`76b123c`). It is extracted from the transcript, not from env.
- **Deletions are not attested.** A note covers lines present at a commit. An AI deleting lines in `my/` leaves no attestation.
- **No review concept.** `human_author` means "who steered the session", not "who reviewed".

## Options

| | A. Adopt git-ai (companion) + native v3 reader | B. Implement the standard natively (writer + reader) | C. Own format/tool | D. Trailers only (`Co-Authored-By`/`Assisted-by`) |
|---|---|---|---|---|
| Capture accuracy | line-level, per edit, ~15 agents | line-level only if we rebuild checkpoints + rewrite tracking | whatever we build | commit-level only |
| Survives rebase/squash/stash | yes (daemon) | only if we rebuild ~the daemon | same | yes (in message), but coarse and lies after squash |
| Effort | small: parser + policy + stats | very large | very large | trivial; already done (Claude Code `attribution`) |
| Interop | git-ai blame, IDE/magit plugins, Teams, Agent Trace bridges | same format, so yes | none | universal but shallow |
| Footprint | daemon, global trace2, agent hook edits, telemetry to disable | ours to choose | ours | none |
| Workspace policy, AI-gen vs assisted, memory link | ours, on top | ours | ours | not possible |
| Lock-in | low: open format, notes in our repo | none | ours | none |
| Verdict | **recommended** | fallback if git-ai dies or diverges | rejected (reinvents, no interop) | keep as a coarse complement |

Notes:

- A over B. The value is in capture and rewrite tracking, not in the note format. B means re-deriving git-ai's daemon. That contradicts "use established libraries" and "don't reimplement common functionality".
- Native reader rather than parsing `git-ai show` output. The note format is a declared stable API, while CLI output is not. `ai` already plans `gix` (memory design), and reading `refs/notes/ai` is one tree lookup per commit. `ai` features then keep working where git-ai isn't installed: CI, a fresh clone with fetched notes.
- Keep trailers. They are the forge-visible, squash-surviving, coarse signal, and this repo already emits `Co-Authored-By: Claude …`. Notes are the precise signal.

## Proposed integration design for `ai`

Grow it in layers. Each layer works on its own.

### Layer 0: configure git-ai (no code)

- `git-ai config set prompt_storage local`
- Turn OSS telemetry off.
- Turn `token_usage_metrics` and `daemon_log_upload` off unless wanted.
- Add the `refs/notes/ai` fetch refspec once a remote exists. git-ai pushes notes on `git push`.
- Pin through Nix (`packages.minimal`, or `unwrapped` plus trace2 config), with auto-update off. Already off here.

### Layer 1: prevention, enforced by the harness

- Claude Code `permissions.deny`: `Edit(my/**)`, `Write(my/**)`, `NotebookEdit(my/**)`.
- Add a `PreToolUse` Bash guard (`ai guard`) that rejects commands whose write targets resolve under `my/`. This is best-effort, because Bash is open-ended.
- Codex and others: their equivalent sandbox write-deny.
- This is the only real *enforcement*. Attribution can't stop an edit.

### Layer 2: `ai attrib` (new crate, reads v3 notes)

- `ai attrib check [<range>|--staged]`: verify the policy.
  - Policy, kept minimal, in `ai/policy` or git config:
    - `my/**`: no `s_` attestation (or legacy key) in any commit in range.
    - Also no uncommitted AI checkpoint on `my/**`: read `.git/ai/working_logs/<HEAD>/` or `git-ai status --json`.
    - Also no change at all to `my/**` in a commit whose note has *any* `s_` key, unless the `my/` lines are `h_`. This catches AI deletions and Bash edits that weren't attested.
  - Runs as a Claude Code `Stop` hook, a pre-push hook and in CI. Exits nonzero with file, lines, session and commit.
- `ai attrib stats [<path>…] [--at <rev>]`: per-line class at a revision, rolled up per file and per workspace:
  - `ai-generated`: last touched by an `s_` attestation, and no later human or untracked change to that line;
  - `ai-assisted`: the line or its file has both AI and human or untracked history (AI line later edited, human line later rewritten by AI);
  - `human`: `h_` only; flagged `inferred` when it came from committer recovery;
  - `unknown`: untracked.
  - File class: `ai-generated` if every line is; `human` if no AI line ever; else `ai-assisted`.
  - Implementation: a blame-style walk (`gix` blame, or `git blame --porcelain`) mapping each line to its origin commit, plus that commit's note. Earlier notes on the line's history decide "edited after AI".
- `ai attrib why <file>:<line>`: commit, session (`tool`, `model`, harness id), the memories with that session id, and the transcript path if local.

### Layer 3: memory link

- Memory record fields (see `20261003T091838--memory-git-ref.md`) already include `head`, `agent`, `model` and `session`.
  - Use the *raw* harness session id in both places.
  - Derive `s_` when joining: `sha256("<tool>:<id>")[0..14]`, with `tool` mapped from `agent` (`claude-code…` to `claude`).
- Commit → memory: `ai memory grep --session <id>` for every session in the commit's note.
- Memory → code: `head`, plus a scan of `refs/notes/ai` for notes whose sessions include the memory's session. Cheap: notes are small and the scan is bounded by commit range.
- Optional: an `ai memory note --ref <file>:<lines>` field for explicit pointers. Defer until someone needs it.
- The memory ref (`refs/ai/memory`) is written by gix, which emits no trace2, so git-ai never attributes memory commits. Good: memory provenance is inline in its records.

### Layer 4: review signal

- The glossary splits AI-generated from AI-assisted on "human review or editing". Editing is visible in notes. Review is not.
- Simplest durable option: a human-added `Reviewed-by: Name <email>` trailer on the commit (kernel convention). `ai attrib stats` then counts AI lines in reviewed commits as `ai-assisted`.
- Alternative: an `ai review <rev>` command writing `refs/notes/ai-review`. More precise (it can target a range of commits after the fact) but adds a ref.

### Platform DB (separate research: `ai/research/*---platform-db.md`, `*---memory-db.md`)

- Notes remain canonical in git, so they travel with the repo and survive without the DB.
- The DB, if adopted, ingests notes, either through git-ai's `post_notes_updated` hook or by a scan of `refs/notes/ai`. It does so into `commit`, `file_range`, `session`, `agent` and `memory` tables or records, to make `why`/`stats`/cross-repo queries fast.
- Shared identifiers to standardise across memory, attribution and the DB: `session` (raw harness id), `agent` (`tool` + version), `model` (models.dev `provider/model` per Agent Trace), `commit`, `origin` (clone).
- Subagent identity: needs `parent_session` + `tool_use_id`. git-ai keeps these only in its metrics DB, so the platform should record its own when it orchestrates agents.

## Prior art

- **Git AI Standard v3 / git-ai.** Described above. https://github.com/git-ai-project/git-ai , spec: https://github.com/git-ai-project/git-ai/blob/main/specs/git_ai_standard_v3.0.0.md
- **Agent Trace** (Cursor, RFC v0.1.0, Jan 2026; git-ai listed as a partner).
  - JSON trace records per revision: `files[] → conversations → ranges{start_line,end_line}`.
  - Contributor types `human|ai|mixed|unknown`, plus optional `content_hash` that follows code across moves.
  - Model ids in models.dev `provider/model` form. VCS-agnostic (git, jj, hg, svn). Storage left to the implementer.
  - Its `mixed` maps onto our "AI-assisted". It is a good *export* target for `ai attrib`, not a capture system.
  - https://agent-trace.dev/ , https://www.infoq.com/news/2026/02/agent-trace-cursor
- **Aider.** By default appends "(aider)" to author and committer names. Options: `--attribute-co-authored-by` (trailer instead), `--attribute-commit-message-author|committer` ("aider: " prefix). Commit-level only. https://aider.chat/docs/git.html
- **`Co-authored-by` trailer.** GitHub renders co-authors and counts them in contribution stats. https://docs.github.com/en/pull-requests/committing-changes-to-your-project/creating-and-editing-commits/creating-a-commit-with-multiple-authors ; trailers: https://git-scm.com/docs/git-interpret-trailers
- **Claude Code `attribution` setting** (`commit`, `pr`; replaces `includeCoAuthoredBy` as of 2.0.62). Produces the `Co-Authored-By: Claude … <noreply@anthropic.com>` seen in this repo. git-ai's `agent_detection.rs` maps that author email to `claude-web` for unnoted commits. https://code.claude.com/docs/en/settings , https://claudelog.com/faqs/attribution-setting-claude-code/
- **Linux kernel AI policy.** The `Assisted-by: AGENT_NAME:MODEL_VERSION [tools]` trailer. AI must never add `Signed-off-by`, and the human certifies the DCO. Clean separation of "who is responsible" from "what helped". https://kernel.org/doc/html/v7.2/process/coding-assistants.html
- **Cursor / Copilot telemetry.** Vendor dashboards report "% AI lines accepted" from editor events (Cursor team analytics, Copilot metrics API). They are server-side, per-vendor, not in the repo, and don't survive rebase. git-ai's README positions itself against exactly this. https://docs.github.com/en/copilot/concepts/copilot-metrics , https://cursor.com/docs/account/teams/analytics
- **SLSA provenance / in-toto.**
  - Signed attestations (`subject` digests, `predicateType`, `builder`, `materials`) about *build* outputs.
  - Not line authorship. Relevant as the *signing/attestation envelope* if attribution ever has to be tamper-evident: an in-toto statement whose subject is a commit and whose predicate is the v3 note, signed via Sigstore/gitsign or the user's SSH-SK key.
  - https://slsa.dev/spec/v1.0/provenance , https://github.com/in-toto/attestation
- **git notes conventions.**
  - Custom namespace per tool (`refs/notes/ai`, `refs/notes/devtools/*` in git-appraise).
  - Not fetched or pushed by default. Merge strategies `ours|theirs|union|cat_sort_uniq`.
  - Notes attach to object ids, so rewrites need a tool (`notes.rewriteRef` covers only amend/rebase copy, not line remapping).
  - https://git-scm.com/docs/git-notes

## Risks

- **Silent gaps.** Without the daemon, inside sandboxes (the daemon refuses to start in agent sandboxes and checkpoint exits quietly), with Bash edits outside the repo root, or with `git mv`, lines become *unknown*, not AI. `check` must treat unknown changes in `my/` as violations and not as passes.
- **`h_` is partly inferred** (committer recovery). For strict provenance, report inferred-human separately. A human-only commit made by an agent through `git commit` without checkpoints would be labelled human.
- **Notes are not tamper-evident.** Anyone (including an agent) can rewrite `refs/notes/ai`. Strict mode would need signed attestations (in-toto/SSH-SK) or a protected remote ref.
- **Subagent identity collapse.** All agents in one Claude Code session share an `s_`.
- **Footprint and privacy.** Global trace2 config, agent hook files rewritten, background daemon, telemetry defaults on. Transcripts are kept locally in SQLite with best-effort secret redaction. Session records in notes include `human_author` email, which becomes public when notes are pushed.
- **Vendor drift.** The format is controlled by a VC-backed company with a paid tier. The schema is versioned and open, so mitigate with our own reader and a native-writer fallback (option B).
- **Forge merges.** Squash/rebase-merge on GitHub drops note mapping unless git-ai's CI action runs.
- **History walks cost.** Per-line "edited after AI" needs blame plus a note lookup per origin commit. Bounded and batched (one notes-tree read), but not free on large repos.

## Open questions for the user

1. Is git-ai accepted as a permanent companion (daemon + global trace2 + agent hook edits), with `ai` reading its notes? Or do you want `ai` to own capture eventually (option B)?
2. Privacy defaults: OK to set `prompt_storage=local` and turn off git-ai telemetry, token metrics and log upload?
3. What counts as "review" for AI-generated → AI-assisted: a `Reviewed-by:` trailer, an `ai review` note ref, or "any human edit in the file"?
4. Is the classification granularity per line, per file, or per workspace (`ai/`, `my/`, main tree)? Should `ai/` be *expected* to be AI-generated and flagged when a human edits it?
5. Strictness for `my/`: should `check` fail on *unknown* changes in `my/` within AI-touched commits (safe, may false-positive), or only on positive `s_` evidence?
6. Should inferred `h_` (committer recovery) count as human, or be shown as "human (inferred)"?
7. Tamper evidence: is a signed attestation (SSH-SK, as used for commits here) wanted, or are unsigned notes enough?
8. Subagent attribution: should the platform record `parent_session`/`tool_use_id` itself, so coordinator and subagent work can be told apart?
9. Should notes be pushed to the remote (publishes model, session ids, email), or stay local?
10. Is Agent Trace export wanted, for interop with Cursor-side tools?
