# Memory on a dedicated database

Research for `ai memory`. Alternative to `20261003T091838--memory-git-ref.md` (git objects under `refs/ai/memory`). No code changed. Date: 2026-10-03. Companion: `20261003T105008--platform-db.md` is the wider-tool question.

## Summary

Recommendation: **keep the git ref as the source of truth and transport. Do not put memory in SurrealDB (or any DB) as the primary store.** Add a DB only later, as a **disposable local index** derived from the ref (SQLite + FTS5, in `$(git rev-parse --git-common-dir)/ai/cache/`), and only when a concrete need appears: BM25/semantic search, joins against platform data, or >1M memories.

Why. Sync decides it.

- No embedded DB we can ship in a Rust binary has an offline, multi-master merge that goes over a git remote. SurrealDB has none (export/import only). Turso sync needs a sync server and resolves "last push wins". cr-sqlite is unmaintained since 2024-10.
- The only DBs that do git-style push/pull/merge are Dolt (Go, server or subprocess) and DoltLite (C SQLite fork, beta 0.50 since 2026-08-31). Beads went this way. It works, but it means a second VCS in the binary, a young on-disk format, and a merge that still needs our own semantics on top (fingerprint reuse).
- A DB file inside git is an unmergeable binary blob. So any DB-first design ends up with two stores: the DB, and a text/object export in git. That is the "two sources of truth" option E rejected in the git-ref research.
- Our data is the easiest possible CRDT: an append-only set under a total order `(ts, origin)`, plus summaries keyed by content fingerprint. The git-ref design merges it in ~50 lines with no dependency. A DB adds nothing to merge, and takes things away (process locks, binary size, startup time).

Measured, SurrealDB 3.3.0 embedded (`kv-surrealkv`, release, stripped, this machine, 12 cores):

| | SurrealDB 3.3.0 embedded | rusqlite 0.40 bundled (FTS5) | `ai` today |
|---|---|---|---|
| Clean release build | **8 m 38 s wall, 63 CPU-min**, 512 crates | 45 s | — |
| Binary | **105 MB** (79 MB `.text`) | 2.2 MB | 4.2 MB |
| Open existing DB | **~0.93 s**, 290 MB RSS | ~ms | OptMem `wake` 0.03 s |
| 1000 single-statement writes | 5.6 s (synced by default) | 6 ms (one txn) | — |
| Second process opens same store | **fails**: `d/LOCK is already locked by another process` | waits/`SQLITE_BUSY`; WAL allows 1 writer + N readers across processes (`busy_timeout`) | `flock` |

The second-process failure alone disqualifies embedded SurrealDB for `ai memory`. Parallel agent sessions in one repo are separate processes; the template says "parallel sessions are all you, and may all write". Embedded SurrealDB needs a daemon (`surreal start`) to serve them, which breaks "nothing runs in the background".

| Choice | Verdict |
|---|---|
| SurrealDB as memory store | no: lock, 105 MB, ~1 s open, BSL, no sync |
| Dolt/DoltLite as memory store | not now; the only real DB contender; revisit if DoltLite gets a Rust binding and a year of stability |
| SQLite as memory store | no as source of truth (no merge, binary in git); **yes as derived index** later |
| Git ref (prior research) | **yes** |

## Requirements recap

| # | Requirement | What it implies for a DB |
|---|---|---|
| 1 | Not in trunk's tree | DB file outside worktree (`.git/…` or `~/.local/share`) |
| 2 | Versioned, per-item provenance | provenance columns; history either from the DB (time travel) or from the log itself (append-only log already is history) |
| 3 | Mergeable across clones/machines | needs a transport and a merge; the hard part |
| 4 | Zoom over summary tree | range queries by key; trivial in any DB |
| 5 | Full-text grep | regex over text; FTS indexes do tokens, not regex |
| 6 | No agent-search pollution | DB file not under the worktree, or binary |
| 7 | Local-first, single Rust binary | embedded, small, fast open, multi-process safe |

Note for 2: memory is append-only. Time travel ("what did the store look like at T") is `WHERE key <= T` on the log. Only summaries are mutable (`forget`, re-`nap`), and their history is minor. So DB-native versioning (SurrealKV `VERSION`, Dolt commits, XTDB bitemporality) buys little here.

### BSL 1.1 for us

- Whole SurrealDB workspace, **including the `surrealdb` SDK crate**, is `license-file = LICENSE` = BSL 1.1 (crates.io shows "unknown"). Not just the server. Only `surrealkv` (Apache-2) is separate.
- Additional Use Grant: any use allowed except offering it as a "Database Service": a product where third parties "create, manage, or control schemas or tables".
- Embedding in a local CLI used by the user and their agents: allowed.
- Risky if `ai` later becomes a hosted multi-tenant service exposing schema control, or is redistributed by someone who does. Also: `ai` would not be OSI open source while it links BSL code (matters for packaging in nixpkgs `unfree`, Debian, etc.).
- Each version converts to Apache-2.0 four-ish years later (3.0 → 2030-01-01).
- Since 3.1, development happens in a private repo, synced publicly ~1 week after release.

### Sync, concretely

Where does the DB file live, and how do two machines converge?

| Strategy | How | Problems |
|---|---|---|
| DB file committed to git (trunk or ref) | binary blob | no merge at all; last push wins; repo bloat (every write rewrites pages) |
| DB file in Syncthing/Dropbox | file sync | corruption under concurrent open; conflict copies; SQLite docs warn against it |
| One central server (SurrealDB/Postgres/Turso Cloud) | all machines connect | not local-first; offline writes need a queue; privacy |
| Turso sync | local file, push/pull logical changes to a sync server | needs server; LWW only; no git transport |
| cr-sqlite changesets in git | export `crsql_changes` as text into a git ref, apply on pull | works in principle; dead upstream; still a git-ref design with a DB in front |
| Dolt / DoltLite | native push/pull/merge, data under `refs/dolt/data` in the same git remote | second VCS; Go (Dolt) or beta C (DoltLite); summaries still need fp-aware merge (a cell conflict on the same `fp` → pick LWW, as in the ref design) |
| **Export log to git ref, DB as cache** | ref is truth; DB rebuilt/updated from ref after every sync | **this is the git-ref design plus a cache**; cache invalidation keyed by ref commit oid |

Only the last row and Dolt avoid a central server. The last row is strictly simpler. It also degrades gracefully: delete the cache, nothing is lost.

### Concurrency, concretely

`ai memory` is invoked by many short-lived processes: each Claude Code / Codex session, hooks, the user. Requirements: fast cold start, and safe concurrent writers.

- SurrealKV, RocksDB, redb, fjall, Kuzu: exclusive process lock. Second process **fails** (verified for SurrealKV). Fix = daemon + client protocol. Then `ai` grows a server lifecycle (start on demand, socket, version skew between client and daemon, crash recovery). Beads did exactly this: embedded Dolt is single-writer; multi-agent setups must run `dolt sql-server`.
- DuckDB: one writer process at a time.
- SQLite WAL: concurrent across processes, one writer at a time with `busy_timeout` (verified: without `busy_timeout` the second writer gets `SQLITE_BUSY`). Fine for a CLI.
- Git ref: optimistic CAS, losers retry. Fine for a CLI.
- SurrealDB open cost (~0.9 s, 290 MB RSS at default settings) is also paid per `note`/`wake`/`zoom`. Possibly tunable (cache sizes, background tasks); not verified. Even at 0.1 s it is 3× OptMem's whole `wake`.

### Search

- Agents want rg semantics (regex, literal, smart-case). FTS indexes do tokenised BM25, not regex. SQLite FTS5 `trigram` tokenizer supports substring and `LIKE`/`GLOB` acceleration, still not full regex. So `grep` stays a scan in every design; an FTS index only adds ranked search (`ai memory search`?) as a second verb.
- Linear scan at realistic sizes (18k/yr) is ~ms. The git-ref doc's numbers hold.
- Vector search: not requested. If wanted later: `sqlite-vec` in the cache, or LanceDB. SurrealDB's HNSW/DiskANN is a strength we would not use yet.

### Pollution

- DB files are binary. rg skips binary files during recursive search by default; GNU `grep -r` prints "Binary file matches" (noise, not content). Text in SQLite pages and FTS shadow tables is still readable by `strings`.
- Place the cache in `.git/ai/cache/` (shared by worktrees, never walked by rg without `--hidden`, ignored by IDEs). Same as git-ref option E's location, but now it holds only derived data.

## Design sketch: DB-first (for comparison)

If we did choose a DB-first design, the least-bad shape is SQLite:

```sql
CREATE TABLE memory (
  ts TEXT NOT NULL, origin TEXT NOT NULL,
  head TEXT, branch TEXT, agent TEXT, model TEXT, session TEXT,
  text TEXT NOT NULL,
  PRIMARY KEY (ts, origin)
) WITHOUT ROWID;
CREATE TABLE summary (
  size INTEGER NOT NULL, fp TEXT NOT NULL,
  ts TEXT NOT NULL, origin TEXT NOT NULL, agent TEXT, model TEXT, session TEXT,
  text TEXT NOT NULL,
  PRIMARY KEY (size, fp)
) WITHOUT ROWID;
CREATE VIRTUAL TABLE memory_fts USING fts5(text, content='memory', tokenize='trigram');
```

- Position = `ROW_NUMBER() OVER (ORDER BY ts, origin)`; or cache it in a column rebuilt on merge.
- Block `[lo, hi)` at size s: fp over keys of rows `lo..hi`; summary lookup by `(s, fp)`. The fp scheme from the git-ref doc carries over unchanged, which shows the merge logic is store-independent.
- Merge = `INSERT OR IGNORE` of the other side's rows; summaries `INSERT … ON CONFLICT(size, fp) DO UPDATE … WHERE excluded.ts > ts`. Same G-Set + LWW.
- Transport: still needed. Options: export both tables as sorted text into a git ref (→ hybrid), or Dolt/DoltLite.

SurrealDB version of the same (validated on 3.3.0, see platform doc for full schema): record ids `memory:[d'2026-10-03T09:00:00Z', 'K3J9QZ']` sort by `(ts, origin)` natively; range scan `memory:[d'2026-10-03', NONE]..`; summary `summary:[2, '<fp>']`; `derived_from` edges summary→memories. Elegant, but it does not solve transport or locking.

## Design sketch: recommended hybrid

```
refs/ai/memory                 source of truth (git-ref design, unchanged)
.git/ai/cache/memory.sqlite    optional, derived, disposable
  meta(oid)                    ref commit the cache reflects
  memory, summary, memory_fts  as above
```

- Every read command: resolve `refs/ai/memory` → oid. If `meta.oid` matches, use cache; else fast-forward the cache (diff tail segments since `meta.oid`; on merge/renumber, rebuild from scratch: 18k rows ≈ ms).
- Every write: CAS the ref first (truth), then update cache best-effort.
- Cache open via SQLite WAL: multi-process safe; corruption → delete and rebuild.
- Build it only when one of these lands: ranked search, vector search, cross-joins with platform tables (sessions/tasks), or scale.
- Until then: zero DB. The git-ref design is complete without it.

## Comparison with the git-ref design

| | Git ref (`20261003T091838--memory-git-ref.md`) | SurrealDB-first | SQLite-first + git export | Dolt/DoltLite-first | Hybrid (ref + SQLite cache) |
|---|---|---|---|---|---|
| Not in trunk | yes | yes (file outside tree) | yes | yes (`refs/dolt/data`) | yes |
| Provenance | inline fields | fields + graph edges | fields | fields + commit history | inline (+ queryable) |
| History | commit per mutation | SurrealKV versions (retention) | none / DIY | commit per write | commit per mutation |
| Merge across machines | **sorted union, own code** | **none** | own code, via export | native cell merge + own fp rule | sorted union |
| Transport | git | none | git | git remote | git |
| Multi-process | CAS | **lock: fails** | WAL | single-writer embedded | CAS + WAL |
| Startup | ms | ~0.9 s | ms | Go subprocess / ms (DoltLite) | ms |
| Binary cost | +gix | +100 MB | +2 MB | +Go binary / +C fork | +gix +2 MB |
| grep | scan | FTS (no regex) | scan / FTS5 | scan | scan + optional FTS |
| Pollution | none | binary in `.git` | binary in `.git` | none (objects) | binary cache in `.git` |
| Moving parts | 1 store | 1 store, no sync | 2 stores | 1 store, 2 VCSs | 1 truth + 1 cache |

**Choice: git ref now; hybrid cache when a concrete need appears.** Dolt-family is the only DB worth re-evaluating, and only if DoltLite stabilises with a usable Rust binding and git-remote push/pull.

## Risks (of the recommendation)

- Git-ref risks from the prior doc stand (gix churn, write amplification, privacy of pushes).
- A future need for semantic search arrives earlier than expected → the cache becomes load-bearing. Mitigation: it is still derived; design its rebuild from day one.
- If the platform (`20261003T105008--platform-db.md`) ends up with a daemon anyway, a server DB becomes cheap, and the cache could live there. The ref stays truth either way.

## Open questions for the user

1. Accept "git ref = truth, DB = optional cache" as the long-term architecture for memory?
2. Is ranked (BM25) or semantic search wanted at all, beside regex `grep`? That is the only trigger for the cache.
3. Is BSL acceptable anywhere in `ai`? (Blocks "OSI open source" and some distro packaging.)
4. Is a background daemon ever acceptable? If yes for the platform, should memory reuse it, or stay daemon-free?
