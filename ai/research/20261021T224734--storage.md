## Today

- **Agents:** `~/ai/projects/<project>/agents/`, format 6 (src/agent/store.rs, `Store::root`). A project's folder is the one of `~/ai/projects/` whose `id` file holds the project's id, whatever its name, else `projects/<name>`, made and claimed on the first write (`Project::claim`); a name another id holds is refused. `~/ai` is one git repository, made when `ai` first writes to it; events commit the project's folder alone, through gix, under one lock, editing HEAD's tree at that folder and only that folder's index entries (`repo::commit_paths`); past `[agent] gc-after-mib` of loose objects written since the last one, a commit starts `git gc` in the background (`repo::gc`). Each thread, `threads/<name>/`, holds its items, lines, session tracks, attachment changes (`attachments.jsonl`), subagents, calls and `sources.jsonl`, in place of a copy (rule 10): per session file it read, the harness, session, the machine (`backup::host`, the name its snapshots carry), the path where the file really sits there (its folder's links resolved, as the session's track records its transcript), the length and SHA-256 of the bytes read from the file's start, and when they were read (`record::Pointer`). A record whose `from` is 0 begins a version; a later one of the file says it grew, going on from the length the one before told of. A sync runs no restic: a file that grew is recorded at its new length, one that no longer begins with what was read begins a new version and is warned of on that sync, and one that is gone adds nothing and is warned of on every sync. `ai agent list` ends each session's line with how many of its files on this machine are gone or shorter than what was read, by size alone. The bytes are read back (`backup::read`) from the file while it begins with them, else from the local repository, then the remote: restic lists the machine's snapshots, searches the last one before the record's time, the first after it and a few later ones for the path (`restic find`), and dumps the newest state long enough until one begins with the bytes. `ai backup threads` does so for every thread in `~/ai` and counts each file as backed up, not yet (the file holds the bytes and the newest snapshot not), with no backup (no repository made), on another machine, or lost; `ai agent resume` puts a session's files that are gone back in place first (`agent::restore`). The threads' locks and compactor logs, and the sessions' locks, are in `~/.ai/agents/<project id>/`. The private settings are `~/ai/projects/<project>/ai.toml`, linked from `<repo>/ai.local.toml`.
- **Moving older stores:** `.ai/local/` in a project's home, where ai up to 0.17 kept the agents (format 4) and private settings, is refused until moved (src/agent/convert.rs). Each file it kept as a directory of 1 MiB segments becomes one file of the same bytes. On a terminal, `ai agent`, `ai resume` and `ai init` offer the move. It locks the old threads' writers, archives `.ai/local/` whole (git history included) in `~/.ai/archive/<project id>/<stamp>--local` and checks the copy byte for byte, moves the private settings and other files (evals) into the project's folder, builds the new store beside its place and renames it in, removes `.ai/local/` and commits. Each copied session file whose harness file still begins with it becomes a record of that file; one the harness lost is restored at its path, and one the harness changed into `<session>/restored/` beside the transcript, which every sync reads. A move cut short is finished by the next, reusing its archive. Rule 14 keeps `.ai/local/`: the move takes only threads and private settings.
- **Memory:** `~/.ai/memory` is a bare git repository with one ref, `refs/ai/memory`: `log/` holds one file per note (1,100 notes, 503 KB), `trees/1` and `trees/2` the summary trees (about 2 MB). The ref has 3,452 commits; the repository's objects take 210 MB. `calls/` (36 MB of summariser calls), `usage.jsonl`, logs and locks sit loose in it. Its id is `~/.ai/memory/origin`.
- **The user's settings:** `~/.ai/ai.toml`.
- **Harness files:** each harness writes its own folders: Claude Code `~/.claude/projects` (`~/.claude` is a link through the Nix store into the config repo), Codex `~/.codex/sessions`, pi, DSH, Gemini, opencode and Hermes their own (`backup::harness::HARNESSES`). They stay where each harness writes them.
- **Harness databases:** OpenCode keeps its transcripts in SQLite, `opencode.db` (`session` and `message` tables, 14.5 MB), and so does Hermes, `state.db` (`sessions` and `messages`, 0.5 MB, beside `kanban.db`). Codex writes JSONL sessions in `~/.codex/sessions`, beside `thread_history_1.sqlite` (34 MB), `state_5.sqlite` and `logs_2.sqlite` (63 MB of logs). Claude Code, pi and DSH keep none; the `.db` files in `~/.claude/context-mode/` belong to the context-mode plugin.
- **The backup:** `ai backup` (src/backup/) runs restic as a program; `ai` holds no storage code of its own. A run backs up each harness's folders, under its default folder, and the folders `[backup] folders` names, each where it really sits, as one snapshot of this machine (`--host`, `backup::host`) in the local repository `~/.ai/backup`, once restic's dry run finds a file new or changed. A database goes in as a copy made first with SQLite's backup API under `~/.ai/backup-staging/` (src/backup/db.rs). With `[backup.remote]`, the run then copies every snapshot the remote lacks into it (`restic copy`); the remote is made with the local repository's chunker parameters, and a copied snapshot has an id of its own there. Nothing is forgotten or pruned. `[backup]` is read from the user's own `~/.ai/ai.toml` alone. A command that prints a password or the remote's variables is run by `sh -c` and stopped after 60 seconds (src/command.rs); restic gets a password in its environment. One run goes at a time, under `~/.ai/backup.lock`, and leaves its outcome in `~/.ai/backup.json`, which `ai backup status` prints. `ai backup watch` runs every `[backup] every`, 5 minutes by default, and a session's end starts a run. `ai backup check` is `restic check`. What a thread read is read back from the file while it begins with it, else from the repositories (src/backup/read.rs, rule 10); `ai backup threads` tells where the bytes every thread read are, and fails if any are lost (src/backup/threads.rs). ai-tools' Home Manager module (`services.ai-tools.backup`) runs `ai backup watch` as the user service `ai-tools-backup`, restarted on failure. Nothing has run on the real transcripts yet.
- **Snapshot count:** measured on restic 0.19.1 with a local repository on this machine, a tree of 300 files, one snapshot per appended line. 1,564 snapshots came from backups and the rest are copies of them at other times (`restic rewrite --new-time`), so the index stayed that of 1,564 backups: a repository of as many real backups holds one index file per run more, whose cost is unmeasured. Seconds at 1,564, 12,520 and 50,084 snapshots: a dry run that finds a change 0.6, 2.0, 5.6; the backup after it 1.1, 1.5, 3.5; a dry run that finds none 0.6, 1.5, 4.5; `snapshots --json` 0.9, 1.1, 4.5 (47 MB of JSON at 50,084); `find` in the newest snapshot for 300 paths 0.6, 2.5, 3.5; `find` in every snapshot for one path 6.8, 40, 134; `dump` of one file 0.9, 1.4, 4.2. Every restic command reads every snapshot's record first, about 0.09 s more per 1,000 snapshots. A run every 5 minutes stays workable: 4.5 s when nothing changed at 50,084 snapshots, which is half a year of a change every 5 minutes around the clock. A search of every snapshot does not, at 3 ms a snapshot, so a read-back searches the snapshots around the record's time alone: `ai backup threads` read one file back in 9 s at 50,084 snapshots.
- **Config errors:** a broken setting fails only the commands that read its table (src/config.rs, `fix(config)` on this branch). A file that is not TOML, an unknown table name, or `[project]` in the user's or private file still fails every table read from that file, since what the file meant to set is unknown.

## Rules

**Agreed**

1. **Five places, one role each.**
   - `~/ai`: what is the user's on every machine, in a git repository the user keeps as they keep `config`: every thread, user-level and every project's; memory, its notes and summary trees; each project's private settings. Small text. It is what a new machine needs.
   - **A remote store,** optional: raw bytes, encrypted, off the machine: a restic repository that gets a copy of every snapshot (rule 11).
   - `~/.ai`: this machine only, never in git: the backup's local repository, locks, logs, caches, settings that belong to this machine.
   - `<repo>/.ai/local`: one project's private working data, kept beside its code: evals, datasets, experiment output. The project's git ignores it; it is a git repository of its own, and reaches another machine only through a remote the user gives it.
   - `<repo>/ai`: the project's parts that can be public, the agents' visible workspace.

   The test: what is about the user and their agents goes in `~/ai`; what the project's work produced goes in `.ai/local`.
2. **Every transcript is backed up in `~/.ai` and stays recoverable**, also for an agent running in a sandbox: the backup holds it (rule 8).
3. **A project repo tracks only what the project shares:** `ai/`, the agents' visible workspace; `.ai/`, hidden, less `.ai/local/` (rule 1); and the tracked `ai.toml`, with the project's own settings and its in-repo hierarchy. User-level details never enter what the project tracks: no threads, no private settings, no address of another project's agent or of a user-level agent.
4. **Agents never touch git.** A sandbox gets its own thread's files read-write and its subordinates' read-only, never `~/ai/.git`. Only `ai` running outside every sandbox commits. One repository per thread is undone: it existed only to hand a sandbox one thread's git.
5. **Nothing `ai` stores goes in a project's `.git`**: no config keys, refs or commits. `ai` reads git through `gix` and never commits in a project repo.
6. **A broken setting fails only the commands that read it**, directly or through others. Nothing guesses past a bad value.
7. **`~/ai/projects/` lists every project.** No separate registry exists.
8. **The backup.** `ai` implements no storage backend: restic, run as a program, keeps every harness's transcripts in a repository in `~/.ai/backup`, from outside every sandbox; no sandbox holds its key. It only grows: nothing is forgotten or pruned, so a harness or agent that deletes or rewrites a file leaves its bytes in the snapshots made before.
9. **`ai backup` runs it.** Harness files stay where each harness writes them. A user service outside every sandbox backs them up every `[backup] every`, and each session's end starts a run. Bytes a harness writes and deletes between two runs are in no snapshot. Which harnesses, and which of their folders, are backed up is `ai`'s own list, with `[backup] folders` for more. A database goes in as a whole copy taken with SQLite's backup API; for OpenCode and Hermes that copy is the transcript.
10. **Threads record what they read**, never copies of their own: the machine, the file's real path, the length and SHA-256 of the bytes from its start, and when they were read. No record names a snapshot, since a copied snapshot has another id in the remote. The bytes are read from the file while it begins with them; after that from the repositories, the local one, then the remote: the machine's last snapshot before that time or its first after holds them if any does. `~/ai` stays small and its remote carries no transcript. On a fresh machine, items, summaries and views work from a clone of `~/ai`, and the raw bytes come from the remote repository.
11. **The remote.** The local repository always exists. A remote one is optional: any repository restic reaches, such as an S3-compatible service, set in `[backup.remote]`; each run copies the new snapshots to it. restic encrypts both. The remote's password is the user's to keep where this machine's loss doesn't reach, in pass on `eagle` for now. `ai resume` refuses to start a sandboxed agent unless the backup runs and a remote is set; every other command keeps working without one.
12. **A project's name is unique in `~/ai/projects/`.** A second project with a name another project holds is refused, and told to set `[project] name`.
13. **Memory lives in `~/ai/memory`**, its notes and its summary trees.
14. **The move from `.ai/local` takes only threads and private settings.** The rest of `.ai/local` stays where it is.

## Layout

**Recommended**

```
~/ai/                          git; the user's
  ai.toml                      the user's settings and user-level agents
  memory/                      memory notes and summary trees
  agents/<name>/               user-level threads (root, the companions)
  projects/<project>/
    ai.toml                    the project's private settings
    agents/<name>/             the project's threads

~/.ai/                         this machine only; never git
  ai.toml                      this machine's settings
  backup/                      the backup's local repository (rule 8)
  locks, logs, caches

<repo>/
  ai/                          tracked; can be public
  .ai/                         tracked
  .ai/local/                   ignored; a git repository of its own; private working data
  ai.toml                      tracked
  ai.local.toml                gitignored link to ~/ai/projects/<project>/ai.toml
```

- `ai init` keeps `ai.local.toml` as a gitignored link, so the project's private settings stay at hand in the repo while their file lives in `~/ai`.
- A thread keeps its items, lines, session tracks, attachment changes, subagents, calls and records of what it read of its sessions' files (rule 10), each a JSON Lines file. gix stores every version of a file whole, so after a commit `ai` starts `git gc` on `~/ai` in the background once the loose objects written since the last one pass `[agent] gc-after-mib` (32 MiB by default, `repo::gc`), which packs a grown file's versions against each other.

## Writing to `~/ai`

**Recommended**

- **Commits through `gix`.** A commit names the paths it covers, a project's folder; it edits HEAD's tree at those paths, writes the commit, moves the ref, and updates only those paths' index entries, so what the user staged elsewhere stays staged and `git status` stays clean. Built (`repo::commit_paths`).
- **One store lock** serialises commits to `~/ai`. Built.
- **Who commits:** `ai` outside every sandbox: the user's own commands, those the desk runs, and the `ai resume` process that launched a sandboxed agent, which commits what its agent wrote. Inside a sandbox `~/ai/.git` does not exist, and `ai` writes its files without committing.
- **When:** memory notes commit each write. A thread commits on events, as today: `ai agent new`, `attach`, `detach`, `resume`, a build, a session's end. A turn's sync and the background summariser write without committing; the next event carries what they wrote.
- **Ignored:** locks, pid files and logs, which live in `~/.ai` anyway.
- **Remote:** `~/ai` gets whatever remote the user gives it; it carries no transcript (rule 10).

## Moving today's stores

**Recommended:** one conversion, detected and offered with a yes/no prompt, as `ai` offers store upgrades.

- **Threads:** `<repo>/.ai/local/agents/threads/*` move into `~/ai/projects/<project>/agents/`. Built ("Today"), with the old store copied whole to `~/.ai/archive/` (open question 4).
- **Private settings:** `<repo>/.ai/local/ai.toml` moves to `~/ai/projects/<project>/ai.toml`; `ai.local.toml` is relinked. Built.
- **The rest of `.ai/local`** stays (rule 14). Built code still moves it and removes `.ai/local`.
- **Memory:** `~/.ai/memory`'s notes and summary trees move into `~/ai/memory/` (rule 13); its history is open question 1.
- **The user's settings:** `~/.ai/ai.toml` moves to `~/ai/ai.toml`, less any setting that belongs to this machine.

## Open questions

1. **Memory's history.** `~/.ai/memory`'s objects take 210 MB, against 503 KB of notes and about 2 MB of trees today. Measure what fills them before choosing whether `~/ai` carries that history.
2. **Interrupted writes.** A crash after changing a file but before committing leaves the change uncommitted. As built, the next commit takes the folder as it is on disk. Should it instead fail naming the change?
3. **A project folder's name after a rename.** A folder is found by its id, so a project whose `[project] name` changes keeps its old folder, and addresses that use the name drift from it. Rename the folder with the project, or let addresses use the folder's name?
4. **Conversion backups.** The move from `.ai/local` copies the old store whole to `~/.ai/archive/<project id>/<stamp>--local`, a plain folder no run backs up. Where it belongs is open.
5. **A bucket lock on the remote.** restic deletes its lock files, and consolidates index files only when it prunes, which never happens here: every run adds one. A lock that refuses deletes must leave `locks/` out, and what it means for `index/` is unmeasured.
6. **Several machines writing at once:** in the backlog (`ai/backlog.md`).
7. **Another machine's files.** A record names its machine, and `ai backup threads` reads another machine's bytes back from the repositories this machine reaches. Nothing puts such a file in place here: `ai agent resume` brings back only files of this machine.
