# Agents

Author: Claude Code (Claude Opus 5.5)

This is a design for `ai agent`. Sections 1, 3 and the start half of 4 are implemented; section 2 and moving a thread between harnesses are not. It builds on `ai/spec.md` and `ai/research/20261021T194314--ids-handles-and-paths.md` ("the ids note"). Points marked **Recommended** await the user's confirmation; the rest is agreed.

## Agreed

- An agent has one thread and its own instructions. It may have a worktree: recommended, not required.
- An agent is tied to no harness and no model. A thread moves between harnesses and tools, and its history belongs to the user, free of any one harness.
- No agent is special. A developer agent and a stabiliser agent are both ordinary agents, interactive like any other.
- `ai memory` is the memory every agent shares.
- Agent configurations may live in `ai.toml`. Threads stay local to the user. `ai.local.toml` overrides a project's settings for one user.
- Definitions and instructions travel; threads stay per project (see "Scope").

Headless agents are a backlog item, not part of this design.

## Scope

Agreed:

- An agent's definition and instructions can be the user's, in `~/.ai/ai.toml` with instructions resolved from `~/.ai`. Such an agent exists in every project, so a role's lessons and patterns of behaviour carry from project to project.
- A project can add its own instructions for the same agent, merged with the user's.
- The thread stays per project: `reviewer` in two projects is two threads under the same instructions.

Why threads stay per project:

- A thread is full of one project's files, decisions and branches. Carried into another repo, it mixes unrelated history into the view.
- Lasting knowledge that should carry over already has a home: `ai memory`, shared by every agent, or the agent's instructions file.
- A cross-project thread would need a project-free store and address, would mix repos in its branches, and would make attaching it to a worktree ambiguous.

Cross-project threads go to the backlog only if a real case appears.

## Today

- A fork's report opens a work turn in its parent's thread (`src/agent/claude.rs`). Nothing else delivers a message from one agent to another.

## 1. Agent and thread

Implemented: one concept. An agent is a thread, plus whatever configuration names it.

- Every thread is an agent. An agent with no configuration has no instructions and no worktree.
- `ai agent` takes over all of `ai chat`'s commands, and `ai chat` goes: `start`, `resume`, `attach`, `detach`, `list`, `view`, `zoom`, `grep`, `build` and the plumbing.
- `ai agent new <name>` is the only command that creates an agent. `start`, `resume`, `attach`, `view`, `zoom`, `grep` and `build` refuse an unknown name, so a typo fails instead of making a stray thread.
- "Thread" stays the word for an agent's history. The store word in addresses becomes `agent`: `agent.<project>.<name>:<branch>.<turn>.<item>`. The minted id's prefix becomes `agent_`.
- Agent names keep the thread-name rules: letters, digits, `-` and `_`, never all digits, never a store word. These are also valid bare TOML keys.
- Forks stay branches of their parent's thread (the ids note), not agents.

## 2. `ai agent message <name> <text>`

**Recommended:** the message waits in the recipient's inbox, and the recipient's harness takes it in at a turn boundary.

- `message` appends `{id, from, text, ts}` to the recipient thread's `inbox.jsonl`. `from` is the sending session's agent, else the user.
- **Recipient running:** its harness plugin delivers pending messages at the next turn boundary. In Claude Code that is the Stop hook (block, with the messages as the reason) or, when the user types first, `UserPromptSubmit` context. Each harness needs its own glue; the inbox is neutral.
- **Recipient not running:** the messages wait, and its next `start` or `resume` delivers them first.
- A delivered message enters the harness session in a recognisable envelope. Sync reads it as a turn opened by agent `<from>`, as a fork report is today, and marks the inbox record delivered by the item it became.
- The sender's own thread already holds the `ai agent message` call. A reply is another `message`; there is no reply protocol.
- On an org account the Stop hook reaches only a managed install (`README.md`, "Claude Code plugin").

## 3. Configuration

Implemented, except merging instructions across files:

```toml
# ai.toml, committed: roles collaborators share
[agents.stabiliser]
instructions = "ai/agents/stabiliser.md"
worktree = "../ai-tools-stabiliser"
```

- `instructions` is a Markdown file, relative to the folder of the settings file that names it: `~/.ai` for `~/.ai/ai.toml`, the project root for `ai.toml` and `ai.local.toml`.
- `worktree` is a directory, relative to the project root whichever file names it, since a worktree belongs to the project. In a linked git worktree that root is the main checkout's, so every checkout names the same directory. Outside a project a relative `worktree` stays as written.
- `ai.local.toml` sits beside `ai.toml` (in a linked git worktree, beside the main checkout's), has the same tables except `[project]`, and wins key by key; agents are matched by name, then merged key by key. Precedence: `~/.ai/ai.toml`, then `ai.toml`, then `ai.local.toml`. `ai init` adds `ai.local.toml` to `.gitignore`, as Claude Code does for `settings.local.json`.
- `instructions` add up instead of replacing each other: `start` and `resume` pass every layer's file, in precedence order, joined by a blank line.
- `[agents.<name>]` is optional. An agent with no table is still an agent.
- No `harness` or `model` key, since an agent is tied to neither.
- The thread lives in `.ai/agents/threads/<name>/` in the project's main checkout, which `ai init` gitignores. Two collaborators who both run `stabiliser` share its instructions and have a thread each.
- `ai` runs an agent in its worktree and fails if the directory is missing, printing the `git worktree add` command. It doesn't create worktrees itself. It refuses a worktree that doesn't share the store: anything but a git worktree of the main checkout holding this project's `ai.toml`.
## 4. Starting in a harness

Agreed: the harness and the model are chosen each time the agent starts.

- `ai agent start <name> [--harness <h>] [-- <harness args>]`, and `resume` takes `--harness` too. The harness defaults to `claude`, the only one accepted on main.
- The model is the harness's own flag after `--`, such as `-- --model sonnet`. `ai` maps no model names across harnesses. Inside a session, the harness's own `/model` switches it.
- `ai` passes the harness the working directory (the worktree, else the current directory), the instructions, the thread binding, and the thread's view as starting context. Claude Code gets the instructions' text through `--append-system-prompt`, read afresh at every `start` and `resume`.
- `resume` runs where the session ran, since Claude Code finds a session only from its own directory.
- `resume` continues the agent's newest session in the same harness. Not implemented: with `--harness` naming another one, it starts a new session there, seeded with the view. That is how a thread moves between harnesses.
- A new session carries on the agent's branch from its newest item, as sessions already graft (`ai/spec.md`).
- Each harness needs an adapter (read its sessions) and a plugin (binding, compaction, inbox). pi and DeepSeek Harness support is on branch `dsh-pi`, unreviewed (`ai/backlog.md`).
