# Agents

Author: Claude Code (Claude Opus 5.5)

This is a design for review, and nothing in it is implemented. Facts about today's code are from main `54393bec`. It builds on `ai/spec.md` and `ai/research/20261021T194314--ids-handles-and-paths.md` ("the ids note"). Points marked **Recommended** await the user's confirmation; the rest is agreed.

## Agreed

- An agent has one thread and its own instructions. It may have a worktree: recommended, not required.
- An agent is tied to no harness and no model. A thread moves between harnesses and tools, and its history belongs to the user, free of any one harness.
- No agent is special. A developer agent and a stabiliser agent are both ordinary agents, interactive like any other.
- `ai memory` is the memory every agent shares.
- Agent configurations may live in `ai.toml`. Threads stay local to the user. `ai.local.toml` overrides a project's settings for one user.

Headless agents are a backlog item, not part of this design.

## 1. Agent and thread

**Recommended:** one concept. An agent is a thread, plus whatever configuration names it.

- Every thread is an agent. An agent with no configuration has no instructions and no worktree.
- `ai agent` takes over all of `ai chat`'s commands, and `ai chat` goes: `start`, `resume`, `attach`, `detach`, `list`, `view`, `zoom`, `grep`, `build` and the plumbing.
- `ai agent new <name>` is the only command that creates an agent. `start` and `attach` refuse an unknown name, so a typo fails instead of making a stray thread.
- "Thread" stays the word for an agent's history. The store word in addresses becomes `agent`: `agent.<project>.<name>:<branch>.<turn>.<item>`. The minted id's prefix becomes `agent_`.
- Agent names keep the thread-name rules: letters, digits, `-` and `_`, never all digits, never a store word. These are also valid bare TOML keys.
- Forks stay branches of their parent's thread (the ids note), not agents.

## 2. `ai agent message <name> <text>`

**Recommended:** the message waits in the recipient's inbox, and the recipient's harness takes it in at a turn boundary.

- `message` appends `{id, from, text, ts}` to the recipient thread's `inbox.jsonl`. `from` is the sending session's agent, else the user.
- **Recipient running:** its harness plugin delivers pending messages at the next turn boundary. In Claude Code that is the Stop hook (block, with the messages as the reason) or, when the user types first, `UserPromptSubmit` context. Each harness needs its own glue; the inbox is neutral.
- **Recipient not running:** the messages wait, and its next `start` or `resume` delivers them first.
- A delivered message enters the harness session in a recognisable envelope. Sync reads it as a turn opened by agent `<from>`, as a fork report is today, and marks the inbox record delivered by the item it became.
- The sender's own thread already holds the `ai agent message` call. A reply is another `message`; there is no reply protocol.
- On an org account the Stop hook reaches only a managed install (`README.md`, "Claude Code plugin").

## 3. Configuration

**Recommended:**

```toml
# ai.toml, committed: roles collaborators share
[agents.stabiliser]
instructions = "ai/agents/stabiliser.md"
worktree = "../ai-tools-stabiliser"
```

- `instructions` is a Markdown file, relative to the project root. `worktree` is a directory, relative to the project root.
- `ai.local.toml` sits beside `ai.toml`, has the same tables except `[project]`, and wins key by key. Precedence: `~/.ai/ai.toml`, then `ai.toml`, then `ai.local.toml`. `ai init` adds `ai.local.toml` to `.gitignore`, as Claude Code does for `settings.local.json`.
- `[agents.<name>]` is optional. An agent with no table is still an agent.
- No `harness` or `model` key, since an agent is tied to neither.
- The thread lives in `~/.ai/chat/<project>/<name>/`, on each user's machine. Two collaborators who both run `stabiliser` share its instructions and have a thread each.
- `ai` runs an agent in its worktree and fails if the directory is missing, printing the `git worktree add` command. It doesn't create worktrees itself.

## 4. Starting in a harness

**Recommended:** the harness and the model are chosen each time the agent starts.

- `ai agent start <name> [--harness <h>] [-- <harness args>]`. The harness defaults to Claude Code, the only adapter on main.
- The model is the harness's own flag after `--`, such as `-- --model sonnet`. `ai` maps no model names across harnesses. Inside a session, the harness's own `/model` switches it.
- `ai` passes the harness the working directory (the worktree, else the project), the instructions, the thread binding, and the thread's view as starting context.
- `resume` continues the agent's newest session in the same harness. With `--harness` naming another one, it starts a new session there, seeded with the view. That is how a thread moves between harnesses.
- A new session carries on the agent's branch from its newest item, as sessions already graft (`ai/spec.md`).
- Each harness needs an adapter (read its sessions) and a plugin (binding, compaction, inbox). pi and DeepSeek Harness support is on branch `dsh-pi`, unreviewed (`ai/backlog.md`).
