# statig in ai-tools: what has states, and the pilot

Author: Claude Code (Claude Opus 5.5)

Which parts of ai-tools have states, what statig offers and costs, and the component to pilot
it on. Scope: control state during a computation, not on-disk formats. Components with states
are written with statig; the rest stays plain Rust (iterators, folds, matches). Nothing here
is built.

## statig

- **Version:** 0.4.1 (crates.io, 2025-07-05), macro 0.4.0. Upstream `main` (mdeloof/statig,
  2025-11-29) has three later commits, one a fix (#77): in 0.4.1 the blocking
  `before_transition` callback gets source and target swapped. `after_transition` is right.
- **Licence:** MIT. Same footing as `anyhow`, `clap` and most of the tree: compatible with
  ai-tools' CC0-1.0, binary distributions carry the MIT notice.
- **Model:** hierarchical (UML statecharts, after Samek's *Practical UML Statecharts*).
  - `#[state]` handlers return `Outcome`: `Handled`, `Transition(State::x(..))`, `Super`
    (defer to the superstate). Superstates nest.
  - Entry and exit actions per state (`entry_action`, `exit_action`), run along the
    transition path.
  - Shared storage: the struct the machine is implemented on (`&mut self`).
  - State-local storage: handler arguments become fields of that state's variant.
  - Context: an external `&mut` passed per event (`handle_with_context`).
  - Generic machines are supported.
- **Tracing:** four hooks, `before_dispatch`, `after_dispatch`, `before_transition`,
  `after_transition`, given the state and the event or the source and target; with
  `state(derive(Debug))` one hook logs every transition through `tracing`.
- **Async:** feature `async`; handlers and actions may be `async fn`. Needs Rust 1.85+
  (`AsyncFnOnce`, #71). ai-tools is on 1.99.
- **Plain Rust stays plain:** handlers are ordinary methods, so iterators, `match` and helper
  functions work inside them unchanged.
- **Compile cost:** `statig_macro` needs `syn` 2 (`full`, `visit`, `visit-mut`,
  `extra-traits`), `quote`, `proc-macro2`, `proc-macro-error2`. ai-tools already builds
  `syn` 2.0.119 with `full`, `fold`, `visit-mut`, `extra-traits`; statig adds `visit`,
  `proc-macro-error2` and its own macro crate. Small.

### Limits that matter here

1. **Handlers return `Outcome`, not `Result`.** No `?` inside a handler. Failure is a state
   (`failed { error }`) or an event; `anyhow::Error` is not `Clone`, so a state keeps the
   error's text (`format!("{e:#}")`), losing downcasts.
2. **Events come from outside** (#31). A handler cannot post an event to its own machine.
   A driver loop (or a channel) feeds every event: the machine decides, the driver does I/O.
3. **Async machines are not `Send` on stable** (#78, rust-lang/rust#100013). An awaitable
   machine cannot be held across `tokio::spawn` on the multi-threaded runtime. A blocking
   machine driven from a task, or a `LocalSet`, works. ai-tools is threads and blocking calls
   (`Api` uses `block_on` inside), so the blocking machine fits everything today.
4. **No move-out of shared storage.** `StateMachine` derefs to it; `inner_mut` is `unsafe`.
   A result lives in a final state's local storage and is cloned out, or the driver keeps it.
5. `proc-macro-error2` is unmaintained (#81): a future `cargo-audit` warning, no known harm.
6. Context has one lifetime (#19); a context holding `&mut` to structs that hold `&mut` needs
   reborrowing. Not hit by any candidate below.

Known awkward spots the states expose:

- **Witness never-agree:** the cycle checking → answering → checking has no exit but a clean
  verdict or a failed call. A summariser and witness that never agree loop until a call fails.
  Still undecided; the pilot keeps this behaviour and makes the missing exit visible.
- **Pump duplication:** memory and agent each carry a node life and a failure policy, written
  twice, differing (backoff and `GaveUp` against `OnFail` and `streak`).
- **Child life in `Drop`:** terminate, grace, kill and reap are ordered inside `Drop for Proc`,
  with `failure()` doing a second kill and wait.

## Ranking

1. **Witness exchange.** Real states with a nested one, about 75 lines of control, tested
   through the fake API server (`witness.rs` tests). One known gap. Shape of the desk.
2. **Summariser pump.** Highest payoff: one node machine for both stores, explicit waiting,
   one failure policy chosen by settings. About 600 lines over two files, threads and channels:
   too big to judge as the first before/after. Second, once the pattern is accepted; its node
   life is also the template for a mail delivery queue.
3. **`claude -p` child.** The sandbox launcher's lifecycle (spawn bwrap, run, terminate, reap,
   die with parent) is this one. Write the launcher with statig, and move `Proc` onto it then.
4. to 9. Plain Rust: flat outcomes or folds, no transitions driven by events.
10. TypeScript: the rule applies without statig.

## Pilot: the witness exchange

**Why:** small enough to read whole before and after; has a superstate, state-local data and
a terminal state; a known gap shows on the diagram; its round trip (draft, reviewer verdict,
findings or edits, author answers, again) is the desk's approve, edit or reject loop with
an agent on both ends. Behaviour unchanged; the existing tests must pass untouched.

```text
                 ┌─ exchange (superstate) ────────────────────────────────────┐
                 │   CallFailed(e) ──▶ failed { error }                       │
 start ──▶ checking { tries }                                                 │
                 │   Witness(reply):                                          │
                 │     OK                       ──▶ settled { summary }       │
                 │     findings                 ──▶ answering { findings }    │
                 │     neither, tries < TRIES   ──▶ checking { tries + 1 }    │
                 │     neither, tries = TRIES   ──▶ failed { error }          │
                 │                                                            │
           answering { findings }   entry: round += 1, log findings           │
                 │   Answered { summary, reasons } ──▶ checking { 1 }         │
                 └────────────────────────────────────────────────────────────┘
```

Shared storage: the request, the current summary, the round, the next message out.
Entry actions set the next message (`found(findings)`, `FORMAT`, or the summariser's answer
with its contested reasons). `after_transition` logs `from → to` with `node` and `round`
through `tracing`.

**Before:** `settle` (50 lines) is a `loop` that calls `check` (a `for k in 1..=TRIES` re-ask
loop), bumps `round`, asks the summariser, splits the answer, maybe calls `fit`, and rebuilds
`message`. Where the exchange stands is the position in the loop.

**After:**
- `struct Settle<T>` with `#[state_machine]`: four states, one superstate, two actions,
  one transition hook.
- A driver of about 20 lines: an exhaustive `match m.state()` with no catch-all. In
  `checking` it asks the witness; in `answering` it asks the summariser, then runs `fit`
  (unchanged, shared with `write_line`). It feeds the reply or the failure as an event.
  `settled` and `failed` return.
- New unit tests feed events with no server: every transition, including the third format
  failure.
- Expected size: 20 to 40 lines more than today. The gain is the transition table in one
  place, exhaustive states, and transitions in the log.

After the pilot the user reads both and decides whether the rule enters `AGENTS.md`.
