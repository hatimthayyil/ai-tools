# SurrealDB as the platform database

Research for the wider `ai` tool: agent floor/orchestration, strict provenance, AI/Human/Both workspaces, attribution. No code changed. Date: 2026-10-03. Companion: `20261003T104835--memory-db.md` (memory store), `20261003T091838--memory-git-ref.md`, `20261003T103840--attribution.md` (separate agent).

## Summary

Recommendation: **SurrealDB models this domain beautifully, but don't build on it now. Use SQLite (rusqlite, bundled, WAL) with an explicit schema for local operational state, and git refs for anything that must merge across machines.** Re-evaluate SurrealDB **in server mode** only if `ai` grows a long-running orchestrator daemon *and* needs push-based live updates to many clients (UI, remote agents).

Reasoning:

- **Multi-process is the deciding constraint.** Every agent session, hook and human invocation is a separate `ai` process. Embedded SurrealDB takes an exclusive directory lock; the second process fails (verified, 3.3.0). Live queries also only notify within the process that holds the datastore. So the orchestration features that make SurrealDB attractive (live queries, permissions per user) all require `surreal start` as a daemon. SQLite WAL gives cross-process concurrency with no daemon.
- **Cost.** Embedded SurrealDB: 105 MB binary (vs `ai` 4.2 MB today), 8.6 min clean build, ~0.9 s and 290 MB RSS to open at defaults. Each short CLI call pays the open.
- **Permissions don't cover our workspaces.** `ai/`, `my/` and the main tree are directories on disk, edited by agents through file tools, not through the DB. DB row permissions cannot stop `Edit my/notes.md`. Enforcement belongs in harness hooks / sandbox rules / pre-commit checks. Also, SurrealDB table `PERMISSIONS` apply only to record-access users; an embedded process opened without `signin` runs as root and bypasses them.
- **Risk.** BSL 1.1 on the whole workspace including the SDK crate; on-disk format churn (2→3 export/import; 3.1 one-way row-format rotation inside a minor); development moved to a private repo in 3.1. Fine for a server you operate; heavy for a library baked into a CLI.
- **Sync.** Platform data that must cross machines (provenance, memory, attribution) needs the same merge story as memory. No DB here gives it offline over git. Keep those in git refs (append-only, union-mergeable); keep the DB local and rebuildable.

What SurrealDB is genuinely good at, kept for the revisit: graph edges (`RELATE`), record ids with composite keys, `DEFINE EVENT` audit trails, `CHANGEFEED` with pre-images, `LIVE SELECT`, record-level `PERMISSIONS`, FTS + vector in one engine. The schema below runs unmodified on 3.3.0.

## Requirements → storage needs

| Feature | Data | Shared across machines? | Live updates? | Natural store |
|---|---|---|---|---|
| Memory | append-only notes, summaries | yes | no | git ref (`refs/ai/memory`) |
| Provenance | who/what/when/model/session for each artifact | yes (travels with artifacts) | no | inline in artifact + git ref log; DB index |
| Attribution | AI vs human per line/commit | yes (with commits) | no | git notes / ref (see attribution doc); DB index |
| Agent floor | agents, sessions, tasks, assignments, messages, status | mostly no (per machine); maybe yes for tasks | **yes** | local DB |
| Workspaces | path → who may write | yes (versioned config) | no | file in repo (`ai/`, AGENTS.md) + hook enforcement |
| Audit | every state change | sometimes | no | DB triggers/events locally; summarised into git |

Takeaway: the DB's job is the *local, live, queryable* part. The *durable, shared* part is git.

## SurrealDB fit

| Need | SurrealDB feature | Fit | Caveat |
|---|---|---|---|
| agents↔tasks↔artifacts↔provenance | `RELATE` edges, typed `record<…>` links, `TYPE RELATION IN … OUT … ENFORCED` | excellent | graph traversal order not stable; order by keys |
| W3C-PROV-style lineage | `generated`, `used`, `derived_from` edges; `<-generated<-session.model` | excellent | — |
| ordered ids | array record ids `memory:[ts, origin]`, range scans `memory:[d'…', NONE]..` | excellent | — |
| row-level workspace rules | `PERMISSIONS FOR update WHERE …`, `DEFINE ACCESS … TYPE RECORD` | partial | only for record users; root (embedded default) bypasses; files on disk unaffected |
| orchestration push | `LIVE SELECT * FROM task WHERE status = 'open'` | good **in server mode** | embedded: same-process only |
| atomic claim | `UPDATE task:x SET status='claimed', owner=$me WHERE status='open' RETURN AFTER` | good | — |
| audit log | `DEFINE EVENT` → `task_log`; `CHANGEFEED 90d INCLUDE ORIGINAL`, `SHOW CHANGES FOR TABLE task SINCE …` | good | changefeeds expire; not a merge log |
| time travel | `SELECT … VERSION d'…'` (SurrealKV, `versioned=true`, retention) | nice | backend-specific; disk growth |
| search | `FULLTEXT ANALYZER … BM25 HIGHLIGHTS`, HNSW/DiskANN | good | — |
| embedded | `Surreal::new::<SurrealKv>(path)` | works | exclusive lock, 105 MB, ~0.9 s open |
| server | `surreal start surrealkv://…`, WS/HTTP/gRPC | works | daemon lifecycle, auth, upgrades |
| multi-machine | TiKV cluster / single shared server | poor for local-first | no offline merge |

### Embedded vs server

| | Embedded | Local server (`surreal start`) |
|---|---|---|
| Processes | one | many clients |
| Live queries | in-process only | all clients |
| Permissions | root unless `signin` | real record users per agent |
| Ops | none | start/stop, socket/port, auth secrets, version skew client↔server, crash restart, upgrades with export/import across majors |
| Binary | `ai` +100 MB | `ai` client (~WS client) + `surreal` binary (or `ai` embeds and serves) |
| OptMem rule "nothing in background" | kept | broken |

## Alternatives for the same role

| Option | Multi-process local | Live updates | Graph/provenance | FTS/vector | Footprint | License | Verdict |
|---|---|---|---|---|---|---|---|
| **SQLite + own schema** (rusqlite bundled, WAL) | **yes, no daemon** | poll `PRAGMA data_version` / watch WAL file (inotify) / daemon if ever needed | tables + edge tables + recursive CTEs | FTS5; `sqlite-vec` | +2 MB, 45 s build | public domain | **recommended** |
| libSQL / Turso DB | yes; MVCC concurrent writers (preview) | — | as SQLite | FTS, native vectors | moderate | MIT | watch; beta |
| SurrealDB embedded | **no** | in-process | excellent | yes | +100 MB | BSL | no |
| SurrealDB server | yes | **yes** | excellent | yes | daemon | BSL | revisit with a daemon |
| Postgres (+pgvector, LISTEN/NOTIFY) | yes | yes (`LISTEN/NOTIFY`) | good | yes | external server | PostgreSQL | too heavy for local-first CLI; right for a hosted team edition |
| Dolt / DoltLite | server / as SQLite | no | tables | limited | Go / C fork | Apache-2 | only if versioned shared tasks become core (beads model) |
| git refs only | CAS | no | append-only logs | scan | gix | — | durable/shared layer, not live state |

Established products agree on the split: Codex keeps JSONL rollouts as truth plus a SQLite `state.db` index; Claude Code keeps JSONL per session; beads uses a versioned DB with a server for multi-agent; Letta and Zep run servers (Postgres, Neo4j) because they are services.

## Design sketch

### Layers

```
git (shared, mergeable)          refs/ai/memory, refs/ai/prov (append-only provenance log),
                                 refs/notes/ai (attribution; per attribution doc)
local DB (live, rebuildable)     .git/ai/state.sqlite  (per clone, shared by worktrees)
                                 tables: agent, session, task, depends_on, message, task_log,
                                         artifact, generated, used, derived_from (+ index of git data)
files (human-facing)             ai/, my/, main tree; rules in a versioned file, enforced by hooks
```

- Orchestrator (when it exists) is just another `ai` process reading/writing the DB. Push-based fan-out can come from that process (it owns the agents it spawned), not from the DB.
- Provenance is written twice by design: inline on the artifact (memory record fields, commit trailers, attribution notes) as truth, and as DB rows/edges for querying. The DB is rebuildable from git + harness logs.
- Session identity: `$CLAUDE_CODE_SESSION_ID`, Codex rollout id, `$AI_SESSION`; model from `$AI_MODEL` or harness logs (Claude Code JSONL has the model per message even though env lacks it).

### Minimal schema (SurrealQL, validated on SurrealDB 3.3.0 embedded)

```sql
DEFINE TABLE workspace SCHEMAFULL;
DEFINE FIELD path    ON workspace TYPE string;
DEFINE FIELD writers ON workspace TYPE set<'ai' | 'human'>;

DEFINE TABLE agent SCHEMAFULL;
DEFINE FIELD kind    ON agent TYPE 'ai' | 'human';
DEFINE FIELD name    ON agent TYPE string;
DEFINE FIELD harness ON agent TYPE option<string>;

DEFINE TABLE session SCHEMAFULL CHANGEFEED 90d;
DEFINE FIELD agent      ON session TYPE record<agent>;
DEFINE FIELD parent     ON session TYPE option<record<session>>;   -- subagent tree
DEFINE FIELD harness_id ON session TYPE option<string>;
DEFINE FIELD model      ON session TYPE option<string>;
DEFINE FIELD origin     ON session TYPE string;                    -- clone id
DEFINE FIELD head       ON session TYPE option<string>;
DEFINE FIELD branch     ON session TYPE option<string>;
DEFINE FIELD started    ON session TYPE datetime VALUE time::now() READONLY;
DEFINE FIELD ended      ON session TYPE option<datetime>;

DEFINE TABLE task SCHEMAFULL CHANGEFEED 90d INCLUDE ORIGINAL;
DEFINE FIELD title     ON task TYPE string;
DEFINE FIELD body      ON task TYPE string DEFAULT '';
DEFINE FIELD status    ON task TYPE 'open' | 'claimed' | 'blocked' | 'done' DEFAULT 'open';
DEFINE FIELD owner     ON task TYPE option<record<agent>>;
DEFINE FIELD workspace ON task TYPE record<workspace>;
DEFINE FIELD by        ON task TYPE record<session>;
DEFINE FIELD updated   ON task TYPE datetime VALUE time::now();
DEFINE TABLE depends_on TYPE RELATION IN task OUT task ENFORCED;

DEFINE TABLE message SCHEMAFULL;
DEFINE FIELD task ON message TYPE option<record<task>>;
DEFINE FIELD from ON message TYPE record<session>;
DEFINE FIELD to   ON message TYPE option<record<agent>>;
DEFINE FIELD body ON message TYPE string;
DEFINE FIELD at   ON message TYPE datetime VALUE time::now() READONLY;

DEFINE TABLE task_log SCHEMAFULL;
DEFINE FIELD task ON task_log TYPE record<task>;
DEFINE FIELD from ON task_log TYPE string;
DEFINE FIELD to   ON task_log TYPE string;
DEFINE FIELD at   ON task_log TYPE datetime VALUE time::now() READONLY;
DEFINE EVENT status ON task WHEN $event = 'UPDATE' AND $before.status != $after.status THEN {
    CREATE task_log SET task = $after.id, from = $before.status, to = $after.status;
};

DEFINE TABLE artifact SCHEMAFULL;
DEFINE FIELD kind      ON artifact TYPE 'memory' | 'summary' | 'file' | 'commit' | 'note';
DEFINE FIELD locator   ON artifact TYPE string;                    -- path@oid, commit sha, ref:key
DEFINE FIELD workspace ON artifact TYPE option<record<workspace>>;

-- W3C PROV: wasGeneratedBy / used / wasDerivedFrom
DEFINE TABLE generated TYPE RELATION IN session OUT artifact | memory | summary;
DEFINE FIELD at   ON generated TYPE datetime VALUE time::now() READONLY;
DEFINE FIELD tool ON generated TYPE option<string>;
DEFINE TABLE used         TYPE RELATION IN session OUT artifact | memory | summary;
DEFINE TABLE derived_from TYPE RELATION IN summary | artifact OUT memory | summary | artifact;

DEFINE ANALYZER mem TOKENIZERS blank, class FILTERS lowercase, ascii;
DEFINE TABLE memory SCHEMAFULL;                                    -- id = memory:[ts, origin]
DEFINE FIELD text    ON memory TYPE string ASSERT string::len($value) <= 338;
DEFINE FIELD session ON memory TYPE record<session>;
DEFINE INDEX memory_text ON memory FIELDS text FULLTEXT ANALYZER mem BM25 HIGHLIGHTS;

DEFINE TABLE summary SCHEMAFULL;                                   -- id = summary:[size, fp]
DEFINE FIELD size    ON summary TYPE int;
DEFINE FIELD first   ON summary TYPE record<memory>;
DEFINE FIELD text    ON summary TYPE string;
DEFINE FIELD session ON summary TYPE record<session>;
```

Queries exercised (all but `LIVE SELECT` run on 3.3.0 with expected results):

```sql
CREATE memory:[d'2026-10-03T09:00:00Z', 'K3J9QZ'] SET text = '…', session = session:s1;
RELATE session:s1->generated->memory:[d'2026-10-03T09:00:00Z', 'K3J9QZ'] SET tool = 'ai memory note';
RELATE summary:[2, 'a1b2c3d4e5f60718']->derived_from->[memory:[…], memory:[…]];
UPDATE task:t1 SET status = 'claimed', owner = agent:claude WHERE status = 'open' RETURN AFTER;   -- atomic claim; event writes task_log
SELECT id, text FROM memory:[d'2026-10-03T00:00:00Z', NONE]..;                                  -- range by key
SELECT id, search::highlight('<', '>', 1) AS hit FROM memory WHERE text @1@ 'dir';              -- FTS
SELECT <-generated<-session.model AS model FROM memory:[…];                                    -- provenance
SELECT ->derived_from->memory.text AS leaves FROM summary:[2, '…'];                            -- zoom
SELECT id FROM task WHERE status = 'open' AND count(->depends_on->task[WHERE status != 'done']) = 0;  -- ready queue
SHOW CHANGES FOR TABLE task SINCE 0 LIMIT 10;                                                   -- audit
LIVE SELECT * FROM task WHERE status = 'open';                                                  -- orchestration (server mode)
```

Gotchas hit while validating: a one-element set literal `{'ai'}` parses as a block, use `<set>['ai']`; `->derived_from->` returned leaves in reverse insertion order, so ordering must come from record keys.

Workspace permission, if run as a server with record users per agent (parses on 3.3.0; enforcement not tested):

```sql
DEFINE ACCESS agent ON DATABASE TYPE RECORD SIGNIN (SELECT * FROM agent WHERE id = $id);
DEFINE TABLE OVERWRITE artifact SCHEMAFULL PERMISSIONS
  FOR select FULL
  FOR create, update WHERE workspace = NONE OR $auth.kind IN workspace.writers;
```

This guards DB rows only. File edits in `my/` are guarded by a harness `PreToolUse` hook / sandbox deny rule reading the same `workspace` definitions.

### SQLite equivalent (recommended)

Same tables, one-to-one: `RELATE` edges become `(in, out, at, …)` tables with indexes on both ends; `CHANGEFEED`/`EVENT` become `AFTER UPDATE` triggers into `task_log`; `memory:[ts, origin]` becomes `PRIMARY KEY (ts, origin) WITHOUT ROWID`; FTS via FTS5. Atomic claim: `UPDATE task SET status='claimed', owner=? WHERE id=? AND status='open' RETURNING *`. Cross-process change notification: `PRAGMA data_version` polling (cheap) or inotify on the `-wal` file. Schema migrations with `rusqlite_migration` or `PRAGMA user_version`.

## Attribution integration points

- Attribution facts (per commit, line ranges → agent/session/model) live with commits (git notes or a ref, per `20261003T103840--attribution.md`). They merge with commits.
- DB indexes them: `artifact(kind='commit', locator=<sha>)`, `generated` edge from `session`, edge properties for line ranges/hunks.
- Join key: harness session id. Memory records, attribution notes, commit trailers and DB sessions must all carry the same `session` and `origin` values. Define those once (env vars `AI_SESSION`, `AI_MODEL`, `AI_AGENT`; clone id `ai.memory.origin` → generalise to `ai.origin`).
- Workspace classification (AI / Human / Both by path) feeds attribution reports ("AI wrote 80% of `ai/`, 5% of `my/`").

## Open questions for the user

1. Will `ai` run a long-lived orchestrator process (agent floor), or stay a set of short CLI calls driven by harnesses? This decides daemon-or-not, hence SQLite vs SurrealDB server.
2. Is BSL acceptable for `ai`? Any plan for a hosted/team edition (where the Use Grant matters)?
3. Should tasks/assignments sync across machines (beads-style), or are they per-machine runtime state? If shared, they join memory in git refs.
4. Workspace enforcement: hooks/sandbox on file paths (proposed), DB permissions, or both?
5. Provenance vocabulary: adopt W3C PROV terms (`generated`, `used`, `derived_from`, `associated_with`) as the canonical names?
6. Per-clone DB at `.git/ai/state.sqlite`, or per-user global `~/.local/share/ai/state.sqlite` with a repo column?
