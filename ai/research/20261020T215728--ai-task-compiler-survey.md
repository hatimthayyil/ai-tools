# Compile explicit task plans into work

`ai task` should compile an authored work breakdown into a validated dependency graph, then combine that graph with recorded progress to explain what can happen next. TaskJuggler supplies the compiler model; Beads supplies the closest agent-facing task workflow. Taskwarrior and Org show useful identity, hierarchy and progress conventions. Snakemake shows when dependencies can be derived from explicit inputs and outputs. Plane Compose shows how to make proposed plan changes reviewable. **The agreed v1 scope is hierarchy, validation, ready tasks and execution order; calendar and resource scheduling come later.** The design below is a proposal within that scope, rather than a set of settled requirements.

The key boundary is between authoring and compilation. Humans and agents decide what work achieves the goal, whether the breakdown is adequate, and which tasks require other tasks. A deterministic compiler checks those declarations and derives their consequences. Task prose alone does not establish a dependable prerequisite relation. An agent can propose one, but the resulting explicit declaration is the compiler's input.

| Product | Useful model for `ai task` | Boundary to preserve |
| --- | --- | --- |
| [TaskJuggler](https://taskjuggler.org/tj3/manual/Getting_Started.html) | Compile a hierarchical project description through validation and calculation into reports. | Its calendar/resource scheduler solves a larger problem than execution readiness. |
| [Beads](https://github.com/gastownhall/beads/blob/882317770349f3c2f61e603b5c1e74030354c955/docs/workflows/molecules.md) | Explicit task graphs, reusable authored workflows, preview, ready work and progress transitions. | Template expansion, live task state and worker coordination are separate concerns. |
| [Taskwarrior](https://taskwarrior.org/docs/man/task.1/) | Small task operations, permanent identity, explicit prerequisites and derived readiness. | Hierarchical project names group tasks; they do not establish a task breakdown tree. |
| [Org](https://orgmode.org/manual/TODO-dependencies.html) | Tasks inside an editable outline, subtree moves and explicit completion rules. | Outline order requires a separate rule before it constrains execution. |
| [Snakemake](https://snakemake.readthedocs.io/en/stable/tutorial/basics.html) | Derive a prerequisite DAG from declared inputs, outputs and requested targets. | File production is stronger and narrower than completing arbitrary human work. |
| [Plane Compose](https://developers.plane.so/dev-tools/plane-compose#reference) | Projects-as-Code YAML, authored IDs, offline validation and previewable reconciliation. | Its application plan describes remote changes, rather than work execution order. |

TaskJuggler makes the compiler idea concrete: project source is parsed, scheduled and rendered into reports. Its source separates preparation and consistency checks from scheduling; dependency diagnostics include invalid references and cycle paths. This suggests clear phases for `ai task`: parse, resolve identities, validate structure, derive the graph, evaluate progress, render explanations. Diagnostics should identify the task and declaration responsible, including the actual cycle rather than only reporting that one exists. ([Getting started](https://taskjuggler.org/tj3/manual/Getting_Started.html), [compiler entry point](/hatimthayyil/code/TaskJuggler/lib/taskjuggler/TaskJuggler.rb:42), [project preparation](/hatimthayyil/code/TaskJuggler/lib/taskjuggler/Project.rb:1094), [dependency checks](/hatimthayyil/code/TaskJuggler/lib/taskjuggler/TaskScenario.rb:2317))

Its task model distinguishes containers, regular tasks and milestones; container dates derive from descendants. Dependencies are separately declared, rather than implied by containment. Its scheduler is heuristic, not a global optimizer, and task completion percentages are reporting data without a scheduling effect. Therefore, borrowing TaskJuggler's compiler structure does not automatically provide the recorded-state readiness that `ai task` needs. Resource allocation, calendars, duration estimates, actuals and scenarios are useful later references. ([Tasks](https://taskjuggler.org/tj3/manual/task.html), [dependencies](https://taskjuggler.org/manual/depends.html), [internals](https://taskjuggler.org/tj3/manual/TaskJuggler_Internals.html), [completion](https://taskjuggler.org/tj3/manual/complete.html), [allocation](https://taskjuggler.org/tj3/manual/allocate.html), [actuals](https://taskjuggler.org/manual/Day_To_Day_Juggling.html), [scenarios](https://taskjuggler.org/tj3/manual/scenario.html))

Beads provides the strongest reference for turning explicit plans into agent work. Its molecules contain actual parent-child records; dotted identifiers alone do not establish hierarchy. Siblings are parallel by default, and explicit blocking relations constrain progress. Its formulas declare `needs`, can expand nested workflows, and support considerably more composition than a first version needs. `bd cook` can emit an inspectable graph without persisting live work. Borrow that separation between source, compiled preview and recorded tasks. Avoid adopting the whole formula language before ordinary hand-authored plans work well. ([Molecules](https://github.com/gastownhall/beads/blob/882317770349f3c2f61e603b5c1e74030354c955/docs/workflows/molecules.md#L45), [dependency relations](https://github.com/gastownhall/beads/blob/882317770349f3c2f61e603b5c1e74030354c955/docs/core-concepts/dependencies.md#L34), [formulas](https://beads.gascity.com/workflows/formulas), [cook](https://github.com/gastownhall/beads/blob/882317770349f3c2f61e603b5c1e74030354c955/docs/cli-reference/cook.md#L10))

Beads also demonstrates why readiness needs an explanation. Its ready command accounts for progress, blocking and deferral, with an explanation option. Live claims use a compare-and-swap transition; leases add heartbeat and reclamation machinery. Those are valuable execution-coordination features, but they can follow a reliable planning core. Readiness itself can depend on time and ordering policy: Beads' implementation includes priority, creation order and clock-sensitive policies. A deterministic `ai task` must make every such input explicit. ([Ready](https://github.com/gastownhall/beads/blob/882317770349f3c2f61e603b5c1e74030354c955/docs/cli-reference/ready.md#L10), [ready implementation](https://github.com/gastownhall/beads/blob/882317770349f3c2f61e603b5c1e74030354c955/internal/storage/sqlbuild/ready.go#L47), [claims](https://github.com/gastownhall/beads/blob/882317770349f3c2f61e603b5c1e74030354c955/internal/storage/issueops/claim.go#L24), [leases](https://github.com/gastownhall/beads/blob/882317770349f3c2f61e603b5c1e74030354c955/internal/storage/issueops/lease.go#L21))

Taskwarrior reinforces two useful distinctions. Its UUID is permanent while displayed numeric IDs can change; `ai task` should likewise distinguish identity from a path or display number. Its derived tags distinguish readiness from starting work, while an active task is not an exclusive worker claim. Org contributes editable hierarchical context and stable links across moves. Its optional dependency rules can prevent a parent becoming done before children, while `ORDERED` explicitly makes siblings sequential. These are policies worth choosing deliberately, rather than accidental consequences of outline layout. ([Taskwarrior IDs](https://taskwarrior.org/docs/ids/), [tags](https://taskwarrior.org/docs/tags/), [terminology](https://taskwarrior.org/docs/terminology/), [Org structure editing](https://orgmode.org/manual/Structure-Editing.html), [links](https://orgmode.org/manual/Handling-Links.html), [dependencies](https://orgmode.org/manual/TODO-dependencies.html))

Plane Compose addresses a different part of the lifecycle: evolving an authored project without making changes opaque. It is a Projects-as-Code CLI for YAML-defined Plane configuration and work items, with `parent`, `blocked_by`, `blocking` and authored IDs. Offline validation checks local input; dry-run and diff expose intended remote changes; resume handles partial application. Authored stable IDs matter because omitted IDs can be derived from content, making title changes affect identity. Its documented push order concerns applying configuration and work items to Plane. The surveyed documentation does not establish a ready-work or topological execution compiler. Borrow reviewable changes and identity discipline, and defer external reconciliation. ([Product](https://plane.so/plane-compose), [CLI reference](https://developers.plane.so/dev-tools/plane-compose#reference), [synchronization modes](https://plane.so/blog/everything-you-need-to-know-about-plane-compose))

The proposed core model has **a containment tree and a prerequisite DAG**. A parent groups scope; a prerequisite says that one task requires another's accepted result. Sibling display order affects presentation only. Stable IDs survive renaming and moving; paths and outline numbers remain readable addresses. Containers organize actionable leaves and summarize their progress. V1 should initially restrict prerequisite edges to actionable tasks, keeping container completion policy explicit instead of silently expanding edges across every descendant.

Recorded status should distinguish pending, in progress, done and canceled. **A terminal task does not necessarily satisfy a prerequisite.** Proposed default: only done satisfies an edge; canceling a prerequisite leaves its dependents blocked until the plan is deliberately revised. Container summaries can report that all children are terminal while still showing canceled scope. This avoids representing abandonment as successful delivery. Beads' source distinguishes non-completing closure through reason classification; that is evidence for making the distinction structural in a new model. ([Non-completing closure](https://github.com/gastownhall/beads/blob/882317770349f3c2f61e603b5c1e74030354c955/internal/types/non_completing_close.go#L8))

A minimal authored example could use YAML, with stable IDs and separate parent references. This illustrates the information needed, not an agreed file format or command syntax.

```yaml
tasks:
  - id: release
    title: Ship the integration
  - id: contract
    parent: release
    title: Agree the API contract
  - id: api
    parent: release
    title: Implement the API
    needs: [contract]
  - id: client
    parent: release
    title: Implement the client
    needs: [contract]
  - id: integration
    parent: release
    title: Verify the integration
    needs: [api, client]
```

This diamond establishes three different outputs. Initially, the ready frontier contains only `contract`. Once it is done, both `api` and `client` are ready; completing only `api` does not release `integration`. A canonical topological order chooses one stable linear presentation, such as `contract, api, client, integration`; the alternative ordering with `client` first is equally valid. The displayed order must not serialize independent tasks. Nor should the compiler impose global waves: a downstream task depending only on `api` could become ready while `client` remains unfinished. Actual parallel execution depends on available people or workers and belongs to a later coordination layer.

The v1 compiler should reject duplicate or missing IDs, missing parents, containment cycles, unknown prerequisites, self-dependencies and prerequisite cycles. It should normalize declarations and produce actionable leaves, container summaries, direct and transitive blockers, a ready frontier and a canonical topological order. A proposed `check` validates, `plan` renders the compiled result, `ready` shows currently available work, and `explain <id>` names blockers and their paths. Progress operations record start, completion, cancellation and reopening. Human output and structured output should express the same facts.

The determinism contract should be precise: **the same normalized source, recorded state and explicit policy/compiler version produce the same semantic plan and ordering**. Identity creation happens during authoring, rather than changing on every compilation. Ordering uses a documented stable tie-break. Compilation should not consult the current clock, random selection or unrecorded external state. TaskJuggler itself has clock-derived defaults and random allocation selection, so deterministic behavior cannot be inferred merely from using a compiler architecture. Byte-identical output is a separate promise that would require canonical serialization. No reproducibility guarantee was established by this survey. ([TaskJuggler selection](https://taskjuggler.org/tj3/manual/select.html), [clock default](/hatimthayyil/code/TaskJuggler/lib/taskjuggler/Project.rb:89))

The next layer should address **plan revision while preserving identity and progress**. Renaming or moving a task should preserve its state. Adding a prerequisite to completed work, deleting a started task or changing what completion means requires an impact explanation. A reviewable change should show changed edges, newly blocked or newly ready tasks and affected completed work. Plane Compose's preview and conflict model is useful inspiration here, although reconciling remote records does not resolve the semantics of revising completed work. The Beads survey did not establish an edited-formula-to-live-graph reconciliation contract. ([Plane Compose reference](https://developers.plane.so/dev-tools/plane-compose#reference))

After that core works, reusable plan fragments can expand into the same simple graph. A later explicit `requires`/`produces` model could derive edges from named artifacts, following Snakemake's declared-input/declared-output approach. Missing producers, ambiguous producers and cycles would need diagnostics. Snakemake also illustrates that rule declaration order is not execution order, and independent jobs can run concurrently. Human deliverables require an acceptance rule: the mere existence of a file does not prove that a contract, review or decision is complete. Avoid claiming that arbitrary executable workflow definitions are inherently deterministic. ([Basics](https://snakemake.readthedocs.io/en/stable/tutorial/basics.html), [producer ambiguity and rule order](https://snakemake.readthedocs.io/en/stable/snakefiles/rules.html), [parallel execution](https://snakemake.readthedocs.io/en/stable/tutorial/advanced.html))

Full template composition, claims and leases, worker dispatch, external sync, calendar dates, resource leveling and schedule optimization should follow demonstrated need. The first useful end-to-end product is an authored hierarchy with explicit edges, strong diagnostics, recorded outcomes and trustworthy next-work explanations. Three decisions remain: which authoring representation users should edit; whether containers can themselves carry work or prerequisites; and which changes to started or completed tasks require an explicit reconciliation action. Storage selection can wait until those behaviors are clear.

This report compares documented models and inspected source, rather than runtime benchmarks. TaskJuggler was inspected at local commit `c0c4cea1f00ce590333ef073739c4e9855d3fdc0` (3.7.2). The local Beads directory contained only Git metadata; its committed objects were inspected at `882317770349f3c2f61e603b5c1e74030354c955` (1.3.0), and links above pin that revision. Other citations refer to official documentation. No product execution tests were performed. Missing capabilities are reported as unestablished by this survey, rather than proven absent.
